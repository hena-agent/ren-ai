# Running OpenCode V2 inside the server (2.0.16)

## Answer

Yes: `@opencode/sdk` hosts OpenCode's API router in memory, accepts a server-defined `@opencode/plugin` at startup or later, and creates sessions whose `location.directory` points to the persona checkout. This permits one Mac-mini Bun/Effect v4 server to own the HTTP API, OpenCode, and the imsg tool implementation without a second listener. **Set `database.path` explicitly**: the embedded SDK defaults to `:memory:`, not the CLI's persistent database. The alternative, `@opencode/client`, is a thinner integration for the application but requires a separately supervised OpenCode service and puts the imsg plugin in that service's process, not in the client. For the map's preference for one clean process, choose the embedded SDK **if sharing a failure domain and managing its persistent database are acceptable**; otherwise choose the client/service boundary. [SDK guide](https://opencode.ai/v2/docs/build/sdk) · [SDK host source at v2.0.16](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/sdk/src/internal/host.ts) · [client guide](https://opencode.ai/v2/docs/build/client) · [map](https://github.com/hena-agent/ren-ai/issues/1).

## Loading the persona and binding tools

- Create the session with `location: { directory: "/Users/chris/git/hena-agent/persona" }` and `agent: "Persona1"`. V2 discovers `.opencode/agents/Persona1.md` and `.opencode/plugins/strip-system-context.js` in the project's `.opencode` directory and loads its `opencode.jsonc`; the existing config disables `opencode.tools`. An agent Markdown body is its system prompt. The current Persona1 agent starts with a blanket permission deny, so any intended imsg tool must be **explicitly allowed after** that deny; never broaden shell access. [Session create OpenAPI](https://opencode.ai/v2/openapi.json) · [agents](https://opencode.ai/v2/docs/agents) · [config](https://opencode.ai/v2/docs/config) · [plugin discovery](https://opencode.ai/v2/docs/build/plugins) · [permissions](https://opencode.ai/v2/docs/permissions) · [persona files](https://github.com/hena-agent/persona/blob/main/.opencode/agents/Persona1.md), [config](https://github.com/hena-agent/persona/blob/main/opencode.jsonc), [plugin](https://github.com/hena-agent/persona/blob/main/.opencode/plugins/strip-system-context.js).
- Pass `plugins: [imsgPlugin]` to `OpenCode.create()` or register it with `await opencode.plugin(imsgPlugin)`; `ctx.tool.transform` adds the tools and each tool execution receives `context.sessionID` (and `signal`). The plugin should resolve that ID against the server-owned Conversation→session/Handle mapping, not accept a recipient from model input or trust session metadata as authorization. Session creation accepts arbitrary metadata, but the last security rule is an architectural inference from the trust boundary in [ADR 0001](https://github.com/hena-agent/ren-ai/blob/main/docs/adr/0001-personas-act-only-through-conversation-bound-tools.md). [SDK guide](https://opencode.ai/v2/docs/build/sdk) · [plugin tools](https://opencode.ai/v2/docs/build/plugins#tools) · [tool context schema](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/schema/src/tool.ts) · [session create OpenAPI](https://opencode.ai/v2/openapi.json).
- SDK `instances: { key, configure }` can select plugins per session, reconstructed from a persisted session key after cache misses/restarts; it is optional for a single shared plugin that looks up the Conversation by session ID. The `key` is further scoped to the canonical Location. Whether a per-Conversation plugin instance is needed is a design choice, **not** a requirement for the basic integration. [SDK Promise interface](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/sdk/src/promise.ts) · [instance selector implementation](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/sdk/src/internal/instances.ts).

## Runtime and Effect v4

- The installed `/Users/chris/.bun/bin/opencode --version` reports **v2.0.16**; the installed `@opencode/cli` package selects a platform executable. Published 2.0.16 `@opencode/sdk` depends on `@opencode/client`, `@opencode/core`, `@opencode/plugin`, `@opencode/schema`, `@opencode/server` and **`effect@4.0.0-rc.112`**; `@opencode/server` depends on **`@effect/platform-node@4.0.0-rc.112`**. This is the same Effect major as the proposed HTTP server, but align the exact RC and avoid duplicate Effect versions rather than assuming any arbitrary v4 release is compatible. [SDK package](https://unpkg.com/@opencode/sdk@2.0.16/package.json) · [server package](https://unpkg.com/@opencode/server@2.0.16/package.json) · [CLI package](https://unpkg.com/@opencode/cli@2.0.16/package.json).
- The SDK has a Promise API and an Effect-native entrypoint (`@opencode/sdk/effect`, including `OpenCode.layer()`); the network client likewise offers Promise and Effect entrypoints. Both can sit beside an Effect v4 HTTP application. [Effect SDK guide](https://opencode.ai/v2/docs/build/sdk/effect) · [Effect client guide](https://opencode.ai/v2/docs/build/client/effect).
- **Bun is the conservative choice for embedding the requested local Bun TypeScript plugin.** The 2.0.16 core publishes separate Bun and Node SQLite/PTY/runtime modules, and the plugin loader selects Bun's transpiler or Node's module loader by runtime. Thus the SDK is **not declared Bun-only**; Node embedding has a Node-specific SQLite implementation (`node:sqlite`), but a full Node + local TypeScript imsg plugin + native-dependency startup has **not been verified**. Do not equate a Bun-compiled `opencode` executable with a requirement that an HTTP client run on Bun. The main `@opencode/client` entrypoint is browser-compatible; its `/service` process-management entrypoint is Node API based. The separate OpenCode service can run the installed executable while the app/client runs Node or Bun; keeping the imsg plugin Bun TypeScript on the service side still needs its service runtime to support that plugin. [core package conditional imports](https://unpkg.com/@opencode/core@2.0.16/package.json) · [Bun plugin loader](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/plugin/src/source.bun.ts) · [Node plugin loader](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/plugin/src/source.node.ts) · [client guide](https://opencode.ai/v2/docs/build/client) · [client service implementation](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/client/src/promise/service.ts).

## Sessions, persistence, credentials and failure

- A single host/service manages multiple sessions; execution is coordinated **per session**, so prompts on the same session coalesce/queue rather than implying global serialization. Different sessions can run concurrently (including restart recovery with unbounded concurrency); the app still needs its own policy to serialize messages or imsg actions for the *same Conversation*, enforce budgets and handle provider limits. [session execution](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/core/src/session/execution.ts) · [restart sweep](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/core/src/session/execution/restart.ts) · [session API](https://opencode.ai/v2/openapi.json).
- `OpenCode.create({ database: { path: "/absolute/path/to/opencode.db" }, plugins: [imsgPlugin] })` avoids the SDK's `:memory:` default; the embedded host starts a background sweep that resumes suspended sessions. A managed separate service normally uses `~/.local/share/opencode/opencode.db` or `OPENCODE_DB`. Both retain history and stored credentials **only if backed by persistent storage**. Stored integration credentials live in OpenCode's SQLite credential table; provider environment variables belong to the **OpenCode host/service process**, not the remote HTTP client. Treat that database and backups as secrets. [SDK host](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/sdk/src/internal/host.ts) · [database options](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/core/src/database/database.ts) · [credential storage](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/core/src/credential.ts) · [providers](https://opencode.ai/v2/docs/providers) · [service files](https://opencode.ai/v2/docs/troubleshooting#service-files).
- A crash of the in-process OpenCode host also kills the app's API/imsg orchestration; a crash of a separate service leaves the API process up but its OpenCode calls fail until the service recovers. The SDK owns an explicit `close()`/async-dispose lifecycle; the Node client `/service` helper can discover/ensure/start/stop an authenticated registered service with version checks. Either host may resume suspended turns after a crash/restart from durable execution claims, **at least once**, not exactly once: an imsg send completed before a crash can be repeated on replay unless the app/tool boundary enforces idempotency against durable message/action IDs. Only one live OpenCode owner should operate on the same database; the recovery source explicitly assumes the previous owner is dead. [SDK guide](https://opencode.ai/v2/docs/build/sdk) · [restart source](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/core/src/session/execution/restart.ts) · [service helper](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/client/src/promise/service.ts).
- Event subscriptions are live-only, without replay/auto-reconnect; persist authoritative Conversation↔session and send state separately and reconcile on restart through session/message APIs, not events alone. Compaction can summarize old messages and lose exact details in model context even though old messages remain stored, so important routing and consent state belongs outside model history. [client events](https://opencode.ai/v2/docs/build/client#stream-events) · [compaction](https://opencode.ai/v2/docs/compaction).

## Upgrade and architecture comparison

| | Embedded `@opencode/sdk` | Separate service + `@opencode/client` |
| --- | --- | --- |
| Upgrade | Bump npm-pinned SDK and its OpenCode dependencies; deploy/restart **the API process** together with its server-defined plugin. Merely upgrading the installed CLI does not upgrade the SDK. [SDK package](https://unpkg.com/@opencode/sdk@2.0.16/package.json) · [SDK host](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/sdk/src/internal/host.ts) | Upgrade/restart the **OpenCode service executable** independently; keep client/API types compatible with the server API. `Service.ensure({version})` can detect a version mismatch and replace a managed local service. Global config `update: "auto"` installs an update but does not restart the running server. [service helper](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/client/src/promise/service.ts) · [client guide](https://opencode.ai/v2/docs/build/client#local-background-service) · [config updates](https://opencode.ai/v2/docs/config#updates) |
| Plugin ownership | Direct registration from API code; one runtime, one supervision target, no OpenCode HTTP listener. [SDK guide](https://opencode.ai/v2/docs/build/sdk) | The client only calls HTTP; plugin runs in the *other* process and must be deployed/configured there. For conversation-bound imsg tools, share an authenticated server-side binding or RPC across processes (additional design), not a closure in the client. [client guide](https://opencode.ai/v2/docs/build/client) · [plugin loading](https://opencode.ai/v2/docs/build/plugins) · [ADR 0001](https://github.com/hena-agent/ren-ai/blob/main/docs/adr/0001-personas-act-only-through-conversation-bound-tools.md) |
| Simplicity / isolation | Fewer moving parts, but larger failure domain, explicit DB path and lifecycle. [SDK host](https://github.com/anomalyco/opencode/blob/v2.0.16/packages/sdk/src/internal/host.ts) | Cleaner process failure and independent upgrade boundary, but a second process, local auth/transport and more complicated plugin-to-Conversation binding. [client service guide](https://opencode.ai/v2/docs/build/client#local-background-service) · [plugin context](https://opencode.ai/v2/docs/build/plugins#context) |

**Open question:** The map calls for *one SQLite file for all state*. The SDK lets the caller select an OpenCode database path, but the published API does **not** document adding application-owned tables or sharing the same SQLite connection/transaction with that database. This is **unconfirmed**, not a promise of atomic app/OpenCode state in one file; the managed service's normal default is its own database. Decide whether “one SQLite file” is literal for both domains or means one app-owned authoritative file before implementing; do not assume cross-process or cross-library atomic writes.
