# Detecting whether a handle has iMessage

## Answer

With the planned SIP-enabled Mac mini, send the Greeting to the submitted Handle with `imsg send --service imessage --no-sms-fallback`, then **check the resulting message's delivery state**; do not equate either a failed command with “no iMessage” or a successful command with a reachable Handle. An explicit iMessage send cannot automatically retry over SMS, but imsg's immediate success means Messages accepted the automation and, when readable, a matching outgoing row appeared, **not** that the other device received it. Treat delivery as positive evidence, an iMessage-specific negative as a waitlist candidate, and timeout/transport/account/unknown outcomes as indeterminate rather than falsely telling someone they lack iMessage. The only live, no-message availability route implemented by imsg is bridge-backed IDS (`whois` or RPC `handles.check`), which needs the injected helper and SIP disabled; local history is not a live check. [imsg send implementation](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/SendCommand.swift#L101-L201), [send verifier](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/SentMessageVerifier.swift#L12-L35), [bridge implementation](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgHelper/HandleHandlers.inc#L1-L51), [bridge prerequisites](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#L40-L49).

## What forced sending actually does

- `--service imessage` explicitly selects iMessage; `--no-sms-fallback` disables only the automatic fallback offered for *auto*, text-only, direct phone sends, so it is redundant here. For a fresh direct recipient, imsg normalizes the phone number, selects the first Messages AppleScript service of type `iMessage`, gets `buddy <handle>` on that service and calls `send`. **There is no pre-send IDS lookup in this path.** A previously stored direct chat may instead be selected, still honoring the explicit service. [CLI routing](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/SendCommand.swift#L130-L173), [AppleScript and fallback eligibility](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageSender.swift#L78-L113), [AppleScript dispatch](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageSender.swift#L208-L276).
- imsg's own docs say an explicit iMessage send to a non-iMessage phone fails fast, but source only guarantees a synchronous failure **if** Messages' AppleScript reports one; before-dispatch errors are `not_started`, errors during/after dispatch are `may_have_completed`. Its transport preserves the numeric AppleScript error but does not decode it as “not registered”. A Mac/account/automation/network failure can also fail the command. What this Mac's Messages version does for an unregistered phone or email (immediate script error versus an outgoing row later marked failed) is **unconfirmed**. [troubleshooting](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/troubleshooting.md#L61-L67), [dispatch-phase marker](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageSender.swift#L208-L276), [error interpretation](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/AppleScriptSendTransport.swift#L67-L117).
- After AppleScript success, CLI `send` searches `chat.db` for matching outgoing text in the selected chat (100 ms polling, eight-second deadline). A missing row becomes `may_have_completed` (no safe retry), whereas a present row is reported as `sent`, often with row ID/GUID. If the database cannot be opened for a direct send, the command can report success without verification. **The row check does not inspect `message.error`, `is_delivered`, or `date_delivered`.** [CLI](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/SendCommand.swift#L106-L112), [verifier](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/SentMessageVerifier.swift#L12-L35), [verification docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/send.md#L98-L109).

## Failure records and observation

- imsg reads `message.error` (integer), `service`, `is_sent`, `is_delivered`, `date_delivered`, `is_delayed`, etc. from `chat.db`; any nonzero `error` yields `failed`, delivery flags/date yield `delivered`, and `is_sent` yields `sent` otherwise `pending`. These fields can be retrieved by GUID via JSON-RPC `message.send_status`; there is no equivalent delivery-status test inside CLI `send`. Neither imsg's source nor Apple's cited public documentation establishes a **specific numeric `message.error` code** for “not registered for iMessage” on macOS 26; the code, row presence, and time to transition after an unregistered-handle send are **unconfirmed**. Do not confuse a numeric AppleScript error with a database `message.error`. [database query and decoding](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore%2BMessages.swift#L325-L358), [status classification](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageSendStatus.swift#L3-L29), [RPC result](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/RPCServer%2BMessageStatusHandlers.swift#L5-L56), [AppleScript error handling](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/AppleScriptSendTransport.swift#L86-L117).
- `imsg whois --local` and auto routing infer prior service from `handle`/`message` history (at least one matching iMessage row with `error == 0`, otherwise SMS-only or unknown). A non-errored row is **not a fresh delivery receipt**; absence of history is unknown, and historical reachability can be stale. [local classifier](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore%2BServiceAvailability.swift#L32-L79), [whois local](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/BridgeIntroCommands.swift#L168-L190).

## No-message IDS path and reliability

- The bridge's `chat-create` resolves/creates a first-contact Handle through the active iMessage account, then checks its canonical address **before** creating or inviting participants. Its `handleCheckIMessageAvailability` queries private `IDSIDQueryController` for `tel:` or `mailto:` destination and service `com.apple.madrid`; `id_status == 1` is available, `2` means unreachable in chat creation, while any other status is **unconfirmed**, not an explicit negative. This check itself sends **no message**. Do not create a chat just to query: `imsg whois --address …` and RPC `handles.check` expose that same bridge action directly. [chat resolution](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgHelper/ChatResolution.inc#L85-L133), [IDS handler](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgHelper/HandleHandlers.inc#L1-L51), [whois](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/BridgeIntroCommands.swift#L168-L237), [RPC](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/RPCServer%2BHandlesCheckHandler.swift#L5-L48).
- That handler uses a synchronous **current** IDS status selector, without a forced refresh or explicit TTL; its fallback selector passes a nil service. Freshness/behavior on cache misses, transient outages and macOS 26 are **unconfirmed**. By contrast, BlueBubbles' own helper uses `forceRefreshIDStatusForDestinations` asynchronously with the iMessage service and returns `available` only for status 1; its server exposes an availability API but also needs its private helper. This is evidence that a no-message live query exists, **not** that imsg's current-status query is fresh or usable with SIP on. [imsg selector](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgHelper/HandleHandlers.inc#L26-L50), [BlueBubbles helper](https://github.com/BlueBubblesApp/bluebubbles-helper/blob/1ee57f3fde63f8cc5769d60cfabfe9a06fcc1069/Messages/MacOS-11%2B/BlueBubblesHelper/BlueBubblesHelper.m#L637-L661), [BlueBubbles server](https://github.com/BlueBubblesApp/BlueBubbles-Server/blob/f2e2286241a7c3b6617a82b37d4afaab4df3a6b9/packages/server/src/server/api/interfaces/handleInterface.ts#L76-L86).
- Apple's Messages settings distinguish signing into an Apple Account from the email addresses and phone numbers selected under “You can be reached for messages at”. Therefore an email merely being an Apple Account **does not prove that particular email currently accepts iMessage**; treat it exactly like any other Handle and require a delivery receipt or confirmed current IDS registration. Whether a disabled-iMessage Apple Account email yields IDS status 2, status 0, or a particular send error on this Mac is **unconfirmed**. [Apple Messages settings](https://support.apple.com/guide/messages/change-imessage-settings-in-messages-on-mac-icht39422/mac).
- The bridge requires `imsg launch` with SIP disabled, and imsg documents additional macOS 26 library-validation/entitlement problems even then. It is not an operational option on the specified SIP-enabled Mac mini. No public Apple iMessage-availability endpoint was confirmed in the cited first-party material; private IDS and historical local data are the identified no-message methods, with only local history available under the current configuration. [imsg prerequisites](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#L40-L49), [launch refusal](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#L69-L73), [whois local versus live](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/BridgeIntroCommands.swift#L168-L190).

## How long a caller waits

| Route | Source-backed bound; meaning |
| --- | --- |
| Forced CLI text Greeting | AppleScript child can take up to **150 s**, then outgoing-row verification up to **8 s** when `chat.db` is readable (approximately **158 s** plus startup/DB overhead; not an end-to-end SLA). A pre-dispatch rejection may arrive sooner, but its typical latency is **unconfirmed**. A found row still needs subsequent delivery-status polling; no guaranteed bound exists for receiving a definitive delivered/failed verdict. [transport timeout](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/AppleScriptSendTransport.swift#L3-L8), [send timeout](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/IMsgBridgeProtocol.swift#L25-L40), [eight-second verifier](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/SentMessageVerifier.swift#L12-L35). |
| Live `whois` / `handles.check` | The imsg bridge defaults non-send actions to a **10 s per-request timeout**, excluding helper launch/startup; actual typical IDS latency is **unconfirmed**. `chat-create` is a send-style bridge action with a **150 s** wait and mutates a chat, so use the direct check instead if a helper ever becomes available. [bridge timeouts](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/IMsgBridgeProtocol.swift#L25-L40). |
| `whois --local` | Database lookup only; no network wait or specified wall-clock deadline, but historical/unknown rather than current reachability. [local query](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore%2BServiceAvailability.swift#L39-L79). |
