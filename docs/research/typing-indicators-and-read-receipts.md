# Typing indicators and read receipts on macOS 26.6.2

## Answer

There is **no verified SIP-on method that guarantees** Persona1 can show a receiver-visible “typing…” indicator before every send *and* choose precisely when a User receives a read receipt. `imsg` implements both controls inside an injected Messages helper and refuses injection while SIP is enabled; a first-hand report confirms a healthy injected bridge with typing/read capabilities on **macOS 26.6.1**, SIP off, **without** the separate library-validation plist change, but not delivery to a second device or operation on this Mac mini's **26.6.2** build. [imsg advanced-feature docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#why-theyre-separate) · [26.6.1 report and correction](https://github.com/openclaw/imsg/issues/236)

With SIP on, driving Messages' composer and selecting/marking a Conversation read through its UI are candidates, **not demonstrated substitutes**: receiver-visible typing, exact read-receipt timing and locked/sleeping operation remain unconfirmed. Apple's read-receipt switch also has per-person overrides, so enabling the global switch does not alone establish a guarantee for every User. [imsg UI proposal](https://github.com/openclaw/imsg/issues/22) · [Apple's macOS 26 read-receipt guide](https://support.apple.com/guide/messages/turn-read-receipts-on-or-off-ichtee6857f6/14.0/mac/26) · [Apple's Mark as Read UI](https://support.apple.com/guide/messages/mark-a-conversation-as-unread-ichtf9781355/14.0/mac/26)

## Injected `imsg` bridge: feasibility and conditions

- The normal `send`, `history`, and `watch` paths do not need SIP disabled; `typing` and `read` use `DYLD_INSERT_LIBRARIES` to load a helper *inside* Messages.app. `imsg launch` checks SIP and refuses injection when it is on; `imsg status` probes availability without injecting. The helper calls `setLocalUserIsTyping:` and `markAllMessagesAsRead` on an IMCore chat; its success response alone is not receiver-device proof. [imsg docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#building-and-launching) · [helper implementation](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgHelper/ReadStatusHandlers.inc#L3-L165)
- Historical failure modes **are distinct**. On 26.3, direct third-party IMCore XPC connections were rejected by `imagent` for missing Apple-private entitlements; a maintainer left injection/library-validation as an open concern. The current code **prefers the injected helper**, falling back to direct IMCore; rejection of the latter does not prove the former fails. [imsg #60, reporter and maintainer](https://github.com/openclaw/imsg/issues/60) · [typing transport source](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/TypingIndicator.swift#L43-L60)
- The macOS 26 bridge was fixed after initially shipping silent typing/read RPC no-ops; later releases fixed helper initialization and an Apple-silicon **arm64e** slice needed by Messages, then repaired macOS 26 typing diagnostics following selector changes. These are version-dependent reasons to use a current matching CLI/helper, not evidence of a 26.6.2 guarantee. [imsg PR #101](https://github.com/openclaw/imsg/pull/101) · [PR #156](https://github.com/openclaw/imsg/pull/156) · [PR #194, live-injected 26.5.1 verification](https://github.com/openclaw/imsg/pull/194) · [changelog](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/CHANGELOG.md)
- **Closest version-specific evidence:** a 26.6.1 / imsg 0.14.1 user reported `v2_ready`, `advanced_features`, `typing_indicators` and `read_receipts` true with SIP disabled and `DisableLibraryValidation` **not** set. They explicitly withdrew a claim that other selectors had broken: their own broker filtered them. The report says typing/read “still work,” but supplies no second-device receipt/typing observation; 26.6.2 remains **unconfirmed**. [imsg #236, report and retraction](https://github.com/openclaw/imsg/issues/236) · [imsg #194, earlier live injected typing-flag and dispatch-timestamp observations](https://github.com/openclaw/imsg/pull/194)
- **Library validation:** imsg warns that Tahoe *may* reject a nonmatching injected dylib even when SIP is off; Apple describes library validation as allowing libraries signed by Apple or the app's Team ID unless the app allows an exception. BlueBubbles' installation guide additionally instructs disabling library validation through a system-wide plist. That is BlueBubbles guidance, **not proof it is necessary for current imsg** (the 26.6.1 report is a counterexample). No documented, universal minimal set of toggles for **26.6.2** was found. [imsg docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#why-theyre-separate) · [Apple library-validation entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation) · [BlueBubbles installation](https://docs.bluebubbles.app/private-api/installation) · [imsg #236](https://github.com/openclaw/imsg/issues/236)
- **AMFI boot-args:** `imsg`'s source labels **direct-IMCore fallback** as requiring “AMFI disabled + XPC plist”; it does **not** prescribe this for its preferred injected helper. A BlueBubbles user tried AMFI-related boot arguments without success; another got a helper connected after changing *several* variables and explicitly could not tell which were necessary. Therefore AMFI boot-args are **not an established requirement or safe remedy** for imsg on 26.6.2. Apple's Apple-silicon LocalPolicy documentation describes an additional boot-arguments allow-list security control; do not equate a suggested boot-arg with a verified fix. [imsg source](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/TypingIndicator.swift#L43-L60) · [BlueBubbles #776 comments](https://github.com/BlueBubblesApp/bluebubbles-server/issues/776) · [Apple LocalPolicy, `sip3`](https://support.apple.com/guide/security/contents-a-localpolicy-file-mac-apple-silicon-secc745a0845/web)
- BlueBubbles' helper also offers sending/receiving typing indicators and marking chats read, but its own README only claims testing through macOS 13. Tahoe field reports show both failure to inject with SIP off and a 26.5 Messages dylib load failure diagnosed as helper linkage rather than an OS-wide injection ban; a separate user had a connected helper yet a threaded send stalled. This corroborates version-/build-specific fragility, **not** a requirement to disable every macOS guard. [BlueBubbles helper README](https://github.com/BlueBubblesApp/bluebubbles-helper/blob/1ee57f3fde63f8cc5769d60cfabfe9a06fcc1069/README.md#features) · [BlueBubbles #776](https://github.com/BlueBubblesApp/bluebubbles-server/issues/776) · [#814](https://github.com/BlueBubblesApp/bluebubbles-server/issues/814)

## Leaving SIP on: UI options and limits

- **Typing:** imsg's own proposal says Messages' AppleScript dictionary exposes no typing-indicator command and suggests (but does not implement or receiver-test) focusing the composer, inserting and deleting a character. It calls out frontmost-window, existing-draft/caret, user interference and Accessibility-permission risks. Apple requires explicit approval for a third-party app to control the desktop with Accessibility. Whether programmatically inserting a character (versus a physical keystroke), deleting it, or holding a draft actually triggers a **receiver-visible** indicator on 26.6.2 is **unconfirmed**. [imsg #22](https://github.com/openclaw/imsg/issues/22) · [Apple Accessibility permissions](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac/26)
- **Read:** Apple's macOS 26 guide says enabling Send Read Receipts makes a User see “Read” when their message has been seen by the Service handle; it is iMessage-only, and a previously disabled individual override must be turned back on individually. Messages has a native **Conversation > Mark as Read** menu action; imsg's injected command instead marks all messages in the specified chat as read. Does **merely opening/selecting** the Conversation immediately mark it read and transmit a receipt on this build, or does invoking Mark as Read always transmit one? **Unconfirmed**; do not assume UI navigation preserves the Persona's intended unread delay or that subsequently marking unread retracts a sent receipt. [Apple receipts](https://support.apple.com/guide/messages/turn-read-receipts-on-or-off-ichtee6857f6/14.0/mac/26) · [Apple read/unread menu](https://support.apple.com/guide/messages/mark-a-conversation-as-unread-ichtf9781355/14.0/mac/26) · [imsg read handler](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgHelper/ReadStatusHandlers.inc#L109-L165)
- **Concurrency/session state:** UI scripting operates on the active composer/selected Conversation, so one desktop focus cannot simultaneously address several different Conversations; serializing focus, preserving drafts and avoiding accidental read state are design implications, not a tested scheduling policy. The imsg proposal explicitly flags loss of frontmost focus/user interference. On a **locked screen**, with the **display off while the Mac remains awake**, and when the **Mac itself sleeps**, reliable UI typing/read and remote visibility are each **unconfirmed**; no primary-source 26.6.2 receiver test was found. Treat locked/sleeping operation as a probe, never a promised background feature. [imsg #22](https://github.com/openclaw/imsg/issues/22) · [Apple Accessibility permission boundary](https://support.apple.com/guide/mac-help/allow-accessibility-apps-to-access-your-mac-mh43185/mac/26) · [Apple's separate sleep/display settings](https://support.apple.com/guide/mac-help/set-sleep-and-wake-settings-mchle41a6ccd/mac/26)

## Security, updates, and reversibility

- SIP limits even root's modification of protected system paths and Apple-installed apps. On Apple silicon it is separate from kernel integrity protection; disabling it increases the consequences of compromise of this internet-facing service/Mac but is **not** equivalent to switching off every Mac protection. Separately disabling library validation or loosening code-signing/boot-arg controls further expands exposure. [Apple SIP overview](https://support.apple.com/en-us/102149) · [Apple Platform Security SIP](https://support.apple.com/guide/security/system-integrity-protection-secb7ea06b49/web) · [Apple LocalPolicy controls](https://support.apple.com/guide/security/contents-a-localpolicy-file-mac-apple-silicon-secc745a0845/web) · [Apple library validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)
- Disabling SIP is **not evidence that macOS updates stop**: Apple documents signed software update delivery and LocalPolicy measurements changing during updates. Conversely, neither Apple nor imsg promises that a pre-update helper will keep loading or that every custom security setting persists unchanged; the imsg history shows macOS 26 helper ABI/selector repairs. Recheck SIP, helper version, bridge readiness and **receiver-visible behavior after each update**. [Apple secure software updates](https://support.apple.com/guide/security/secure-software-updates-secf683e0b36/web) · [Apple LocalPolicy `nsih`/`spih` update behavior](https://support.apple.com/guide/security/contents-a-localpolicy-file-mac-apple-silicon-secc745a0845/web) · [imsg changelog](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/CHANGELOG.md)
- To restore SIP, boot the Apple-silicon Mac into Recovery, run `csrutil enable` in Recovery's Terminal, reboot and check `csrutil status`; imsg documents the same rollback. If other protections were independently changed (e.g. a library-validation plist or boot-args), reversing SIP **alone** is not proof they were restored; inventory/reverse each separately under human control. This research changed none of them. [Apple Recovery startup](https://support.apple.com/en-us/102518) · [Apple SIP configuration and reboot](https://developer.apple.com/library/archive/documentation/Security/Conceptual/System_Integrity_Protection_Guide/ConfiguringSystemIntegrityProtection/ConfiguringSystemIntegrityProtection.html) · [imsg rollback](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/advanced-imcore.md#building-and-launching) · [BlueBubbles' separate library-validation step](https://docs.bluebubbles.app/private-api/installation)
