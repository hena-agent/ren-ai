# imsg watch, message identity, and crash recovery

## Answer

At pinned `openclaw/imsg` main commit [`1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c`](https://github.com/openclaw/imsg/commit/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c) (latest published release [`v0.15.9`](https://github.com/openclaw/imsg/releases/tag/v0.15.9)), SIP-on `watch` plus `messages.after` can catch up on new message and tapback rows within one database instance, but cannot by themselves guarantee every real-world inbound event, changes to previously emitted messages, or exactly-once outbound sends after an uncertain AppleScript result. Outgoing read receipts are available by querying `message.send_status` with a *known* GUID, not in watch/history's outgoing message payload. [Watch and cursor limits](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/watch.md#L25-L44), [send uncertainty and bridge-only tracked sends](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L545-L571), [read-state payload](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/json.md#L58-L67).

## 1. Watching

- `watch` monitors `chat.db`, `chat.db-wal`, `chat.db-shm`, and their directory using macOS filesystem events; a default 5-second fallback poll refreshes watches and catches missed events. Both paths query message rows, rather than receiving Messages.app event callbacks. [Watcher configuration](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageWatcher.swift#L7-L30), [filesystem sources/polling](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageWatcher.swift#L142-L154), [file event handlers](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageWatcher.swift#L167-L265).
- A **positive** `--since-rowid N` / RPC `since_rowid: N` replays rows with `ROWID > N` on startup, then keeps following them. Omitted/`0` starts at the then-current maximum (no backlog); RPC `-1` starts from the beginning. Watch scans and drains bounded pages in increasing ROWID order. [CLI cursor docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/watch.md#L25-L43), [RPC cursor docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L363-L375), [scan query](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore+Queries.swift#L86-L103).
- Message JSON uses `id` (message ROWID), `guid` (message GUID), `chat_id`, `chat_identifier`, `chat_guid`, `chat_name`, `participants`, `is_group`, `sender` (raw handle; may be empty for self-sent), `sender_name` (optional), `is_from_me`, `text`, `created_at`, `attachments` (array), and optional `reply_to_guid`, `thread_originator_guid`, `thread_originator_part`, `reply_to_text`, `reply_to_sender`, `destination_caller_id`, `balloon_bundle_id`, `url_preview`, `poll`, and `reactions`. Attachment entries expose filenames, UTI/MIME, size and disk paths; RPC watch needs `attachments: true` to populate them (CLI watch has its historical JSON behavior). [Message schema](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/json.md#L37-L65), [additional encoded fields](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/OutputModels.swift#L113-L147), [attachment schema](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/json.md#L177-L192).
- With `--reactions` / `include_reactions: true`, a tapback has its own message `id` and the optional extension `is_reaction`, `reaction_type`, `reaction_emoji` (custom emoji), `is_reaction_add`, `reacted_to_guid` (target GUID); these fields are omitted for ordinary messages. There is **no documented edit/unsend marker** in this output schema. [Reaction schema](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/json.md#L123-L140), [payload encoding](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/OutputModels.swift#L177-L231).

## 2. Which events appear

- Watch explicitly includes inbound and outbound rows, regardless of whether the outbound was produced by `imsg send` or a human using Messages, **provided Messages writes a new row to the watched database**; filter on `is_from_me`. Debouncing allows short follow-up writes, including `is_from_me` corrections, to settle *before* initial emission. [Watch docs](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/watch.md#L6-L15), [debounce](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/watch.md#L86-L100).
- Both event-triggered and fallback reads use `WHERE m.ROWID > ?`; therefore subsequent edits to a previously scanned row, unsends that change/delete it, and delivery/read-status changes to an outgoing row are **not emitted as updates to that row**. Apple confirms Messages can show edits and unsends; whether a particular operation on macOS 26.6.2 also creates a *different* new row visible to this scanner is **unconfirmed**. [Row query](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore+Queries.swift#L86-L103), [Apple edits/unsends](https://support.apple.com/guide/messages/unsend-or-edit-messages-ichtd68328c6/mac).
- Tapback additions and removals *are* separate `message` rows with association type/GUID pointing back to the reacted-to message, emitted only when reactions are enabled; `history` hides the standalone rows but can show current reaction snapshots on target messages. [Reaction row query](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore+ReactionEvents.swift#L53-L89), [history behavior](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/history.md#L64-L68).
- All-chat watch chooses the lowest linked chat ID if a physical row is linked to multiple chats; an explicitly filtered chat retains that chat context. A not-yet-linked row is retried briefly, **then skipped** rather than exposed as `chat_id=0`: a hard edge for the requirement to ingest *every* inbound event. Bounded queues can overflow; RPC supplies a conservative resume cursor and may replay an already accepted row. [Chat choice](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/watch.md#L10-L15), [unresolved-chat skip](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageWatcher.swift#L335-L352), [overflow](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L408-L438).

## 3. Message identity and cursors

- `guid` is the message's stable cross-machine identifier; `id` is a local, database-instance-scoped ROWID, useful for ordered scans, **not** a portable durable identity. `messages.after` explicitly says to discard cursors after replacement/restoration/recreation of `chat.db` and not transfer them between machines/accounts. [Identity](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/json.md#L42-L52), [cursor scope](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L330-L345).
- The scanner assumes future rows have greater ROWIDs and does not rescan old IDs. A general guarantee that Apple never reuses/decreases ROWIDs on deletion, reimport, migration or iCloud sync is **unconfirmed**: imsg's source reads Apple's schema but does not establish its allocation policy. Apple does document that Messages in iCloud syncs sends, receives and deletions across devices; this does not establish local ROWID ordering. [Scanner SQL](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore+Queries.swift#L86-L103), [Apple iCloud Messages](https://support.apple.com/guide/icloud/keep-your-messages-up-to-date-mma17ed475f7/icloud).

## 4. Confirming a send after a crash

- CLI `imsg send --json` returns `{"status":"sent","id":ROWID,"guid":GUID,"message_id":GUID}` **when verification resolves the row**; text mode just prints `sent`. RPC `send` returns `{"ok":true,"id":ROWID,"guid":GUID}` when observed, but IDs can be absent in uncertain cases. [CLI output code](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/Commands/SendCommand.swift#L172-L200), [RPC send result](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L545-L551).
- After a lost response, inspect `messages.after` from a previously stored cursor (or time-filtered `history`) for the candidate outgoing chat/text/time; if a GUID was saved, use RPC `message.send_status(guid)` to inspect its row/delivery state. Without a known GUID, matching text/time is **not proof** that a particular attempt sent; a missing row is likewise not proof of no send, so an uncertain attempt is not safely retryable. [History date filters](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/history.md#L17-L36), [cursor pagination](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L304-L345), [missing-status behavior](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/RPCServer+MessageStatusHandlers.swift#L15-L36), [send uncertainty](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/send.md#L79-L87).
- Ordinary SIP-on AppleScript `send` has **no caller-owned idempotency key**; RPC rejects `attempt_id` for ordinary `send`. `send.tracked` supports a caller-owned GUID and subsequent status lookup, but requires an already-running injected IMCore bridge and is thus out of scope with SIP on. [Send handler](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/RPCServer+SendHandlers.swift#L27-L54), [tracked requirements](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L553-L571).

## 5. History

- CLI `history --chat-id ... --start ISO8601 --end ISO8601 --json` (or RPC `messages.history`) includes outgoing messages and the shared message schema, newest first by date then ROWID; there is **no** `since-rowid` parameter on history. RPC `messages.after` is the exclusive-ROWID, oldest-first, bounded-page catch-up method (optional `chat_id`, `attachments`, `include_reactions`): persist **`next_rowid`**, not the final returned message's `id`, and continue while `has_more`. [History](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/history.md#L6-L35), [RPC history](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L264-L281), [RPC catch-up](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L304-L339).
- Standalone reactions are excluded from `history` even when the targeted message carries a `reactions` snapshot; request `include_reactions: true` in `messages.after` for the reaction-event stream. URL-preview rows may be coalesced/suppressed, so the authoritative physical cursor can exceed the last visible `id`. [Reaction differences](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/json.md#L110-L140), [cursor rule](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L330-L339).

## 6. RPC mode

- Start `imsg rpc` as one long-lived child. It uses JSON-RPC 2.0 **one JSON object per line over stdin/stdout**, no socket/daemon; stderr is diagnostics. The documented lifecycle supports multiple requests and simultaneous subscriptions with one child and cached database resources, avoiding per-action process startup and allowing live notifications. The claim that it is measurably faster than repeated CLI invocation is **unconfirmed** (no benchmark). [Transport/lifecycle](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L6-L20), [resource reuse](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L70-L85).
- Relevant methods: `initialize`, `status`, `chats.list`, `messages.history`, `messages.after`, `watch.subscribe`, `watch.unsubscribe`, `send`, `message.send_status`. `watch.subscribe` returns a subscription ID, then emits `message` notifications (`params.subscription`, `params.message`); `watch.overflow` terminates with a resumable cursor. Unsubscribe awaits cancellation before responding; `send.tracked` is bridge-only. [RPC history/after](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L264-L339), [subscription/overflow](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L363-L436), [unsubscribe/send/status](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L505-L614).
- On database replacement the RPC process rotates new requests to the new database, but **existing subscriptions stay bound to the old one**: recreate subscriptions and reset old-generation cursors. [RPC lifecycle](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L76-L86).

## 7. Read state of outgoing messages

- JSON `is_read`/`date_read` in watch/history/`messages.after` are **inbound-only**; the output encoder explicitly sets both to absent on `is_from_me` messages, and a later change to an emitted row generates no new watch message. `message.send_status` instead directly reads outgoing row `date_read` (and delivery columns) by GUID; **poll it** if the recipient shares read receipts. [Message encoder](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/OutputModels.swift#L175-L186), [status SQL](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore+Messages.swift#L325-L355), [status response](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/RPCServer+MessageStatusHandlers.swift#L44-L56), [Apple read-receipt requirement](https://support.apple.com/guide/messages/turn-read-receipts-on-or-off-ichtee6857f6/mac).
- `message.send_status` reports `pending` with null fields when a GUID is not found; a null `date_read` on a found message does **not** prove the recipient has not read it (they may disable receipts). No SIP-on watch notification for delivery/read-status changes was found. [Missing status](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L582-L614), [watch query](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/IMsgCore/MessageStore+Queries.swift#L86-L103), [Apple receipts](https://support.apple.com/guide/messages/turn-read-receipts-on-or-off-ichtee6857f6/mac).

## 8. Conversation identity

- A direct chat has a handle shaped `SERVICE;-;TARGET` (e.g. `iMessage;-;+15551234567`), while `;+;` denotes a group. `chat.chat_identifier` and `chat.guid` are separate exposed fields; `chat_id` is the local chat ROWID. `chats`/`group --chat-id` expose chat ID, identifier, GUID, service, participants, and account routing hints. [Direct/group form](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/groups.md#L6-L22), [chat fields](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/chats.md#L27-L57).
- Send to a direct `--to` phone/email handle or explicitly to `--chat-id`, `--chat-identifier`, or `--chat-guid` (RPC `to` versus exactly one chat selector). A direct handle send can reuse a compatible existing chat; explicit `--service imessage` does not reuse an SMS chat. A person can have separate phone- and email-addressed conversations, and imsg tries distinct `iMessage;-;`, `SMS;-;`, and sometimes `any;-;` candidates; do not merge these solely on contact name. [Send routing](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/send.md#L8-L37), [RPC target rules](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/rpc.md#L519-L539), [candidate logic](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/Sources/imsg/ChatTargetResolver.swift#L74-L122), [Apple on phone vs email conversations](https://support.apple.com/en-us/101744).
- The local Apple identity is implicit in chat participants, while `destination_caller_id` is an outgoing routing hint. `account_id` and `account_login` are diagnostics: AppleScript send cannot force the outbound number on a multi-number Apple ID, so confirm `hi@hena.dev` routing in a live probe. [Chat identity/routing](https://github.com/openclaw/imsg/blob/1aca78d212c888ef8b09d2abc2f3ca0b6d1f776c/docs/chats.md#L69-L78).
