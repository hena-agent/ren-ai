# ren-ai: Agent 역할 분리와 중단·복귀 스펙 (초안)

## 문제와 목표

유저는 iMessage에서 한 Persona와 지속적인 관계를 맺는다. Persona가 대화하지 않는 동안에도 일상은 흐르고, 관계가 달라질 계기가 생기며, 유저는 필요할 때 대화에 관한 조언을 받을 수 있어야 한다. 그러나 일상을 만들어 낸 이유나 관계를 진전시키려는 기획 의도가 Persona의 Context에 들어가면, Persona가 자기 삶을 사는 인물보다 각본을 수행하는 인물처럼 행동할 수 있다.

또한 어느 Agent도 상시 실행된다고 가정할 수 없다. 유저 메시지가 쌓이는 동안 Persona가 내려가 있을 수 있고, Life·Kizuna·Advisor도 각자 중단되거나 실패할 수 있다. 복귀 후 입력을 잃거나, 같은 사건을 다시 겪거나, 이미 보낸 메시지를 또 보내면 관계의 일관성이 깨진다.

**목표:** 역할별 Context와 결정권을 분리하고, Agent의 실행 여부와 무관하게 확정된 사실·상태·미처리 입력을 보존한다. Agent가 복귀하면 현재까지의 사실을 바탕으로 자연스럽게 이어간다. 여기서 Persona는 인물이고, Persona Agent는 그 인물을 구현하는 실행 역할이다.

이 문서는 [컴패니언 MVP](companion-mvp.md)와 [Persona Engine](persona-engine.md)의 제품 방향을 전제로 한다. **설계 초안이지 현재 구현이나 ADR을 대체하는 결정문은 아니다.**

## 유저가 경험하는 동작

1. 유저는 Persona가 실행 중이지 않을 때도 메시지를 보낼 수 있다. 복귀한 Persona는 쌓인 메시지를 순서대로 알고, 지금도 유효한 이야기에 반응한다.
2. Persona는 유저와의 대화 밖에서도 일상을 겪고, 그 경험을 자기 관점에서 해석한다. 먼저 연락할지, 기다릴지도 스스로 결정한다.
3. 유저와 Persona는 같은 사건을 다르게 받아들일 수 있다. 이벤트가 곧바로 호감이나 연애를 확정하지 않는다.
4. Advisor에게 물어보면 유저는 대화를 이해하는 데 도움이 되는 조언을 받는다. Advisor가 유저 대신 대화하거나 Persona의 감정을 바꾸지는 않는다.
5. 장애와 재시작으로 메시지가 사라지거나 답장이 중복되지 않는다. 시스템이 연락을 처리하지 못한 시간을 유저나 Persona의 의도적인 무응답으로 해석하지 않는다.

## 네 역할과 결정권

| 역할              | 담당하는 질문                                   | 결정·출력                                                       | 넘지 않는 경계                                           |
| ----------------- | ----------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| **Persona Agent** | 나는 무엇을 겪었고, 어떻게 느끼고 행동할까?     | 주관적 해석, 개인 상태와 관계 판단, 기억, 대화·선제 연락·기다림 | 다른 Agent의 기획 이유나 아직 모르는 사실을 알지 않는다. |
| **Life Agent**    | 일상과 주변 세계에서 실제로 무슨 일이 일어났나? | 일정의 경과, 주변 인물의 행동, 외부 사건과 선택의 결과          | Persona의 감정·호감·답장 내용을 지정하지 않는다.         |
| **Kizuna Agent**  | 관계가 변화할 계기가 필요한가?                  | 계기 제안, 적절한 시점의 판단, 개입하지 않기                    | 사랑·고백·관계 상승을 결과로 강제하지 않는다.            |
| **Advisor Agent** | 유저는 이 대화를 어떻게 읽을 수 있나?           | 유저를 위한 해석과 조언                                         | Persona를 대신해 답장하거나 관계 상태를 바꾸지 않는다.   |

Life가 일상의 사건을 확정해 Persona에 전달하면, Persona가 그 사실을 경험하고 해석한다. Persona가 친구와 약속을 잡거나 취소하는 등 외부에 영향을 주는 선택을 하면 Life가 그에 따른 결과를 진행한다. Persona는 사건의 수동적 수신자가 아니다.

Kizuna가 관계에 도움이 될 사건을 제안할 수 있지만, Life는 이미 확정된 일정·사실과 양립하는지 검토한 뒤에만 일상 사건으로 확정한다. Kizuna가 아무것도 제안하지 않는 것도 정상적인 판단이다. Advisor의 조언은 유저에게만 전달된다.

예를 들어 Life가 “발표 후 팀장이 다음에는 근거 자료를 더 준비해 달라고 말했다”를 확정할 수 있다. “창피하니까 유저에게 위로를 청하고 호감이 오른다”는 Persona가 직접 해석·선택할 영역이다. Kizuna가 이 사건을 제안했다는 사정도 Persona에게 전달하지 않는다.

## Context와 기록의 경계

**기록**은 수신된 메시지, 확정된 생활 사건, 판단 결과, 상태 변화와 발신 결과처럼 재시작 뒤에도 유지해야 하는 사실이다. **Context**는 이번 실행에서 한 Agent에게 보여 주는 정보다. 기록이 보존된다는 것이 네 Agent가 동일한 대화 기록이나 프롬프트를 읽는다는 뜻은 아니다.

- **Persona:** 자신의 설정, 해당 Conversation의 대화와 기억, 개인·관계 상태, 자신이 알게 된 확정 사건, 현재와 사건의 시각을 본다. 기획 의도, 검토 중인 제안, Advisor와 유저 사이의 비공개 대화는 보지 않는다.
- **Life:** 확정된 일정·사건·주변 상황 및 Persona가 외부에 실행한 선택을 본다. 일상에 필요한 사실만 전달받으며 유저와의 대화 전체를 기본 입력으로 삼지 않는다.
- **Kizuna:** 계기를 판단하는 데 필요한 관계 상태와 주요 사건을 본다. Persona의 전체 세션을 공유하지 않는다.
- **Advisor:** 유저가 도움을 요청한 대화와 유저가 제공한 정보를 본다. 내부 상태의 비공개 정보에 접근할지는 미결정이다.

확정된 외부 사건과 Persona의 주관적 해석을 구분해 보존한다. 한 유저와 한 Persona의 Conversation에 속한 관계·유저 기억이 다른 Conversation에 섞여서는 안 된다. 기존 [도메인 용어](../../CONTEXT.md)의 **Memory**는 한 Conversation의 최근 메시지와 오래된 메시지 요약을 뜻한다. 생활 사건의 기록 및 복구용 상태를 모두 Memory라는 이름으로 묶지는 않는다.

## 공통 실행·복구 계약

### 입력과 실행

메시지 수신, 확정 사건, 예약된 시각, 재시도 등이 Agent 실행의 계기가 된다. 입력은 수신한 Agent가 실행 중인지와 무관하게 먼저 보존한다. 깨우는 신호가 유실되어도 복귀 시 미처리 입력을 다시 찾을 수 있어야 한다. 별도 메시지 브로커나 상시 실행 프로세스는 이 요구사항 자체에 포함되지 않는다.

1. 외부 입력 또는 Agent 간 전달 내용을 안정적인 식별자·발생 시각·대상과 함께 기록한다.
2. 해당 Agent가 자신의 미처리 입력과 현재 확인 가능한 사실을 읽는다.
3. 판단 결과, 상태 변화, 후속 전달·발신 의도, 처리 위치를 일관된 단위로 확정한다.
4. 필요한 외부 발신을 실행하고 결과를 확인한다.

발생 시각, 시스템 수신 시각, Agent 처리 시각을 구분한다. 늦게 처리한 사건을 방금 발생한 일로 전달하지 않는다. 실행 중 새 입력이 들어왔다면 오래된 판단이 그대로 발신되지 않도록 발신 전에 유효성을 재확인한다. 동시에 돌아가는 실행이 같은 상태를 덮어쓰지 않도록 Conversation 또는 대상 상태 단위로 순서·버전을 관리한다.

### 중복·실패

- 같은 입력이 재수신되거나 실행이 재시도되어도 사건·감정 변화·관계 변화·후속 작업은 중복 적용되지 않는다.
- 판단 결과가 확정된 뒤 중단되면 복귀 시 결과를 다시 생성하지 않고 이미 확정된 결과에서 이어간다.
- 발신 결과를 알 수 없으면 무작정 재전송하지 않는다. iMessage 기록과 대조해 확인할 때까지 해당 Conversation의 다음 발신을 보류한다.
- 장애로 실행되지 못한 시간은 관계상의 의도적 무응답으로 계산하지 않는다. 재검토 주기가 여러 번 지났다고 같은 감정 변화를 주기 횟수만큼 적용하지 않는다.
- 서비스가 수신을 확인한 입력의 보존을 보장한다. 수신 서비스 자체가 내려간 동안의 iMessage 입력은 채널 기록에서 누락분을 찾아 복구해야 한다.

### Agent별 복귀

**Persona:** 미처리 유저 메시지를 원문과 시각·순서대로 확인하되, 현재 유효한 전체 맥락을 놓고 반응한다. 예를 들어 유저가 `오늘 저녁에 시간 있어?` → `7시쯤 어때?` → `오늘은 취소해야겠다. 내일은?`를 남겼다면, 첫 제안을 따로 수락하는 답장을 보내지 않는다. 복귀가 메시지마다 한 통씩 답장을 밀어내는 원인이 되어서는 안 된다. 읽고 기다리기로 결정한 경우에도 같은 입력으로 상태 변화를 반복하지 않는다.

**Life:** 마지막으로 진행한 시점부터 현재까지 확정된 일정과 결과를 따라잡는다. 긴 공백의 평범한 일상은 요약할 수 있다. 이미 일어난 대화와 모순되는 과거를 뒤늦게 만들거나, 보내지 않은 연락을 보냈던 일로 기록하지 않는다.

**Kizuna:** 과거의 제안을 일괄 실행하지 않는다. 최신 상태에서 유효한지 재검토하고, 때를 놓친 제안은 폐기하거나 새로 판단한다. 이미 확정된 사건을 다시 만들지 않는다.

**Advisor:** 요청 이후 대화가 진행됐다면 현재 유효한 조언인지 확인한다. 이미 해결된 상황에 대한 오래된 조언을 자동으로 보내지 않는다.

한 Agent의 중단이 무관한 역할까지 멈추게 하지 않는다. Life나 Kizuna가 내려가 있어도 Persona는 확정된 사실로 대화할 수 있고, Persona가 내려가 있어도 유저 메시지와 확정 사건은 보존된다.

## 보존 대상

| 범주      | 복구에 필요한 정보                                                                |
| --------- | --------------------------------------------------------------------------------- |
| 입력      | 식별자, 출처·대상, 원문/사건, 발생·수신 시각, 처리 위치                           |
| Persona   | 인물 설정, 해당 Conversation의 기억·개인·관계 상태, 주관적 해석, 약속·미완료 행동 |
| Life      | 확정된 사건, 일정과 주변 상황, 마지막 진행 시점                                   |
| Kizuna    | 제안, 근거로 삼은 상태와 시점, 유효 기간, 채택·폐기 여부                          |
| Advisor   | 유저의 요청, 조언의 근거가 된 대화 범위, 전달 결과                                |
| 실행·발신 | 확정된 판단과 후속 작업, 재시도 상태, 다음 실행 시각, 발신 의도·결과              |

## 검증 시나리오

구현할 때는 모델의 문구를 고정해 비교하기보다 **입력 기록 → 실행 → 중단 → 복귀 → 관찰 가능한 상태·발신 확인**이라는 경계에서 검증한다. 현재 Persona Lab의 메시지 보존·저장 기록 복원 테스트를 출발점으로 삼는다.

1. Persona 중단 중 메시지가 여러 개 쌓이고 제안이 취소·수정되어도, 복귀 후 오래된 제안을 수락하지 않는다.
2. 동일 입력 수신이나 판단 재시도 후에도 상태 변화, 사건 및 발신이 한 번만 확정된다.
3. 판단 도중, 결과 확정 직후, 발신 직후 각각 중단되어도 입력과 결과가 일치하며 불명확한 발신은 확인 없이 반복하지 않는다.
4. Life가 오래 중단됐다 돌아와도 기존 대화·확정 사건과 모순되는 과거를 만들지 않는다.
5. 오래된 Kizuna 제안과 Advisor 응답을 최신 맥락에서 재검토한다.
6. Kizuna의 기획 이유와 Advisor의 비공개 대화가 Persona Context에 나타나지 않는다.
7. 한 역할이 중단되어도 다른 역할은 확정된 사실을 바탕으로 계속 동작한다.
8. 서비스 장애 시간에 유저나 Persona가 의도적으로 상대를 무시한 것처럼 관계가 변하지 않는다.

## 기존 설계와의 접점 및 열린 결정

다음은 구현 전에 맞춰야 할 지점이며, 이 초안만으로 기존 결정을 변경하지 않는다.

1. **누적 메시지의 전달 방식:** [ADR-0002](../adr/0002-each-conversation-has-one-lifelong-opencode-session.md)는 유저 메시지마다 GUID에서 파생한 프롬프트 하나를 Persona의 평생 세션에 전달한다. [ADR-0003](../adr/0003-the-persona-reads-a-tagged-transcript.md)은 그 형식과 캐싱을 정한다. 이 문서의 요구는 *누적 메시지를 읽고 현재 맥락에 맞춰 행동한다*는 제품 동작이다. 기존 메시지별 프롬프트를 유지하며 답장을 늦춰 함께 판단할지, 입력을 묶어 전달할지는 별도 검증·결정이 필요하다.
2. **기록의 범위:** ADR-0002에서는 iMessage가 Conversation의 기록이며 세션을 재구축할 수 있다. 이번 스펙의 생활 사건·주관적 상태와 Agent 간 제안은 iMessage 대화 자체가 아니다. 기존 Conversation 기록의 권위를 유지하면서 이 정보들을 어디에 확정·복원할지 정해야 한다. 서버 자체 상태와 OpenCode 저장소의 분리는 [ADR-0006](../adr/0006-the-server-keeps-its-own-sqlite-file-apart-from-opencodes.md)에 따른다.
3. **Persona 내부 판단:** 현재 [Persona Engine 개발 스펙](persona-engine-development.md)과 Lab은 Jev의 상태·발송 판단, Gemini의 대사 생성을 분리한다. 여기서 말하는 Persona의 최종 결정권은 역할 전체의 책임이며 모델 하나가 모든 결정을 내려야 한다는 뜻은 아니다. 기존 상태 전이·단계 검증의 경계는 유지한다.
4. **Kizuna의 목표:** 이 초안은 사랑을 보장하기보다 사랑이 생길 수 있는 계기를 마련한다고 가정한다. 결과를 강제하는 연출자로 둘지는 아직 결정되지 않았다.
5. **Advisor의 정보 범위:** 첫 기준은 유저가 볼 수 있는 대화와 유저가 제공한 사실이다. Persona의 숨겨진 상태를 힌트로 제공할지, 제공한다면 어디까지인지는 결정되지 않았다.
6. **Agent 간 전달의 단위:** Persona의 생활 정보가 Conversation마다 독립된 인물 경험인지, 하나의 인물에게 공통인 생활인지 먼저 정해야 한다. 현재 MVP의 전속 배정 및 사용자별 기억 분리를 전제로 하되, Lab의 여러 세션은 비교 실험용으로 취급한다.

모델 공급자, 프롬프트 문구, 스케줄 간격, 저장소의 구체적 스키마, Advisor 화면과 결제 정책은 이 문서의 범위 밖이다.
