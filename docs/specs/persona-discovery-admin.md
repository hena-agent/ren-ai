# 페르소나 탐색 웹사이트와 Admin — MVP 작업 스펙

상태: 제품 흐름은 확정, 화면·저장소·배포의 세부 설계는 아래 작업 목록과 미결정 항목으로 관리한다.

현재 이미지 작성 흐름은 아래 **최신 흐름: 다각도 인물 시트에서 시작하는 이미지 제작**이다. 문서 저장은 사진 생성과 독립적이며 이름·설정 변경도 기존 사진과 함께 저장한다. 앞선 대표 사진의 정체성 참조·전체 갱신 강제·장면 갤러리·추천 단계·공유 프롬프트·병렬 기본 생성은 구현 이력이다.

## 목표와 앱 구성

사용자가 틴더처럼 페르소나를 스와이프하고 Like하면, 그중 한 명이 나중에 iMessage로 먼저 연락한다. 운영자는 Admin에서 페르소나를 저장·관리하고, 초대 링크를 발급하며, 대기자 중 연락할 N명을 선정한다.

사용자 웹사이트는 `apps/discovery`다. 즉시 대화를 시작하던 이전 테스트 사이트 `packages/discovery.hena.dev`는 삭제했다([ADR-0015](../adr/0015-discovery-is-the-only-onboarding.md)). Admin은 `apps/admin`에 둔다.

| 앱              | 경로             | 역할                                                                           |
| --------------- | ---------------- | ------------------------------------------------------------------------------ |
| 사용자 웹사이트 | `apps/discovery` | 페르소나 탐색, Like / Pass, 연락처 등록, 초대 적용, 등록 상태 확인·연락처 수정 |
| Admin           | `apps/admin`     | 페르소나 저장·관리, 초대 링크 관리, 대기자 선정, 첫 연락 상태 확인             |

공개 페르소나 목록과 운영자 편집 화면은 같은 저장된 페르소나를 참조한다. 선정·초대 사용·발송 예약의 판단은 서버에서 수행하며, 두 웹 앱이 서로 다른 규칙을 구현하지 않는다.

### 1차 구현: Admin 페르소나 편집

- `apps/admin`에서 목록 → 생성/수정 → 저장 → 공개/비공개 흐름과 저장된 카드 미리보기를 제공한다.
- 인물 모델은 **OpenCode 기준**이다. 사용자 결정에 따라 Persona Engine 대신 프롬프트·언어·시간대·첫 인사 지침·기억 지침을 관리한다.
- `packages/personas`가 OpenCode Markdown 로더, 검증, 파일 저장, 공개 프로필 조회를 공유한다. 공개 프로필도 같은 Markdown의 YAML frontmatter에 저장하며 별도 메타데이터 DB를 두지 않는다.
- Admin Catalog 공개 projection은 Admin의 `GET /api/personas`가 제공한다. 브라우저용 Discovery는 이 응답을 직접 호출하지 않고, 매 요청마다 api-app의 `GET /discovery/personas`를 호출한다. api-app은 현재 Admin 공개 Catalog를 읽어 이미지 URL을 Admin origin으로 해석해 반환한다.
- 이미지는 첫 버전에서 HTTPS URL을 입력한다. 기존 파일에 공개 프로필 필드가 없으면 ID를 이름으로 표시하고 비공개 상태로 연다.
- 기존 iMessage API도 공용 로더를 사용한다. 같은 디렉터리를 지정하면 저장한 OpenCode 설정을 읽으며, 실행 중인 API에는 **재시작 후** 반영된다. 공개/비공개는 카드 노출 상태이며 기존 Conversation을 삭제하지 않는다.
- Admin은 어두운 중립색·고밀도 편집 화면으로 구성하고 네이티브 HTML 폼으로 저장한다. 브라우저 JavaScript와 별도 프런트엔드 빌드 없이 서버에서 HTML을 렌더링한다.

초기 버전의 ID·이미지 URL·런타임 설정 입력은 아래 **3차 구현: 캐릭터 제작 흐름**으로 대체한다.

로컬 실행:

```sh
ADMIN_PASSWORD='<운영자 비밀번호>' bun run --cwd apps/admin dev
```

`http://127.0.0.1:3729`에 접속해 사용자 이름 `admin`과 설정한 비밀번호로 로그인한다. 포트는 `PORT`로 변경할 수 있다. 기본 저장 위치는 `apps/admin/data/personas`다. 실제 iMessage API와 같은 파일을 관리하려면 `PERSONA_DIRECTORY`에 API가 사용하는 절대 경로를 지정한다. 설정 예시는 `apps/admin/.env.example`에 있다.

Admin과 저장 API에는 비밀번호 인증과 동일 출처 폼 제출 검사를 적용한다. 공개 프로필 조회에는 인증이 필요하지 않다. 테스트·품질 검사는 저장소의 `.nvmrc`에 맞춰 **Node 24**에서 실행한다.

검증 결과:

- 전체 테스트와 파일별 커버리지 100%, `bun run ci:checks`, `bun run verify-gates`를 통과했다.
- 신규 Admin·공용 저장소의 변이를 모두 검출했고, 저장소 전체 변이 검사도 CI와 같은 `STRYKER_SHARD=1/4`부터 `4/4`까지 모두 100%로 통과했다. 단일 `bun run ci` 실행은 로컬 한 시간 제한에 걸려 변이 단계를 4개 shard로 나누어 완료했다.
- 실제 Bun 서버에서 인증·생성·저장 후 조회를 확인하고 Chromium으로 데스크톱·모바일 화면을 검토했다.
- Standards / Spec 코드 리뷰는 각각 지적 사항 0개였다.
- Mac의 대소문자 비구분 파일 시스템에서도 다른 대소문자의 ID로 기존 페르소나를 조회·수정하지 못하도록 실제 파일 이름과 일치하는 ID만 허용한다. 파일이 조회 도중 사라지면 기존과 동일하게 찾을 수 없음으로 처리한다.

### 2차 구현: Discovery 탐색과 실제 대기 등록

이번 단위는 사용자 결정에 따라 선택 확인을 넘어 **실제 대기 등록**까지 포함한다.

- `apps/discovery`는 공개 프로필 카드, 터치 스와이프·Like / Pass 버튼·방향키, Like 개수, 연락받기 화면을 제공한다. 공개 목록 조회와 등록은 api-app을 사용한다. 목록은 조회마다 최신 Admin 공개 Catalog에서 가져와 배포된 브라우저 번들을 다시 만들지 않아도 공개된 새 인물을 반영한다. 선택은 브라우저에 보관하고 새로고침 후 복원한다. 다시 탐색은 Pass만 되돌리고 Like를 유지한다.
- 한 명만 Like해도 연락처 입력으로 진행한다. 전화번호와 Apple ID 이메일을 정규화·검증하고 AI 안내·개인정보 disclosure·동의·Turnstile을 웹에서 처리한다. 현재는 휴대전화 번호만 받는다([Discovery 연락처](#discovery-연락처-iphone-휴대전화-번호만)).
- api-app은 `GET /discovery/personas`와 `POST /discovery/waitlist`를 제공한다. 공개 목록은 요청 시 Admin의 `GET /api/personas`를 호출하고, 브라우저에는 공개 필드만 반환하며, 제출 시 Like 후보가 현재 공개되어 있는지 다시 검증한다. Discovery에는 별도 목록 API Worker나 D1 binding을 두지 않는다.
- SQLite의 `discovery_registration`과 `discovery_like`에 정규화된 Handle, Like 목록, 언어, 동의 버전, 등록 시각을 트랜잭션으로 보관한다. 등록 시각이 동의 시각이다. Handle의 UNIQUE 제약과 `INSERT OR IGNORE`로 동시 제출을 처리하며 재제출은 기존 Like를 덮어쓰지 않는다.
- 차단·삭제 진행 중인 Handle은 거부한다. 이미 대화가 시작된 Handle은 `active`를 반환하고 새 등록을 만들지 않는다. 운영자 `remove`는 대기 등록과 Like도 삭제한다.
- 응답은 `waiting` 또는 `active`다. 새 Waitlist 등록은 Notification을 함께 저장하고 다음 백그라운드 실행에서 `noti@renai.im`으로 한 번 발송을 시도한다. Conversation은 만들지 않으며 순서·연락 시점·안내 도착을 약속하지 않는다. 중복 등록과 이미 활성화된 Handle에는 다시 보내지 않는다. [Notification 명세](notifications.md)를 따른다.
- 기존 사이트의 `/onboard`·`/waitlist` 계약은 계속 지원한다. 공유 Turnstile은 브라우저 전용 subpath로 내보내며 기존 사이트도 같은 구현을 사용한다.

로컬에서 Admin에 페르소나를 저장·공개한 다음 루트에서 실행한다:

```sh
bun dev
```

프런트엔드는 `http://127.0.0.1:3867`, api-app은 `http://127.0.0.1:4879`, DB 없는 api-msg executor는 `http://127.0.0.1:4700`이다. Discovery에는 별도 카탈로그 Worker나 4873 listener가 없다. 로컬 서비스 및 개발용 token 설정은 각 앱의 `.env.example`을 복사한 `.env` 하나를 사용한다. `TOKEN_CATALOG`는 Admin과 api-app에서, `TOKEN_MANAGEMENT`는 Admin·api-app·api-msg에서 각각 일치시킨다. api-app 예시는 `BOOTSTRAP_ONLY=true`로 시작하므로 공개 목록 조회는 가능하지만 등록 쓰기와 실행은 차단된다.

실제 iMessage API에도 같은 경로를 연결하고 기존 `server.sqlite`에 새 테이블을 추가했다. 공개 배포에서는 실제 Turnstile 키, API URL과 CORS origin을 맞춰야 한다. 기존 사이트는 이후 삭제했다(ADR-0015).

검증 결과:

- 433개 테스트와 파일별 커버리지 100%, `bun run ci:checks`와 `bun run verify-gates`를 통과했다. 두 사이트의 빌드도 포함한다.
- 실제 Chromium에서 데스크톱·모바일 카드, Like, 새로고침 후 복원, 터치 Pass, 연락처·동의와 실제 API/SQLite 대기 등록 완료를 확인했다. 브라우저 smoke에서는 Turnstile만 테스트 응답으로 대체했다.
- Standards / Spec 코드 리뷰는 각각 최종 지적 사항 0개였다. 동의 버전은 클라이언트의 동의 표현이며 서버는 누락·불일치 버전을 거부한다. 공개 후보 검증은 제출 처리 중 읽은 파일 저장소의 스냅샷 기준이다.
- Node 24에서 `bun run mutate --concurrency 8`로 저장소 전체 7,295개 변이를 검사해 생존 0·커버되지 않은 변이 0·최종 점수 100%로 통과했다. 로컬 병렬도만 높였으며 임계값·검사 범위는 그대로다.
- API 테스트의 `@ren-ai/onboarding`을 Stryker 샌드박스 안의 소스에 연결했다. Bun의 워크스페이스 symlink로 원본을 읽어 요청 스키마 제거 변이가 생존하던 문제를 고쳤고, 해당 파일과 전체 변이 검사를 다시 통과했다.

#### 디자인 개선: Ren AI

사용자가 선택한 **밝고 깔끔한 앱** 방향을 적용했다. 헤더·브라우저 제목의 브랜드명을 `Ren AI`로 맞추고, 화이트·밝은 회색·차콜을 기본색으로 사용한다. 큰 감성 문구·명조체·장식 하트·기울어진 카드 더미를 제거하고 데스크톱과 모바일 모두 프로필 카드를 중앙에 배치한다. Pass / Like는 동일한 SVG 아이콘 체계와 텍스트를 함께 사용하며, 연락처·동의·완료 화면도 같은 스타일을 적용한다.

- Chromium의 1440×900, 390×844, 375×667 화면을 확인했다. 모바일에서 주요 버튼이 화면 안에 들어오고 수평 넘침이 없음을 검사했다.
- 브랜드 표기·아이콘 파일 로딩, Like·터치 Pass·선택 복원·웹 동의·실제 대기 등록을 다시 검증했다.
- 디자인 변경 후 `bun run ci:checks`의 433개 테스트·파일별 커버리지 100%와 두 사이트 빌드를 통과했다. 변경한 세 TSX 파일의 변이 275개도 모두 검출했다.

#### 후속 디자인: 사진 중심의 스와이프 앱

- 사용자 제공 틴더 화면을 참고해 모바일은 화면 높이를 채우는 큰 사진 카드, 짧은 앱 바, 원형 Pass / Like 버튼과 하단 탐색·좋아요·연락받기 메뉴로 구성한다. 데스크톱은 왼쪽 좋아요 목록과 오른쪽 큰 카드의 2열 구성이다. 브랜드는 Ren AI이며 애니메·실사 선택은 상단의 작은 스위치로 유지한다.
- 카드에는 이름·정체성의 생년월일에서 계산한 숫자 나이·공개 소개 요약을 표시한다. 상세 모달도 같은 이름·나이 정보를 사용한다. AI 페르소나 배지는 카드와 상세에서 제거한다. AI 사용 고지는 동의 화면에 계속 둔다. 카드 탭과 정보 버튼은 공개 소개 전체를 읽는 모달을 열고 Like로 처리하지 않는다. 모바일 좋아요 메뉴는 좋아요한 페르소나의 썸네일 목록을 열며, 같은 목록이 데스크톱 사이드바에 보인다.
- 드래그 위치에 따라 카드가 이동·회전하고 LIKE / PASS 표시가 나타난다. 기준을 넘으면 카드가 퇴장한 뒤 선택을 한 번 확정하고 다음 카드를 표시한다. 짧은 이동·수직 이동·취소·다른 포인터는 선택으로 처리하지 않는다. 버튼과 방향키도 같은 퇴장 흐름을 사용한다. 모션 감소 설정에서는 즉시 확정한다.
- 퇴장 중과 등록 요청 중에는 화면 이동을 잠시 막는다. 이미지 스타일을 전환해도 진행 중 선택·Like / Pass·입력한 연락처가 유지된다. 상세 모달은 Tab·Escape를 지원하고 닫으면 열기 전 포커스를 스크롤 이동 없이 복원한다.
- 실제 Chromium에서 데스크톱 1440×900, 모바일 390×844·375×667, 태블릿 768×1024를 확인했다. 공개된 실제 페르소나로 사이드바·하단 메뉴·사진 높이·넘침·모달·터치 Pass·모션 감소·방향키·스타일 동시 전환·연락처 입력·새로고침 복원을 검증했다.
- 변경한 탐색·카드·화면 틀·상세보기·등록 폼의 480개 변이를 모두 검출했고, `bun run ci:checks`의 전체 511개 테스트·파일별 커버리지 100%·정적 검사·두 사이트 빌드와 `bun run verify-gates`를 통과했다.

### 3차 구현: Admin 캐릭터 제작

#### 확정한 입력과 생성 흐름

운영자가 직접 작성하는 원본은 **이름과 긴 캐릭터 설명**이다. 긴 설명은 외모·배경·성격·말투·취향·관계관·대사 예시를 담는 내부 자료다. 사용자에게는 AI가 만든 공개 소개와 프로필 이미지가 보인다.

- ID는 서버가 자동 발급하고 이후 유지한다. 화면에는 ID·이미지 URL·첫 인사 지침·기억 지침·페르소나 프롬프트 입력칸을 두지 않는다.
- 공개 소개와 이미지를 설명에서 생성한다. 버튼은 하나이며 결과가 없으면 **프로필 생성**, 결과가 있으면 **프로필 다시 생성**으로 표시한다. 이름·설명이 같으면 소개를 유지하면서 이미지 후보만 교체하고, 이름·설명이 바뀌었거나 소개·이미지가 없으면 소개와 이미지를 함께 생성한다. 생성 실패 시 입력과 기존 결과를 유지한다.
- 첫 생성과 이미지 재생성 버튼을 누르면 모달에서 선택적으로 이미지 추가 프롬프트를 입력한다. 페이지 본문에는 추가 입력란을 두지 않는다. 비워 두고 생성하거나 취소할 수 있다. 추가 프롬프트는 캐릭터 설명과 각 스타일의 작화 지시에 덧붙여 애니메·실사 두 이미지에 함께 적용한다. 공개 소개는 캐릭터 설명에서 생성하며, 이미지 재생성 때는 기존 소개를 유지한다. 추가 프롬프트는 실패·재시도 동안 미리보기 상태에 유지하고, 페르소나 파일·공개 API·로그에는 남기지 않는다.
- 생성 결과는 저장 전 미리보기다. **저장하기**가 캐릭터 파일을 갱신하고, 공개 설정을 켜서 저장해야 탐색 목록과 공개 이미지 경로에 나타난다.
- 간단한 설명만으로 AI가 이름과 긴 캐릭터 설명의 초안을 만든다. 초안은 편집 가능한 내부 원본이며 자동 저장·공개하지 않는다. 생성 실패 시 간단한 설명과 기존 캐릭터를 유지한다.
- 이미지 생성은 같은 캐릭터를 **러브플러스풍 애니메**와 **실사에 가까운 스타일**로 각각 만든다. 구도·표정·광원·배경·색감을 스타일별 프롬프트로 조합한다. Admin은 두 이미지를 함께 저장·공개하며 스타일을 하나로 확정하지 않는다.
- 스타일 선택은 **Discovery 사용자**가 한다. 첫 탐색에서 애니메·실사를 선택하고 탐색 전체에 적용한다. 탐색·연락처 화면에서도 전환할 수 있고 새로고침 후 선택을 복원한다. 스타일을 바꿔도 페르소나 ID, Like·Pass와 입력 중인 연락처를 유지한다.
- 이름이나 설명을 바꾸면 기존 공개 소개·이미지를 그대로 확정하지 않고 전체 프로필을 다시 생성한다. 프로필이 없는 캐릭터는 설명만 비공개 초안으로 저장할 수 있다.
- 새 런타임 설정은 설명과 공통 대화·인사·기억 규칙에서 구성한다. 기존 캐릭터는 ID를 유지하고, 설명을 변경하지 않으면 기존 런타임 지침도 유지한다.

#### 저장·생성·호환

- `description`을 OpenCode 파일의 선택적 frontmatter 필드로 추가했다. 기존 파일은 그대로 읽고, 편집 화면에서는 기존 프롬프트를 설명의 초기값으로 사용한다. 원본 설명과 런타임 설정은 공개 API에 포함되지 않는다.
- Admin은 서명된 미리보기 상태를 폼에 보관한다. 생성 결과를 저장하기 전 기존 파일을 변경하지 않으며, 같은 캐릭터의 동시 작업과 오래된 편집 화면의 덮어쓰기를 거부한다.
- 생성 이미지는 같은 페르소나 디렉터리의 `images/`에 고유 파일명으로 보관한다. PNG·JPEG·WebP 형식과 20MB 한도를 검사하며, 기존 파일을 덮어쓰지 않는다. 이전 후보는 재시도 실패 시에도 유지된다.
- 운영 이미지는 `https://persona-images.renai.im/<objectKey>`에서 직접 제공한다. 공개 여부는 프로필 목록만 제어하며 사진 URL 접근을 회수하지 않는다. Admin의 `/images/`는 로컬 개발에서만 같은 공개 이미지 동작을 로컬 R2로 제공한다.
- 캐릭터 파일과 공개 프로필의 선택적 `portraits`에는 `anime`·`photo` 두 URL을 모두 보관한다. 공개 이미지 경로는 공개 캐릭터가 참조하는 두 이미지 모두 제공한다. 기존 `imageUrl`은 구 클라이언트 호환용으로 유지하며 서비스의 기본 스타일을 뜻하지 않는다. 새 Discovery는 사용자 스타일에 해당하는 이미지를 사용하고, 기존 단일 이미지 캐릭터는 기존 이미지로 표시한다. 별도 API 배포에서는 두 서비스 소유 경로 모두 API URL을 붙인다.
- 기본 생성 모델은 공개 소개 **Gemini 3.8 Flash**, 이미지 **Gemini 3.1 Flash Image**, 4:5·1K다. 모델과 API 주소는 환경 변수로 바꿀 수 있으며, 실제 Gemini 요청으로 소개와 JPEG 이미지 생성을 확인했다. 이미지 생성에는 현재 [이미지 생성 가이드](https://ai.google.dev/gemini-api/docs/image-generation)와 [generateContent API 계약](https://ai.google.dev/api/generate-content)을 따른다.
- 사용자 결정에 따라 Admin의 `GEMINI_API_KEY`가 없으면 `apps/persona-lab/.env`의 기존 키를 재사용한다. Admin 전용 키를 설정하면 우선하며, 키는 브라우저·페르소나 파일·로그에 포함하지 않는다.
- 캐릭터 초안은 구조화된 이름·설명 JSON을 검증해서 받는다. 이미지 쌍은 서명된 미리보기의 캐릭터 원본에 포함하고, 저장 후에도 두 URL을 유지한다. Admin의 이미지 선택 컨트롤은 제거하며, 클라이언트가 제출한 이미지 교체 값으로 저장 원본을 변경하지 않는다. 공개 API에는 이미지 쌍만 추가하고 비공개 설명·런타임 지침은 노출하지 않는다.
- 페이지는 계속 서버 렌더링한다. 진행 중 표시와 중복 제출 방지를 위한 작은 브라우저 모듈만 시작 시 Bun으로 메모리 내 번들링한다. 별도 프런트엔드 `dist/`나 라이브러리 빌드를 추가하지 않는다.

배포는 새 선택적 필드와 이미지 경로를 읽을 수 있는 API를 먼저 준비하고, 새 이미지 형식을 처리하는 Discovery를 배포한 뒤 Admin에서 새 형식을 저장하는 순서로 진행한다. 기존 대화 설정은 API 재시작 후 반영된다. 백업 시 캐릭터 Markdown과 `images/` 디렉터리를 함께 보관한다.

#### 후속 수정: 미리보기·2D 작화·개발 서버 연결

- 이미지 비교는 폼 입력 그룹이 아니라 제목이 있는 콘텐츠 영역으로 표시한다. 제목이 카드 테두리에 걸치지 않도록 내부 여백을 맞추고 두 이미지·캡션의 높이를 정렬했다. 데스크톱·태블릿·390×844·375×667의 실제 Admin 화면에서 잘림과 수평 넘침이 없음을 확인했다.
- 사용자 결정에 따라 애니메 스타일은 **러브플러스풍 일본 미연시 2D 작화**다. 큰 애니 눈, 간략한 코·입, 섬세한 선화와 셀 채색을 우선하며 실사·웹툰풍 얼굴 비율과 3D 렌더링을 배제한다. 캐릭터 설명은 외형·설정의 원본이며 렌더링 스타일보다 우선하지 않는다. 3D 모델은 추후 단계다. 실제 Gemini 요청으로 기존 캐릭터의 새 2D 샘플을 생성·확인했다. 저장된 이미지는 재생성 후 저장할 때 교체된다.
- 공개 목록이 Admin에서는 정상인데 Discovery에서 실패한 원인은 로컬 API 미실행이었다. API 패키지에 `dev`를 연결해 루트 `bun run dev`가 Discovery API도 시작하도록 했다. 실제 공개 캐릭터와 두 이미지가 Vite 프록시를 통해 조회되고 브라우저에서 스타일 전환·복원되는 것을 확인했다.
- 수정 후 `bun run ci:checks`의 469개 테스트·파일별 커버리지 100%, 정적 검사·두 사이트 빌드와 `bun run verify-gates`를 통과했다. 변경한 `page.tsx`의 48개 변이를 모두 검출했다.

#### 후속 수정: 캐릭터의 매력을 살리는 독립적인 실사 생성

- 사용자가 이미지 복사판 같은 결과를 원하지 않는다고 정정했다. 애니메를 실사 요청의 참조로 전달하던 시도는 철회하고 **같은 캐릭터 설명에서 두 스타일을 독립적으로 병렬 생성**하는 방식으로 복원했다. 이미지 참조 API 인자·전송 코드·전용 보정 프롬프트를 제거했다.
- 실사는 매력적인 로맨틱 주인공으로 의도적으로 캐스팅한 인상, 살아 있는 눈빛·표정, 캐릭터다운 헤어·메이크업·의상과 사진 연출을 강조한다. 설명은 정체성·성격·취향의 원본이며 고정된 장면이나 소품 목록으로 다루지 않는다. 취향에 맞는 새로운 순간을 선택하고, 포즈·의상·구도·장소를 독립 생성마다 바꿀 수 있도록 지시한다. 원본에 명시된 나이·성별·핵심 외형은 유지한다.
- 직업을 그대로 책상·노트북·키보드 같은 업무 장면으로 표현하거나 애니메 이미지를 실사로 복제하지 않는다. 프로필 카드에서 얼굴이 읽히도록 얼굴 중심의 상반신 구도를 사용하며, 일반 스냅사진의 무난함보다 캐릭터의 매력과 존재감을 우선한다.
- 추가 이미지 지시는 두 스타일에 함께 적용한다. 한쪽이 실패해도 이전 완성된 미리보기와 저장된 공개 프로필을 유지하며 성공한 두 결과는 저장 시 함께 확정한다. 병렬 작업 각각을 관찰해 응답 후 도착한 다른 스타일의 실패도 요청 ID와 함께 기록한다. 입력 프롬프트·키·이미지 바이트는 로그에 노출하지 않는다.
- 실제 Gemini 요청으로 한서연·강서율을 각 두 번씩 독립 생성해 장면·포즈·의상이 달라짐을 확인했다. 최종 `bun run ci:checks`의 514개 테스트·파일별 커버리지 100%·정적 검사·빌드와 `bun run verify-gates`를 통과했고, 생성 어댑터와 작업 흐름의 214개 변이를 모두 검출했다.

#### 후속 구현: 캐릭터별 가변 장면 갤러리

- 모든 캐릭터의 사진 수를 동일하게 맞추지 않는다. AI가 설명에서 성격·매력의 서로 다른 면을 읽고 **2~4개 중 필요한 최소 장면 수**를 선택한다. 같은 포즈에 소품만 바꾼 사진으로 수를 채우지 않는다. 운영자는 공통 추가 이미지 지시를 선택적으로 제공한다.
- AI는 공통 외형 정체성과 장면별 장소·표정·자세·의상·구도를 JSON으로 계획한다. 명시된 외형을 유지하고 얼굴이 잘 보이는 상반신 구도를 우선한다. 직업·취향을 책상·노트북·헤드폰·굿즈 목록으로 직역하지 않는다. 계획은 생성용 내부 자료이며 원본 설명·공개 소개·저장 파일·공개 API·로그에 넣지 않는다.
- 각 장면의 애니메·실사를 **둘 다 생성·저장**한다. 같은 장면 지시를 텍스트로 사용하지만 스타일 간 이미지 참조는 전달하지 않는다. 한 장면의 두 스타일은 병렬 생성하고 장면 간에는 순차 처리한다. 계획·생성·이미지 저장 중 어느 단계가 실패해도 부분 결과를 완성 미리보기로 교체하거나 공개하지 않는다. 기존 완성 미리보기와 공개 갤러리는 유지한다.
- Markdown의 선택적 `portrait-gallery`, 공개 API의 선택적 `portraitGallery`는 순서가 있는 `{ anime, photo }` 쌍 배열이다. 저장·공개 계약은 1~~4쌍을 허용하며 생성 계획은 2~~4장면이다. 첫 쌍은 기존 `portraits`에도 저장하고 `imageUrl`은 첫 실사 URL을 유지한다. 기존 단일 이미지·이미지 쌍 캐릭터와 구 API 응답을 계속 처리한다. 공개 이미지 경로는 공개 인물이 현재 참조하는 모든 장면만 제공한다.
- Admin은 장면 번호와 각 장면의 두 스타일을 함께 미리본다. Discovery 카드와 상세 모달은 이전·다음 사진, 장면 선택 표시와 현재 사진 수를 제공한다. 스타일 전환 시 같은 장면을 유지하고 다음 페르소나에서는 첫 사진으로 시작한다. 사진 넘김은 Like / Pass를 만들지 않으며 카드 퇴장 중에는 사진 컨트롤도 비활성화한다. 상세 모달의 Tab 순환에는 활성 사진 컨트롤을 포함한다.
- 중첩된 provider 작업도 요청 ID·인물·장면 순번·스타일을 유지한다. 실패 원인·모델·상태 코드를 남기되 외형 정체성·장면 지시·추가 프롬프트·키·이미지 바이트는 제외한다. 새 API 계약을 먼저 배포하고 Discovery, Admin 저장 기능 순서로 배포한다.
- 실제 Gemini로 두 캐릭터가 각각 3장면을 선택하고 총 12개 이미지를 생성하는 흐름을 확인했다. Chromium에서는 실제 생성 이미지를 사용하는 결정적 응답으로 3장면 기존 미리보기 → 2·4장면 생성·저장·공개, 모든 이미지 HTTP 조회, 같은 순번 스타일 전환·상세보기, Tab·Escape·포커스 복원, 데스크톱 1440×900·모바일 375×667, 기존 이미지 쌍·단일 이미지 호환을 검증했다.
- Admin 진입점은 여러 생성 호출을 기다리는 동안 Bun의 기본 10초 idle timeout이 연결을 끊지 않도록 설정한다. 각 provider 호출의 120초 제한은 유지한다. 실제 실행 진입점에 느린 테스트 provider를 연결해 22초 넘게 걸린 2장면 갤러리 요청이 정상 미리보기로 완료됨을 확인했다.
- `bun run ci:checks`의 전체 526개 테스트·파일별 커버리지 100%·타입·lint·데드 코드·중복 코드 검사·두 사이트 빌드와 `bun run verify-gates`를 통과했다. 갤러리 관련 13개 변경 모듈의 1,183개 변이 검사에서 생존·미커버 변이는 0개, mutation score는 100%다. 검증용 임시 설정은 제거했으며 저장소의 변이 범위·품질 임계값은 유지한다.

#### 후속 수정: 기본 먼저, Gemini 추천 뒤 선택한 서브만 생성

이 흐름은 위의 **전체 갤러리 일괄 생성**을 대체한다. 사용자는 기본 이미지를 먼저 확인하고, 추가 생성 비용을 직접 조절한다.

- 첫 **프로필 생성**은 공개 소개와 기본 애니메·실사 2장만 만든다. 이때 서브 계획이나 서브 이미지 생성은 실행하지 않는다. 두 기본 스타일은 동일 캐릭터 설명에서 독립적으로 병렬 생성한다.
- 기본이 마음에 들면 **이 기본으로 서브 구성 추천받기**를 실행한다. Gemini는 설명과 두 기본 이미지를 보고 서로 다른 매력을 보여 주는 최소 **1~5개 서브 장면**과 추천 이유를 제안한다. 이미 갤러리가 있으면 남은 용량 이하로 제안한다. 추천은 이미지 입력을 사용하는 텍스트 모델 요청이며 이미지 생성 호출은 0회다.
- 추천 화면은 개수·이유·장면별 제목과 연출, 남은 추천을 모두 생성했을 때 추가되는 실제 이미지 수를 표시한다. 각 **이 장면 추가**는 해당 장면의 애니메·실사 2장만 생성한다. 추천 전체를 자동 생성하는 동작은 없다. 완료한 장면은 표시·비활성화하며 기존 기본·서브는 다시 생성하지 않는다.
- 애니메 서브는 **기본 애니메 이미지**, 실사 서브는 **기본 실사 이미지**를 직접 참조한다. 스타일 사이의 참조는 보내지 않고 이전 서브를 다음 서브의 기준으로 쓰지도 않는다. 승인한 얼굴·헤어·핵심 외형과 렌더링 스타일을 유지하면서 의상·표정·자세·장소를 바꾼다. 참조는 서명된 미리보기 또는 저장된 페르소나가 지정한 서비스 소유 이미지에서만 읽으며 임의 외부 URL을 fetch하지 않는다.
- 추천안·완료한 장면 순번·추천 당시 추가 지시는 서명된 비공개 편집 draft에 보관한다. Admin 프로세스의 인물별 최신 draft를 재사용해 저장·새로고침 동안 진행을 유지하고, 같은 장면을 재제출해도 추가 이미지 호출을 하지 않는다. 이 재제출 복구 캐시는 프로세스 범위이며 서버 재시작 후에도 저장된 이미지와 현재 서명 draft의 완료 상태는 유지된다. 새 편집 화면에서는 추천을 다시 받을 수 있다. 추천안은 페르소나 파일·공개 API·로그에 넣지 않는다.
- 실패하면 완성된 기본·서브, 이전 추천안과 승인한 지시, 저장된 공개 프로필을 유지한다. 성공한 두 이미지가 모두 저장된 뒤에만 한 장면을 미리보기에 추가한다. 동시에 여러 추가를 실행할 수 없으며 오래된 추천안·변경된 캐릭터 원본·갤러리 한도를 검증한 뒤 provider를 호출한다. 기본을 다시 생성하거나 AI 캐릭터 초안을 교체하면 새 미리보기의 서브와 추천을 초기화한다.
- 저장·공개 계약은 선택적 `portraitGallery` / `portrait-gallery`의 **1~6쌍**으로 확장한다. 첫 쌍은 기본이며 기존 `portraits`·`imageUrl`을 유지한다. 기존 이미지 쌍·단일 이미지·구 API 응답은 계속 처리한다. 기존 최대 4장면을 넘는 파일을 저장하기 전에 API와 Discovery의 6장면 지원을 먼저 배포한다.
- 실제 Gemini 검증에서 한서연의 기존 기본 이미지를 사용해 **서브 2장면을 추천받았고 이미지 생성 호출은 0회**였다. 그중 한 장면만 선택해 **2회 호출로 두 스타일의 서브**를 생성했다. 기본 얼굴과 외형을 유지한 새 장면을 확인했고, 실제 운영 데이터는 변경하지 않은 격리 저장소에서 저장·공개 이미지 조회와 비공개 정보 제외를 검증했다.
- 실제 Chromium에서 기본 생성 2회, 1·5장면 추천 시 이미지 호출 0회, 실패·재시도, 선택한 장면당 2회, 기본 URL 보존, 저장·새로고침 후 완료 표시, 6장면 공개, 모바일·데스크톱 Discovery의 사진 넘김·스타일 전환·상세 모달·키보드 동작을 검증했다. 브라우저 비용·장애 검증은 실제 생성 이미지와 결정적 테스트 provider를 사용한다.
- 최종 `bun run ci:checks`의 541개 테스트·파일별 커버리지 100%·정적 검사·두 사이트 빌드와 `bun run verify-gates`를 통과했다. 단계별 생성 관련 12개 모듈의 1,144개 변이는 생존·미커버 0개, mutation score 100%다. 마지막 회귀 테스트 추가 후에는 앞선 결과 중 1,122개를 재사용하고 영향받은 22개를 재검사했다. 임시 검증 설정을 제거했고 검사 범위·임계값·예외 목록은 변경하지 않았다. 두 축 코드 리뷰에서 문서화된 기준 위반과 명세 불일치는 없었다.

#### 후속 수정: 이미지별 재생성·모든 생성의 선택 프롬프트·성별 선택

- 새 프로필의 첫 기본 애니메·실사는 함께 생성한다. 기존 이미지의 **이 이미지 다시 생성**은 선택한 스타일·장면의 1장만 교체한다. 다른 기본·서브 URL, 공개 소개, 인물 ID와 저장된 공개 프로필은 유지하며, 미리보기 확인 후 저장할 때 교체를 확정한다. 기본 실사를 바꾸면 구 클라이언트용 `imageUrl`도 갱신한다.
- 기본 이미지의 개별 재생성은 캐릭터 원본에서 해당 스타일을 새로 연출한다. 서브의 개별 재생성은 같은 스타일의 기본 이미지를 정체성 참조로, 현재 서브 이미지를 장면·구도 참조로 사용한다. 추가 프롬프트로 장면·표정·의상을 조정할 수 있다. 스타일 사이의 이미지 참조는 전달하지 않는다. 기본을 교체하면 기존 서브는 보존하고 추천안을 초기화한다. 이전 기본을 참조하는 오래된 서브 재생성 요청은 거부한다.
- 기본 쌍 생성, 서브 쌍 추가, 개별 이미지 재생성 모두 선택적 추가 프롬프트 모달에서 확인한 뒤 실행한다. 빈 입력은 정상 기본 지시로 진행한다. 취소는 요청을 보내지 않는다. 모달은 대상과 실제 생성 수를 표시하며, 실패한 같은 대상은 입력을 보존하고 다른 대상을 선택하면 빈 입력으로 시작한다. 프롬프트는 비공개 서명 draft에만 보관하고 파일·공개 API·로그에서 제외한다. 이 규칙을 `AGENTS.md`에 기록한다.
- 이름·캐릭터 설명을 바꾼 경우는 사용자의 선택대로 **전체 갱신 규칙을 유지**한다. 화면은 개별 생성·추가·추천을 비활성화하고 전체 프로필 갱신 버튼을 표시한다. 서버에서도 원본 일치와 stale 편집을 확인한 뒤 provider를 호출한다. 갱신하지 않은 원본 변경은 저장할 수 없다.
- 새 페르소나의 성별 선택은 여성 기본, 남성 준비 중·비활성화다. 두 작성 폼은 같은 선택을 사용하고 생성 경계에서 남성 선택 우회를 거부한다. 성별은 선택적 `gender: female | male` frontmatter에 보관한다. 기존 성별 없는 파일은 기존 설명을 유지하고 기존 남성 레코드는 읽기·편집할 수 있다. 공개 프로필에는 성별 필드를 추가하지 않는다.
- 캐릭터 초안·소개·기본·서브·개별 재생성 프롬프트는 명시된 성별을 반영하며 여성·남성 모두 표현할 수 있게 작성한다. 남성 얼굴·스타일링·말투를 여성으로 바꾸지 않는다. 성별이 없는 기존 인물은 설명을 기준으로 한다. `gender`를 쓰는 새 Admin 저장 전에 API의 선택적 성별 필드 읽기를 먼저 배포한다.
- 실제 Gemini로 기존 서브 실사를 정체성·장면 이미지 두 참조와 선택 프롬프트로 재생성해 **이미지 호출 1회, 나머지 3장 보존**을 확인했다. 실제 운영 데이터는 변경하지 않은 격리 저장소에서 미리보기·저장·공개 조회와 프롬프트 제외를 검증했다. Chromium에서 여성 기본·남성 비활성화, 첫 2장, 개별 1장, 모든 생성 모달·취소·빈 입력·같은 대상 재시도·다른 대상 초기화, 원본 변경 전체 갱신, 모바일·데스크톱 저장 흐름을 확인했다.

#### 최신 흐름: 장수 직접 선택·독립 이미지·본인이 고른 자기표현

- 모든 이미지 생성 모달은 **1장 기본값**이다. 여러 장은 운영자가 직접 선택한 경우만 생성한다. 첫 프로필 생성은 스타일당 1~6장을 선택하며 애니메·실사 합계 **2~12장**을 확인 전에 표시한다. 첫 두 메인은 같은 캐릭터 설명에서 독립 병렬 생성하고, 선택한 추가 사진은 해당 스타일 메인을 참조한다.
- 이후에는 **이미지 추가**에서 애니메 또는 실사를 선택해 기본 1장부터 원하는 수를 만든다. 메인을 포함해 스타일별 최대 6장이다. 추가·개별 재생성은 다른 이미지를 유지하며, 개별 재생성은 항상 1장이다. 추천 요청이나 추천 개수를 자동 선택하는 단계는 없다.
- 생성 후에는 `portraits`의 스타일별 메인과 `secondaryPortraits`의 독립 `{ style, imageUrl }` 배열만 관리한다. Markdown의 추가 이미지 필드는 `secondary-portraits`다. 장면/쌍 ID, 완료 순번, 추천안·‘추가됨’·구성 복원 상태를 저장하지 않는다. 기존 `portrait-gallery` 파일은 첫 쌍을 메인, 나머지를 독립 사진으로 읽고 새 형식으로 저장한다. 기존 이미지 파일을 재생성하지 않는다. 공개 `imageUrl`은 구 클라이언트용으로 유지한다.
- 대표 참조는 인물의 얼굴 구조·나이·헤어·특징과 작화 스타일을 식별하는 용도다. 추가 사진은 촬영자·카메라 위치·행동·시선을 새 장면에 맞게 정하고 얼굴 각도·표정·손동작을 함께 새로 그린다. 얼굴이나 손을 그대로 두고 몸·의상·배경만 교체하거나 원본의 휴대폰·브이·든 팔을 무관한 장면에 반복하지 않도록 지시한다. 개별 재생성에서는 현재 사진의 장면·구도 참조 역할은 유지하되 대표 이미지의 포즈를 이식하지 않는다.
- 메인 개별 재생성은 원본에서 그 스타일의 사진만 새로 만든다. 추가 이미지 재생성은 같은 스타일 메인으로 외형을, 현재 사진으로 장면·구도를 참조한다. 스타일 간 이미지 참조는 보내지 않는다. 메인을 바꿔도 다른 사진은 유지하고 이전 메인을 참조한 오래된 추가 이미지 재생성은 거부한다.
- **이 이미지 삭제**는 한 사진만 미리보기에서 제거한다. 메인이면 같은 스타일 남은 사진을 승격하며, 반대 스타일은 유지한다. 한 스타일 사진이 없으면 Discovery는 빈 사진 안내를 표시한다. 모든 사진을 삭제하면 비공개 초안이 된다. 저장 전 공개 목록·이미지는 그대로이고, 저장 후 프로필에서 해당 사진 참조만 제거된다. 물리 파일과 직접 R2 URL은 유지한다.
- 이미지와 자기소개는 **본인이 데이팅 프로필에 골라 올릴 자기표현**이다. 사진은 자연스럽게 잘 나온 셀카·친구가 찍은 일상·카페·취미·여행 전신처럼 촬영자와 거리를 다양하게 한다. 설명의 집착·불안·트라우마를 공포·붕괴·위협적인 장면으로 직역하지 않고 은근한 분위기 정도로만 표현한다. 상반신이나 연예인 화보 구도를 강제하지 않는다. 애니메는 저채도 살구·회색 계열, 굵고 부드러운 외곽선과 최소한의 내부 선, 경계가 번지는 그라데이션 명암, 무광 피부 및 배경의 옅은 필름 그레인으로 표현한다. 인물 시트와 사진에 같은 작화 지시를 적용하고 기존 참조의 강한 색·선화·명암은 인물 정체성으로 오인하지 않는다.
- 공개 소개는 페르소나가 자기 말투로 직접 쓰는 짧은 **1인칭 소개**다. 직업·성격·내면 요약문이나 제삼자 캐릭터 설명으로 쓰지 않는다. **자기소개만 다시 쓰기**는 텍스트 모델만 호출하고 사진을 유지한다.
- 선택적 추가 프롬프트는 이번 생성 대상에만 적용한다. 취소는 모델 요청 0회, 빈 입력은 정상 기본 지시다. 실패한 같은 대상은 프롬프트·선택 장수를 유지하며 다른 대상으로 바꾸면 빈 프롬프트·1장부터 시작한다. 비공개 서명 draft에만 담고 파일·공개 API·로그에서는 제외한다.
- 첫 기본 두 스타일이나 명시적 여러 장 생성 중 일부 실패하면 완성된 사진을 미리보기에 보존하고 요청 ID가 있는 복구 안내를 표시한다. 두 스타일의 결과를 모두 관찰한 뒤 응답하며, 모두 실패하면 이전 서명 미리보기를 유지한다. 미리보기의 사진 편집 상태는 현재 Admin 프로세스에서 새로고침 시 복원하고, 성공한 동일 추가 요청의 재제출은 유료 호출을 반복하지 않는다. 서버 재시작 후 저장된 이미지와 제출한 서명 미리보기는 계속 사용할 수 있다. 이름·설명을 바꾼 경우는 전체 갱신 후에만 저장한다.
- 신규 성별은 여성 기본·남성 비활성화이며 기존 male·성별 없는 레코드는 계속 읽는다. 새 형식·성별의 선택적 필드를 읽는 API → Discovery → Admin 저장 순서로 배포한다. Discovery는 기존 단일 이미지·이미지 쌍과 구 API의 갤러리 응답도 처리한다.
- 실제 Chromium에서 기본 1장(첫 2회 호출), 선택 스타일 추가 1장(1회), 직접 선택한 2장(2회), 개별 재생성 1회, 취소 0회, 실패 재시도·개별 삭제·저장 전후 공개 URL과 1440×900·375×667 화면을 확인했다. 격리 저장소의 실제 Gemini 요청에서는 자기소개 1회와 선택한 실사 추가 1회로 본인 말투의 소개와 자연스러운 여행 전신 사진을 생성했다. 운영 데이터는 변경하지 않았다.
- 최종 `bun run ci:checks`의 597개 테스트·123개 테스트 파일과 파일별 모든 커버리지 100%, 타입·lint·데드 코드·중복 코드 검사와 두 사이트 빌드, `bun run verify-gates`를 통과했다. 변경한 28개 런타임 모듈의 2,488개 변이는 생존·미커버 0개, mutation score 100%다. 마지막 검사는 기존 1,995개 결과를 재사용하고 영향받은 493개를 다시 검사했다. 검증용 임시 설정은 제거했으며 품질 임계값·검사 범위·예외 목록은 변경하지 않았다. Standards / Spec 최종 리뷰에서 문서 기준 위반과 남은 명세 불일치는 없었다.

#### 최신 흐름: 다각도 인물 시트에서 시작하는 이미지 제작

문서 생성은 신규·기존 개선·검수 후 수정 모두 JSON 스키마의 인물 설정 템플릿을 채우는 방식이다. AI는 비공개 `CharacterSheet` 객체와 자유로운 공개 프로필 Markdown을 반환하고 서버가 `renderCharacterSheet`로 최종 Persona Markdown을 조립한다. 신규 생성만 초기 State·Memory를 함께 반환하며 기존 개선은 초기 문서를 유지한다. 날짜·필수 내용·수치·정체성은 검증하지만 사람이 편집한 문서의 줄 앞뒤 공백이나 빈 줄 개수는 실패 이유로 삼지 않는다.

- 신규 Persona는 설명에서 **애니메·실사 다각도 인물 시트 각 1장**을 먼저 만든다. 시트는 동일 인물의 정면·반측면·측면을 한 장에 배치하고 중립적인 닫힌 입·단순한 회색 상의·흰 배경을 사용한다. 시트 생성에는 3:2·1K, 프로필 사진에는 기존 4:5·1K를 사용한다. 두 스타일은 독립적으로 생성하고 완성된 스타일의 시트를 즉시 기준으로 자동 채택한다. 별도 승인 단계나 자동 사진 생성은 없다.
- 기존 Persona는 같은 스타일의 기존 서비스 소유 사진에서 **이 사진으로 시트 만들기**를 실행하거나 설명에서 새 시트를 만들 수 있다. 원본 사진을 보존하고 외형과 작화만 추출해 중립적인 다각도 시트를 만든다. 애니메 사진을 실사 시트에 넘기거나 임의 외부 URL을 참조하지 않는다. 시트가 없는 스타일의 사진 생성·재생성은 provider 호출 전에 거부하며 기존 사진 조회·편집·저장·공개 상태는 유지한다.
- 시트와 갤러리 사진 생성은 공개 프로필의 유효성이나 자기소개 유무를 전제로 하지 않는다. 기존 공개 나이 항목 등 문서의 보완 과제가 있어도 이미지 작업을 할 수 있으며, 이 과정에서 Persona 원문을 검증·자동 보완·재작성하지 않는다. 공개 저장의 문서·초기값 검증은 그대로 유지한다.
- 갤러리 사진은 모두 동등하다. 대표·추가 구분, 대표 지정·승격, 첫 사진 전용 생성, 전체 사진 재생성 동작은 없다. 첫 사진부터 스타일별 **사진 추가**에서 기본 1장, 최대 남은 용량까지 선택하고 사진별 프롬프트를 확인한다. 스타일별 최대 6장을 완료 사진과 예약량을 합쳐 검증한다. 기존 사진은 재생성하지 않고 현재 순서를 유지하며 Discovery는 목록의 첫 사진부터 보여 준다. D1은 기존 스타일·순서 행을 사용하고 저장·공개 계약의 첫 사진 필드는 갤러리 순서에서만 투영한다. 작성 경계의 사진에는 `main` 플래그가 없다.
- 모든 AI 사진의 추가·재생성은 같은 스타일의 읽을 수 있는 인물 시트를 필수 정체성 참조로 사용한다. 시트가 없거나 읽히지 않으면 UI를 비활성화하고 서버의 등록·실행·행 재시도에서도 유료 호출 전에 중단한다. 대표 사진이나 설명으로 참조를 대체하지 않는다. 모든 사진의 개별 재생성은 시트와 선택한 사진의 장면·구도를 함께 참조하고 선택한 URL만 교체한다. 삭제는 선택한 사진만 제외하고 나머지 순서와 시트를 유지한다. **설명에서 시트 다시 만들기**는 기존 시트나 사진을 참조하지 않고 현재 편집 중인 설명·선택 스타일·추가 프롬프트로 외모를 새로 구성한다. **이 사진으로 시트 만들기**는 명시적으로 선택한 같은 스타일의 보유 사진만 참조한다. 교체 성공은 이후 생성에만 적용하고 실패하면 이전 시트를 유지한다. 이미 완성된 사진은 보존한다.
- 시트 연결은 Persona Markdown·Persona 버전·공개 API·Conversation Catalog에서 분리한다. 운영 D1의 `persona_identity_sheets`는 Persona ID·스타일로 조회하고 objectKey CAS로 교체한다. 최초 Persona 저장 전에도 시트가 영속되며 서버 교체 후 재사용된다. 파일 저장소는 별도의 `identity-sheets/`에 연결을 보관한다. 이미지 원본은 기존 R2 이미지 저장 경계를 사용하며 직접 URL의 접근 정책도 기존 사진과 같다. 시트는 공개 프로필에 나열하지 않고 스타일별 여섯 사진 한도에도 포함하지 않는다.
- 시트도 같은 Durable Object FIFO에서 한 장씩 처리한다. 두 스타일 생성은 실제 시트마다 선택 프롬프트 1개씩, 개별 생성·교체는 1개를 제공하고 유료 호출 전 대상·장수를 확인한다. 완료 즉시 미리보기와 생성 기준을 갱신하고 재제출은 같은 작업 영수증으로 복구한다. 생성 중 같은 Persona의 다른 작업·저장·원문 변경을 잠그고, 다른 Persona의 작업은 FIFO에 추가할 수 있다. 중단된 유료 호출은 자동 반복하지 않으며 실패한 행의 명시적 재시도만 실행한다. 사진 작업은 제출한 시트 기준과 영속된 현재 기준의 일치를 확인해 오래된 참조의 유료 호출을 막는다.
- 시트 연결과 마지막 완료 작업 식별자는 같은 저장 쓰기로 확정한다. 시트 저장 후 Durable Object 초안 checkpoint 전에 중단되면 해당 식별자로 완성 결과를 복구하고, 확인한 행 재시도는 provider를 다시 호출하지 않는다. 작업 식별자가 없는 이전 실행 기록은 복구 파일로 보존하고 자동 실행하지 않는다. AI 캐릭터 초안으로 인물 전체를 교체하면 이전 시트와 생성 사진 초안을 초기화하고 새 설명에서 시트부터 다시 만든다. 이름·원문을 일반 편집하는 경우는 기존 시트를 유지한다.
- Admin은 원문 오른쪽에서 기준 시트와 프로필 사진을 구분한다. 시트 영역은 스타일별 미리보기·생성·다시 만들기를 제공하고 기존 사진마다 시트 원본 선택 동작을 제공한다. 폴링 중에도 열린 옵션과 입력값을 보존하며 완성된 시트를 즉시 표시한다. 배포는 새 D1 테이블을 먼저 적용한 뒤 Admin을 배포한다. 기존 인물의 시트를 일괄 자동 생성하지 않는다.

#### 사진별 프롬프트·공통 순차 큐·보이는 생성 과정

로컬 데이터 이관은 운영자 결정에 따라 `import:local` 명령으로 명시적으로 수행할 수 있다.
기존 ID·원문·공개 상태·현재 초기 문서·스타일별 사진 순서를 보존하고, 생성 이미지 원본은 기존 키로 로컬 R2에 옮긴다.
초기 문서가 없는 이전 공개 인물은 빈 초기값과 기존 공개 상태를 유지한다. 다음 일반 저장의 공개 검증은 계속 적용한다.
원본 파일을 수정하거나 AI로 다시 생성하지 않으며, 동일 데이터의 재실행은 건너뛰고 충돌은 덮어쓰지 않는다.

현재 배포에서는 D1의 Persona·초기 State·초기 Memory와 저장된 사진 연결을 revision CAS와 atomic batch로 확정한다.
사진 원본은 R2 `persona-images`에 보관하고 `https://persona-images.renai.im/<objectKey>`로 직접 제공한다.
D1은 objectKey를 저장하고 Persona·공개/비공개 Catalog는 절대 이미지 URL을 반환한다. 운영 Admin·API는 사진을 프록시하지 않는다.
신규 UUID 키 업로드에는 1년 immutable 캐시 메타데이터를 설정한다. 생성 참조용 서버 원본 읽기는 R2 binding을 사용한다.
초안·미참조 사진도 URL로 접근할 수 있으며 비공개 전환·참조 삭제가 기존 이미지 URL을 회수하지 않는다. 저장·공개 상태는 프로필 목록 반영만 제어한다.
로컬 개발의 `/images/<key>`는 Worker 경계에서 인증 없이 GET·HEAD를 제공하는 로컬 R2 경로다.
운영 R2와 같이 초안·미참조 사진도 URL로 접근할 수 있으며, 편집 화면과 비공개 Catalog의 인증은 유지한다.
Wrangler의 로컬 origin은 실제 로컬 Admin 포트로 명시해 공개 사진 URL에 배포용 호스트가 섞이지 않게 한다.
이전 `/discovery/images/` 경로는 제공하지 않는다.
아래 FIFO·편집 캐시·중복 요청 상태의 소유자는 프로세스 메모리에서 단일 SQLite Durable Object로 바뀌었다.
사진별 alarm 처리와 private draft/task checkpoint를 사용한다. 중단된 유료 호출은 자동 반복하지 않으며,
운영자가 해당 사진의 재시도를 확인해야 한다. 완성 사진은 유지하고, 중단된 공통 문서 준비의 의존 사진은 차단한다.
Discovery와 iMessage는 같은 Worker Catalog를 읽는다. 새 Conversation에만 초기 State/Memory를 적용하고,
기존 Conversation 문서와 Catalog에서 사라진 인물의 세션 스냅샷은 보존한다.
Admin 저장 확정 후 기존 관리 인증으로 api-app의 `POST /management/catalog/refresh`를 호출한다. api-app은 시작 시와 변경 알림에만 Catalog를 읽으며 heartbeat에서는 조회하지 않는다. 알림 실패는 저장 실패와 구분해 적용 대기를 표시하고, Admin Durable Object에 기록한 미전달 알림만 공유 alarm으로 재시도한다.

- 편집 화면은 왼쪽 Markdown 원문과 오른쪽 사진 관리로 구성하며 사진 패널·저장 툴바를 고정하지 않고 페이지 전체를 스크롤한다. 오른쪽은 실사·애니풍의 독립 갤러리로 나누고, 스타일별 완료 사진 수·대기 예약량·추가 버튼을 함께 표시한다. 모든 갤러리 사진은 동등하며 스타일별 순서만 유지한다. 사진 재생성·삭제는 개별로 실행하고 삭제 전에 대상과 sibling 보존을 확인한다. 좁은 화면에서는 사진 영역을 원문 아래에 배치한다. 폴링은 갤러리와 장수 표시만 갱신하며 열린 옵션 입력과 키보드 포커스를 유지한다.
- 저장된 Persona의 기본 편집 화면에는 빈 아이디어 생성 폼을 표시하지 않는다. 새 Persona 작성과 실제 초안 입력을 복구할 때만 표시한다. 인물 이름·변경 상태·공개 설정·저장을 페이지 맨 위 한 줄에 모으고, 원문은 제목/형식 상태/편집·미리보기 전환과 간결한 이름·문서 도구만 둔다. 중복 원문 제목과 중첩 에디터 테두리를 제거한다. 사진은 작은 2열 썸네일로 표시하고 스타일 영역의 중첩 배경·테두리·반복 설명은 제거한다. 썸네일은 R2 원본 이미지 URL로 연결해 크게 확인할 수 있다.
- 본화면 정리 검증: 백도희의 설정·사진 4개를 격리 저장소로 복사한 Chromium 1440·1024·390·375px에서 상단 저장바·빠른 원문 진입·작은 사진·가로 넘침 없음과 편집/미리보기·원문 저장 시 사진 보존·이미지 옵션 취소·새 Persona 작성 흐름을 확인했다. 실제 운영 파일과 유료 생성은 변경하지 않았다. Node 24의 `bun run ci`도 1,059개 테스트·201개 파일, 파일별 커버리지 100%로 통과했다.
- 운영자는 생성할 **실제 사진마다** 선택적 프롬프트를 입력한다. 추가 2장이면 입력칸 2개, 첫 생성에서 스타일당 2장이면 애니메·실사 합계 4개다. 개별 재생성은 1개다. 각 입력은 해당 사진에만 전달하고, 빈칸은 캐릭터·스타일·참조와 자연스러운 사진 방향을 사용한다. 장수를 줄이면 제외한 입력은 제출하지 않고, 모달 안에서 다시 늘리면 편집값을 복원한다. 다른 생성 대상으로 바꾸면 1장·빈 입력부터 시작한다.
- Persona 정체성은 `이름`·`성별`·`생년월일: YYYY-MM-DD`를 보유한다. 생년월일 검증은 Gregorian 유효 날짜와 UTC 오늘 이전 또는 당일을 요구한다. 연령은 UTC 기준 오늘과 월·일을 비교해 계산하며, 2월 29일 생일은 비윤년의 3월 1일에 나이가 증가한다. 공개 API의 나이는 배포 전환 중 선택 필드이며 Admin과 Discovery는 동일한 숫자 형식을 표시한다. 기존 공개 인물은 날짜 누락만으로 무효화·비공개 전환하지 않으며, 조회 중 날짜를 생성하지 않는다.
- 신규 생성과 전체 Persona 개선은 누락되거나 잘못된 생년월일을 정확한 날짜로 설정한다. 현재 UTC 날짜를 생성·검수에 제공하고 기존 나이·연령대·배경과 일관되게 보완한다. 기존의 유효한 날짜는 수정·검수·보정에서 보존한다. 보완한 날짜는 개선 요약과 편집 초안에 반영하며 일반 저장으로 확정한다. 공개 기본 정보의 기존 수동 나이·생년월일은 제거하고 정체성 한 곳에만 기록한다. 공개 저장 경계는 수동 나이 행을 거부하며, 미완성 private draft에는 날짜가 없어도 된다.
- 첫 프로필·추가 이미지·개별 재생성을 **Admin 전체의 공통 FIFO 큐**로 묶고, 이미지 생성·저장·미리보기 반영은 한 장씩 진행한다. 첫 애니메·실사는 같은 캐릭터 설명에서 독립 생성하며 스타일 간 이미지 참조는 보내지 않는다. 같은 페르소나도 처리 중 추가 이미지·개별 재생성·실패 사진 재시도를 뒤에 등록할 수 있다. 스타일별 최대 6장은 완료 사진과 실행·대기 중 추가 사진 예약량을 합쳐 서버와 화면에서 검증한다. 뒤 묶음은 실행 직전 최신 미리보기를 이어받으며, 이미 교체된 재생성 대상은 유료 호출 전에 거부한다.
- 브라우저는 옵션 확인 후 등록 요청을 보내고 바로 해당 작업 URL로 이동한다. 인증된 `/image-jobs/<id>` 화면을 짧은 간격으로 조회해 묶음의 대기 순서와 사진별 **대기·생성·저장·완료·실패·기준 이미지 대기** 상태, 완료 수, 경과 시간과 완료 썸네일을 보여준다. 모델이 제공하지 않는 가짜 진행 퍼센트는 만들지 않는다. 완성된 사진은 모두 끝날 때까지 기다리지 않고 현재 서명 미리보기에 바로 반영한다. 기존 폼 요청도 공통 큐를 통해 처리하며 완료 응답 계약을 지원한다.
- 상태와 요청 중복 방지는 기존 편집 캐시와 같은 **Admin 프로세스 메모리**에서 관리한다. 새로고침·다른 탭으로 이동한 뒤 작업 URL이나 저장된 인물의 편집 화면에서 현재 작업을 다시 조회할 수 있다. 이미지 파일은 기존 저장소에 보관한다. 큐 상태·작업 ID·사진 순번은 운영 중 진행 표시용이며 페르소나 Markdown·공개 API에 저장하지 않는다.
- 한 사진이 실패해도 처리 가능한 뒤의 사진은 계속 생성한다. 초기 메인이 없으면 그 스타일의 추가 사진은 유료 호출 없이 기준 이미지 재시도 상태로 둔다. **이 사진만 재시도**는 해당 입력을 다시 보여주는 확인 모달을 열고 선택한 실패/대기 사진 1장만 큐에 넣는다. 완료한 사진·다른 스타일은 유지한다. 같은 옵션이라도 운영자가 다시 확인하면 새 묶음으로 등록하고, 같은 확인 요청의 통신 재시도는 기존 작업을 돌려줘 중복 비용을 만들지 않는다. 한도 초과 등 등록 오류도 기존 진행 화면과 편집 잠금을 유지한다.
- 실행·대기 묶음을 한 화면에 함께 표시하고, 다음 요청의 옵션·프롬프트를 작성하는 동안 폴링이 입력과 선택 장수를 지우지 않는다. 처리 중인 인물의 이름·설명·성별·자기소개·삭제·저장은 마지막 묶음까지 잠그며, 새 이미지 요청은 계속 등록할 수 있다. 전체 프로필 갱신은 기존 작업이 끝난 뒤 실행한다. 큐 등록과 작업 시작 시 저장된 원본 스냅샷을 확인하고, 원본이 바뀐 오래된 요청은 유료 생성 전에 거부한다. 처리 후에는 미리보기를 확인하고 **저장하기**로 공개 변경을 확정한다.
- 프롬프트는 비공개 입력·서명 draft와 운영 큐 안에서만 사용한다. persona 파일·공개 응답·로그에는 넣지 않는다. 큐 등록 요청 ID를 백그라운드 각 사진의 job ID·스타일·순번·단계와 연결하고, 재시도는 새 요청 ID를 사용한다. 원인·provider 상태·실패 진단은 각 작업에서 한 번 기록하며, 묶음 종료에는 결과와 소요 시간의 구조화된 요약을 남긴다.

#### Identity sheets and equal gallery photos

- 스타일별 정체성 시트는 Persona 문서 및 공개 갤러리 사진과 분리해 저장하며, 스타일의 최대 6장 사진 제한에 포함하지 않는다. 새 Persona는 애니메·실사 시트를 각각 생성해 완료 즉시 채택한다. 기존 Persona는 보유한 해당 스타일 사진 또는 설명을 기준으로 시트를 만들거나 교체할 수 있다.
- 모든 사진은 동등하다. Discovery는 선택 스타일의 갤러리 순서대로 표시하며 첫 사진은 단지 첫 번째일 뿐이다. 대표/보조 역할, 대표 선택·승격, 전체 갤러리 생성은 제공하지 않는다. 추가·재생성·삭제는 선택한 사진만 대상으로 하며 나머지 사진과 시트는 보존한다.
- 모든 사진 추가와 재생성은 서버 경계에서 같은 스타일의 읽을 수 있는 시트를 요구한다. 새 사진은 시트를 외모 기준으로 사용하고, 개별 재생성은 시트와 선택된 기존 사진의 장면·구도 참조를 함께 사용한다. 시트가 없거나 읽을 수 없으면 설명만으로 대체하지 않고 유료 생성을 거부한다.
- 시트 생성·교체도 이미지별 프롬프트/확인과 전역 FIFO 큐를 사용한다. 시트 생성은 해당 페르소나의 대기 작업이 없을 때만 시작하며 완료 전 같은 페르소나의 경쟁 작업은 잠근다. 교체 실패 시 이전 시트를 보존하고 완료 사진은 유지한다.

#### 캐릭터 초안 생성 harness

- 현재 작성 계약은 [persona.md 단일 원본](persona-authoring-profiles.md)이다. 기본 설명에서 **고정된 인물 설정과 본인이 쓴 공개 프로필을 함께 포함한 Markdown**을 한 생성 요청으로 만든다. 기억과 실제 현재·관계 상태는 런타임에서 결정한다.
- 생성 기준은 `apps/admin/src/character-policy.json`에 배포 가능한 생성 전용 자료로 정리한다. 샘플은 성향과 행동의 양립을 설명하는 참고이며 새 인물의 이름·직업·수치 기본값이 아니다. 생성 규칙과 검수·보정 지시는 대화 에이전트의 지침에 추가하지 않는다.
- Gemini는 완성된 Markdown 본문을 반환한다. 비공개 영역은 인물 설정·말투·문자 예시·기본 Stat 6개와 근거·숨겨진 특성을 검증하고, 마지막 `## 공개 프로필`에는 필수 자기소개와 Persona가 원하는 자유로운 제목·글·목록을 둔다. 공개 관심사나 생활 항목은 생략해도 정상이며 자동 보충하지 않는다.
- 기존 이름 등 원본에 명시된 사실과 핵심 모순을 보존하고 빈 부분만 보강한다. 선택된 성별은 생성과 보정 결과에서 검증한다. 성장 배경은 인물 설정으로 창작할 수 있지만 사용자 사실·공동 경험·약속·근거 사건·형성된 특성·상태 파일·기억 파일은 만들지 않는다.
- 순서는 **전체 Markdown 생성 → 문서 구조·값 검증 → 의미 검수 → 필요할 때 한 번 보정·재검수**다. 기본 성공은 생성·검수 2회이며, 소개·공개 항목을 따로 생성하지 않는다. 검수 JSON은 실패 판단과 private 보강 보고서에만 사용한다.
- 저장 원본은 Markdown 본문 하나이며 별도 description·bio·고정 공개 항목 사본을 frontmatter에 쓰지 않는다. 디자이너는 원문 하나에서 수정·추가·삭제한다. 이름·성별·비공개 설정·공개 글 변경을 기존 사진과 함께 저장하며 사진 생성은 별도로 선택한다. 실패하면 이전 입력과 결과를 보존한다.
- 생성·검수·보정과 provider 실패는 기존 요청 ID로 진단하고 오류 코드·모델·단계·소요 시간을 기록한다. 생성된 비공개 설정과 검수 지적도 로그에서 제외한다. 실제 Admin 요청 경계에서 저장·실패 복구·제한된 보정·민감 정보 제외를 검증한다.
- 검증: Node 24에서 `bun run ci`의 977개 테스트·190개 파일, 파일별 커버리지 100%, 정적 검사·두 Discovery 빌드·gate 자체 검증을 통과했다. 실제 Gemini로 하린·지우의 고정 설정과 짧은 도예가 아이디어를 확장해 각각 약 2,200~2,800자 상세 description을 생성했다. 세 경우 모두 생성·검수 2회로 완료했고 기본 성향 6개와 런타임 섹션 제외를 확인했다. 원본과 참고 예시의 혼동으로 이름이 바뀌던 지침을 수정한 뒤 하린·지우의 이름 보존을 재확인했다.

#### 공개 프로필 항목 편집·페르소나 개선

- Persona 문서는 저장 시 버전을 보관하고 최신 저장본을 에이전트에 자동 적용한다.
  Admin의 버전 기록에서 현재/선택 원문을 비교하고 과거 문서를 새 최신 버전으로 복원한다.
  사진·공통 초기 State/Memory·공유 State/Life memory·사적인 Relationship 범위는 복원 범위에서 제외한다.
  저장 충돌, 현재 초기값과의 불일치와 미저장 편집은 실제 저장 전에 검사한다.

- Persona 원문 하나를 유지하면서 공개 자기소개와 기본 정보·관심사·라이프스타일·관계
  스타일·문답·자유 항목을 선택해 추가·수정·삭제·정렬한다. 정보 행·태그·질문/답변 입력을
  제공하고 원문과 미리보기에 동기화한다. 자기소개 외 항목은 선택이며 자동 생성은 인물의
  생활·취향·관계 기대를 알 수 있게 구체적인 공개 내용을 작성한다.
- `형식 정리`는 정상 문서에도 실행 가능한 `페르소나 개선`으로 대체한다. 전체 Persona/
  공개 프로필 범위와 선택적 개선 요청으로 현재 편집본을 보강한다. 변경 전후·요약을
  확인한 뒤 초안에 적용하거나 취소하고 저장해야 공개한다. 오래된 원문에는 적용하지 않는다.
- 사진·State·Memory와 의도적인 비공개 선택을 보존한다. 상세 계약과 저장 표현은
  [Persona 작성·상세 프로필](persona-authoring-profiles.md)을 따른다.

#### 공통 상태·기억 초기값 작성

현재 흐름은 **세 문서 탭·동시 생성·개별 재생성·공개 저장 검사**이며 이전 별도 초기값 화면과 내부 Markdown 미리보기를 대체한다.

런타임 소유권은 [ADR-0023](../adr/0023-personas-share-one-life-across-up-to-five-conversations.md)을 따른다.
첫 Conversation에서 공유 State·Life memory를 한 번 초기화하고 이후에는 인물의 현재 생활을 함께 사용한다.
새 Conversation마다 별도 Relationship 범위를 만들고 출발 affection만 Catalog에서 가져온다.
이후 초기값 편집은 미래 출발 affection과 Discovery의 공개 초기 실력에만 반영한다.
agent·ground rules는 인물 루트 한 곳에 적용하며 보존·종료 세션도 현재 지침을 읽는다.

- 아이디어에서 Persona·State·Memory를 한 생성 요청으로 작성하고 함께 검수한다. 정상 생성·검수는 2회이며 State의 숨겨진 특성 이름·강도는 생성된 Persona에서 가져온다. 공개 글과 초기값을 따로 추가 생성하지 않는다.
- Persona / State / Memory 탭은 입력·커서·실행 취소를 유지한다. State와 Memory에는 각각 현재 Persona의 비공개 영역으로 해당 문서만 다시 생성하는 버튼을 둔다. 공개 글·사진·다른 초기값을 입력에 다시 보내지 않는다.
- 내부 문서 미리보기 토글은 삭제하고 오른쪽에 사진 스타일/사진 넘김·현재 이름·공개 프로필 전체를 실시간 표시한다. 공개 경계 오류에서 비공개 원문을 대체 표시하지 않는다. 사진 관리는 같은 화면에서 독립적으로 실행한다.
- 공통 저장 버튼은 세 문서를 함께 다루며 저장 후 선택한 탭을 유지한다. 새 공개 저장은 실제 Persona 형식·이름/성별·공개 자기소개/사진, State 수치/특성 일치, Memory 제목/내용을 클라이언트와 서버에서 검사한다. 기존 공개 노출은 유지하고 다음 공개 저장부터 검사한다. 미완성 비공개 초안과 공개 해제는 허용한다.
- 전체 계약은 [Persona 작성·상세 프로필](persona-authoring-profiles.md)과 [상태·기억의 소유권](persona-state-memory.md#범위와-초기값)을 따른다.

##### 이전 별도 초기값 화면 구현 이력

- 저장된 Persona에서 **초기 상태·기억** 화면으로 이동해 `STATE.md`·`MEMORY.md`를 별도로 생성·편집·저장·다운로드한다. 생성은 저장된 비공개 시트를 사용하는 텍스트 호출 1회이며 사진 생성은 호출하지 않는다.
- 컨디션 5개는 인물의 생활에 맞춰 생성하고, 초기 호감도 `affection`은 성향·관계관·연락 기대에서 제안한다. 모두 정수 0–100이며 운영자는 State 원문에서 직접 수정한다. affection은 처음 만난 상대를 알아가려는 관심이지 이미 쌓인 친숙함·신뢰·연애 의사나 행동 확률이 아니다. affection 출발값만 새 Conversation마다 복사하며 공유 범위는 첫 Conversation에서 한 번 초기화한다. 숨겨진 특성의 이름·강도는 시트에서 그대로 가져온다. 생활 기억은 인물에 맞는 출발 상황을 보강할 수 있으나 사용자와의 공동 경험·약속은 만들지 않는다.
- 생성 결과는 미리보기이며 저장 전 기존 파일을 유지한다. 두 파일은 `initial/{id}/`에서 함께 확정한다. Persona 수정으로 자동 재생성하지 않으며 오래된 원본·초기값 스냅샷의 덮어쓰기를 거부한다.
- CodeMirror 두 에디터는 각 원문을 즉시 폼에 동기화하고 이미지 작업 중 잠금과 기존 요청 진단 경로를 따른다. 공개 API는 초기값을 반환하지 않는다.
- 화면은 Persona로 돌아가는 경로·인물 이름·짧은 작업 제목과 저장 상태를 분리한다. 저장은 주 버튼, 다시 생성은 보조 버튼이다. 데스크톱은 좁은 STATE와 넓은 MEMORY 패널, 모바일은 한 열로 표시한다. 파일 제목·설명·원문·작성 규칙에 각각 같은 여백을 적용한다. STATE는 CodeMirror YAML, MEMORY는 Markdown으로 문법 강조하며 원문에 장식 밑줄을 넣지 않는다.
- 파일 계약·저장 방식·백업 범위는 [상태·기억 설계](persona-state-memory.md)를 따른다.
- 검증: Node 24에서 `bun run ci`의 1,059개 테스트·201개 파일과 파일별 커버리지 100%, 정적 검사·두 Discovery 빌드·gate 자체 검증을 통과했다. 실제 Gemini 텍스트 요청 1회로 공통 초기값을 생성하고 격리 저장소의 Chromium 1440×900·375×667에서 두 CodeMirror 편집·저장·다운로드·재생성 실패 시 입력과 파일 보존을 확인했다. 수평 넘침과 브라우저 예외는 없었으며 사진 provider와 운영 Persona 파일은 사용하지 않았다.
- UI 수정 후 같은 `bun run ci`를 다시 통과했다. 백도희의 저장된 설정을 격리 저장소로 복사한 Chromium 1440·1024·390·375px 화면에서 패널 정렬·YAML 강조·밑줄 없음·44px 버튼·가로 넘침 없음과 실제 입력·저장·실패 복구를 확인했다.

#### Discovery 상세 프로필

공개 전달 계약은 **구조화된 JSON**이다. 작성 원본은 Markdown을 유지하고 Catalog가
공개 영역만 `profile: { introduction, sections }`로 변환한다. 섹션은 기본 정보·관심사·
라이프스타일·관계 스타일·문답·자유 글의 명시적 타입을 갖는다. Discovery는 Markdown
문자열을 받거나 렌더링하지 않고 정보 행·관심사 태그·질문 카드로 표시한다. Admin도
같은 변환과 표시를 사용한다. 자세한 필드와 순차 배포 계약은 아래 문서를 따른다.

공개 자기소개 확장, 기본 정보·관심사·라이프스타일·관계 스타일·문답과 기존
Persona 검사·변환의 현재 계약은 [Persona 작성·상세 프로필](persona-authoring-profiles.md)을 따른다.

- 첨부 Tinder 화면처럼 **탐색 카드가 그 자리에서 상세 프로필로 펼쳐지는 흐름**이다. ↑ 버튼으로만 보고 있던 사진에서 상세를 열고, 상단 이름·↓ 접기 버튼을 고정한다. 사진·이름·소개 클릭은 상세 전환을 만들지 않는다. 아래로 큰 사진과 본인이 쓴 공개 자기소개를 읽으며 사진 넘김과 4:5 비율을 유지한다. 데스크톱은 왼쪽 목록과 중앙 카드 자리를 유지하고, 모바일 상세는 화면 전체 너비·높이를 쓴다.
- Pass/Like는 탐색과 상세가 공유하는 **플로팅 원형 버튼**이다. 카드 하단에 여백을 두고 띄우며, 상세에서는 부드러운 페이드 위로 버튼이 떠 있다. 마지막 소개가 버튼 위까지 올라오도록 스크롤 끝 여백과 모바일 안전 영역을 확보한다. 상세에서 선택하면 기존 퇴장 애니메이션·중복 선택 방지·선택 저장을 거쳐 다음 인물로 이동한다. 상단 제목은 고정하고 사진·소개는 휠·터치로 읽는다. 클릭으로 접는 동작은 ↓ 버튼뿐이며 Escape도 지원한다. 바깥 영역·내용 클릭·드래그는 접지 않고 Tab은 페이지의 일반 탐색을 따른다.
- 좋아요 목록의 인물도 같은 중앙 영역에서 읽는다. 원래 탐색 카드와 사진 선택, 연락처 입력 폼·입력값은 상세를 읽는 동안 유지한다. 사이드바에서 다른 인물을 열어도 새 선택이 유지된다. 퇴장 중에는 사진·접기·목록·페이지 이동 컨트롤을 잠근다.
- 최신 플로팅·화살표 전용 동작은 실제 Chromium 1440×900·375×667에서 사진·이름 탭 무동작, 바깥 클릭 유지, ↑/↓·Escape, 고정 헤더·플로팅 버튼·마지막 소개의 읽기 여백과 Like를 확인했다. 전체 695개 테스트·140개 파일 및 파일별 커버리지 100%, `bun run ci:checks`와 `bun run verify-gates`를 통과했다. 변경한 탐색·카드·상세 3개 모듈의 400개 변이는 생존·미커버 0개다. 품질 임계값·예외 목록 변경 없이 임시 검증 설정을 제거했다.
- 카드 내 상세 전환은 실제 Chromium의 1440×900·375×667 화면에서 중앙 카드 위치·크기 유지, 모바일 전체 너비, 고정 제목·하단 버튼, 사진 보존·바깥 클릭·Escape·키보드 스크롤·상세 Like를 검증했다. 전체 `bun run ci:checks`의 693개 테스트·140개 파일과 파일별 커버리지 100%, 빌드·정적 검사 및 `bun run verify-gates`를 통과했다. 수정한 탐색·카드·목록·상세 4개 모듈의 497개 변이는 생존·미커버 0개, mutation score 100%다. 임시 검증 설정은 제거했다.
- 앞선 큐·모달 단계에서는 실제 Chromium의 데스크톱 1440×900·모바일 375×667에서 같은 인물의 복수 묶음 등록, 열린 프롬프트 보존, 순차 생성·실패 사진만 재시도, 공개 저장과 상세 모달의 사진 선택·키보드 스크롤·바깥 클릭·Escape·포커스 복원을 확인했다. `bun run ci:checks`의 687개 테스트·139개 파일과 파일별 커버리지 100%, 타입·lint·데드 코드·중복 코드·두 사이트 빌드, `bun run verify-gates`를 통과했다. 변경한 Admin/상세 모달 26개 런타임 모듈의 2,609개 변이는 생존·미커버 0개, mutation score 100%였다.

#### Discovery 연락처: iPhone 휴대전화 번호만

연락처 입력은 **iMessage를 쓰는 iPhone의 휴대전화 번호만** 받는다. Apple ID 이메일 입력과 한국 번호 전용 검증을 대체한다.

- 국가 번호 선택기(`🇰🇷 +82 ⌄`)는 플랫폼 기본 목록을 연다. 감지한 국가·한국·일본·미국을 먼저 두고 나머지 국가를 화면 언어의 이름 순으로 나열한다. 기본 국가는 기기 시간대 → 브라우저 언어의 지역 → 한국 순으로 정하며 네트워크 조회는 하지 않는다.
- 번호는 선택한 국가 형식으로 입력 중 서식을 맞춘다. 국가 번호가 포함된 번호를 자동 완성하거나 붙여 넣으면 국가가 바뀐다. 국가를 바꾸면 국내 형식으로 입력한 숫자는 새 국가의 번호로 다시 읽고, `+`로 시작한 번호는 이전 국가의 번호이므로 비운다.
- 오류는 번호를 입력한 뒤 입력란을 벗어나거나 등록 버튼을 누를 때만 표시한다. 전화 키패드에는 완료 키가 없으므로 번호 때문에 등록 버튼을 비활성화하지 않고, 누르면 오류를 알린다.
- 휴대전화 번호만 유효하다. 브라우저와 api-app이 `@ren-ai/onboarding`의 같은 `libphonenumber-js` 휴대전화 메타데이터로 검증하고 E.164(`+821012345678`)로 저장한다. 미국·캐나다처럼 유선·휴대 번호 형식이 같은 국가는 유효한 번호를 모두 받는다. 새로 개통된 번호 대역은 라이브러리 갱신 전까지 거부될 수 있다.
- 새 대기 등록 후 지속 백그라운드 작업에서 Apple IDS로 iMessage 수신 대상을 조회한다. 확인 자체는 메시지를 보내지 않는다. 결과(사용 가능·미지원·확인 실패)와 확인 시각을 API SQLite에 기록하고 Admin 목록에 표시한다. 기존 미조회 등록은 미확인으로 표시한다. 미지원은 Android 판정이 아니다.
- iMessage 사용 가능으로 확인된 번호만 직접 선정·무작위 선정·테스트 즉시 시작의 대상이 된다. 미확인·확인 실패는 확인 전 선정 보류로 표시하며 등록과 Like를 보존한다. 미지원은 별도 사유로 제외하고 안내 메시지도 시도하지 않는다. 조회 실패와 미확인을 미지원으로 간주하지 않는다. 이 조회는 전달 보장이 아니므로, 실제 첫 연락에서 iMessage 수신 불가가 확인되는 경우의 기존 처리는 유지한다.
- 운영자 도구의 Handle 입력은 이메일과 한국 국내 형식·국제 형식의 전화번호를 받는다. 이전에 등록된 유선·070 번호도 삭제·차단할 수 있도록 휴대전화 번호로 제한하지 않는다. 기존 이메일 등록과 대화는 그대로 둔다.
- `/reset` 후 Discovery로 다시 등록하는 테스트 연락처는 이메일이 아닌 테스터의 iPhone 번호여야 한다.
- 개인정보 안내는 `discovery-2026-10-16`으로 갱신했다. API와 Discovery가 함께 배포되는 동안, 그리고 배포 전에 열어 둔 화면에서는 동의 버전이 맞지 않아 등록이 실패하며 새로고침하면 해결된다.

## 확정된 제품 규칙

### 현재 계약: 운영자 선정·정원 배정·지속 첫 연락 예약

- Admin의 대기자/첫 연락 화면이 인증된 메시징 관리 API를 호출한다. 대기 등록·선정·배정·예약의 원본은 API SQLite이며 Admin D1에 복사하지 않는다.
- handle은 현재 배정 하나, 페르소나는 다섯까지 가질 수 있다. 대기·실패·불확실 첫 연락과 테스트 handle도 포함하며 예약 트랜잭션에서 제한을 검사한다. 기존 Conversation과 배정은 전환 때 보존한다.
- N(1~100)명 실행은 무작위 사람 → 그 사람의 공개·정원 미달이며 그 handle과 종료한 적 없는 Like 후보 중 무작위 한 명 순서다. 후보 부족 시 실제 선정 수를 반환하며 확인 요청 ID의 재제출은 같은 결과를 반환한다. 테스트 즉시 시작에도 같은 정원·종료 제외를 적용한다.
- 운영자는 대기자 행을 체크해 직접 선정할 수도 있다. 선택한 등록만 기존 선정 흐름에 넣고, 배정 가능한 Like 페르소나 무작위 배정과 5분~1시간 예약은 동일하게 적용한다. 이미 사용 불가해진 선택 항목은 건너뛰되 선택하지 않은 사람으로 대체하지 않는다. 실패 시 선택한 등록 ID와 요청 ID를 유지해 같은 결과를 확인한다.
- 관계 종료는 해당 handle에만 영구적인 배정 제외다. 다른 사용자의 관계·배정·공개 프로필은 유지한다. Discovery는 정원에 찬 인물도 badge 없이 표시하고 토큰 기반 재선택 목록에서만 그 handle과 종료한 인물을 숨긴다. 전속 연결을 약속하는 섹션과 이미지는 제거한다.
- 첫 연락 예정 시각은 5분~1시간 범위에서 한 번 저장한다. 서버가 지속 예약을 읽어 세션과 Conversation을 만들고 페르소나 Greeting을 시작한다. 별도 서비스 Notice는 발송하지 않는다.
- 준비 중단·발송 불확실은 자동 재생성/재전송하지 않는다. 기존 세션·발송을 관찰하며 실패·연락처 수정 필요·결과 확인 필요·대화 시작을 구분한다. 실패한 배정은 유지하며 운영자 삭제나 테스트 Reset 때 해제한다.
- 초대, 연락처 수정 화면, 수동 첫 연락 복구 실행은 후속 작업이다. 관리 화면은 API 연결 실패를 빈 목록으로 표시하지 않으며 조회·선정·작업의 요청 ID를 제공한다.

1. 연락 채널은 iMessage다. iMessage를 쓰는 iPhone의 휴대전화 번호만 받고 Apple ID 이메일은 받지 않는다.
2. 카드 스와이프 또는 버튼으로 Like / Pass한다. 모든 카드를 볼 필요는 없다.
3. 한 명 이상 Like하면 언제든 **연락받기**로 진행할 수 있다.
4. Like는 즉시 매칭이 아니다. 실제로 연락하는 페르소나는 Like한 후보 중 한 명이다.
5. 사용자당 한 페르소나와만 관계를 시작한다. 다른 초대 링크나 중복 제출로 관계를 추가하지 않는다.
6. AI 서비스 안내와 필요한 동의는 웹사이트에서 처리한다. 새 대기 등록에는 `noti@renai.im`에서 안내 iMessage 한 건을 시도한다. 서비스 전체 시간당 30건을 초과하면 생략하며 재시도하지 않는다. 안내 실패는 선정 자격에 영향을 주지 않는다. 페르소나의 첫 인사는 `hi@renai.im`에서 보낸다.
7. 첫 iMessage는 선택된 페르소나가 자신의 말투로 보내는 인사다.
8. 초대 등록자는 등록 완료 후 5분~1시간 사이에 첫 연락을 시도하도록 예약한다.
9. 일반 방문자는 대기 등록한다. 운영자가 **N명 선정하기**를 실행하면 대상과 페르소나를 무작위 선택한다.
10. 일반 대기자도 선정 후 5분~1시간 사이에 첫 연락을 시도하도록 예약한다.
11. 대기자는 등록 순서대로 선정하지 않는다. 먼저 사람을 무작위 선택하고, 각 사람의 Like 목록에서 페르소나를 무작위 선택한다. Like 개수가 선정 확률을 높이지 않는다.
12. 주기적 자동 선정이나 하루 신규 연락 한도 대신 운영자의 N명 선정 실행으로 대기자 유입을 조절한다. 초대 등록은 이 실행을 기다리지 않는다.

- [x] 연락처 수정 필요 또는 선정 가능한 Like 후보가 없는 등록은 선정 대상에서 제외한다.
- [x] 반복 클릭·동시 실행·응답 유실 후 재시도로 같은 등록이 중복 선정되지 않게 한다.

### 첫 연락 상태와 운영 접근

- [x] 예약 목록에서 예정 시각·페르소나·연락처·전송 상태를 확인한다.
- [x] 수신 불가·일시적 실패·전송 결과 불확실을 구분해 표시한다.
- [x] 운영자만 Admin과 현재 페르소나 저장 경로에 접근할 수 있게 한다. 후속 관리 기능도 같은 인증 경계를 사용한다.
- [ ] 선정 실행과 페르소나 저장의 성공·실패 결과를 확인할 수 있게 한다.

### iMessage 수신 불가

현재 구현은 실제 전송 결과로 iMessage 수신 가능 여부를 판단한다. 연락처 형식 검증에 성공한 등록과 실제 전달 성공을 구분한다.

- [x] 메시지 없이 수신 가능 여부를 확인할 수 있는지 조사했다. SIP를 켠 Mac에서는 불가능하다. imsg 0.15.9의 `handles.check`와 BlueBubbles의 확인 API는 Messages에 주입하는 helper(SIP 해제)가 필요하고, AppleScript와 공개 프레임워크에는 해당 기능이 없다. 번호를 외부로 보내는 유료 조회 서비스(Loop Lookup·Sendblue 등)만 가능하다. Apple 기기를 흉내 내는 비공식 클라이언트(rustpush 등)는 Apple 계정 위험 때문에 쓰지 않는다. 등록 화면 안내와 첫 연락 결과로 처리한다.
- [ ] 수신 불가가 확인되면 연락처 수정 필요 상태로 전환한다.
- [ ] 이미 사용한 초대 링크를 다시 공개하지 않고 그 등록자의 초대 자격을 보존한다.
- [ ] 일반 대기자도 이미 선정된 자격을 보존한다.
- [ ] 연락처 수정 후 초대·선정 자격을 유지하며 첫 연락을 다시 예약한다.
- [ ] 연락처 수정 권한을 확인할 수 있는 등록 관리 경로를 설계한다.

## 현재 저장소와 연결할 작업

- `packages/discovery.hena.dev`: 삭제했다. 탐색과 등록은 `apps/discovery`가 맡는다(ADR-0015).
- `packages/onboarding`: Handle 검증과 요청·응답 형식을 재사용·확장한다. API가 별도로 배포되므로 신규 필드는 배포 전까지 선택적으로 두고 구 API의 응답도 처리한다.
- `apps/api/src/onboarding/onboarding.ts`: 고정 페르소나·즉시 Notice·Greeting 흐름과 함께 삭제했다. 테스트 연락처는 Admin에서 바로 시작한다.
- `apps/api/src/personas/personas.ts`: `packages/personas`의 공용 OpenCode 로더를 재사용한다. 런타임 실시간 반영이 필요해지면 별도 적용 정책을 정한다.
- `apps/api/src/database.ts`: 현재 이메일 기반 대기 리스트를 새 Handle·Like·상태 기반 등록과 어떻게 이관할지 결정해야 한다. 과거 항목에 없는 Like를 임의로 만들어 선정하지 않는다.
- `apps/api/src/follow-ups/follow-ups.ts`: 기존 대화의 후속 연락 기능이다. 새 첫 연락 예약과 역할을 구분해 연결한다.
- `apps/persona-lab`과 `packages/persona-engine`: 별도의 인물 모델 실험 도구다. 새 Admin과 서비스의 페르소나 기준은 OpenCode로 결정했다.
- 앱 추가·사이트 이동에 맞춰 워크스페이스, 타입 검사, 품질 게이트 대상, CI 빌드, 배포 경로와 API CORS를 갱신한다. 라이브러리는 기존 JIT 형태를 유지한다.

### 기존 문서와의 관계

이번 탐색·등록·첫 연락 흐름은 [기존 컴패니언 MVP](companion-mvp.md)의 사용자가 한 명을 직접 확정하는 진입 흐름을 대체한다. 이미지·관계 엔진·과금에 관한 기존 논의를 모두 새로 확정하는 문서는 아니다.

배정 정책은 **handle당 하나·페르소나당 최대 다섯 현재 배정**이다. 첫 연락 예약부터 세고 실패·불확실 상태에서도 유지한다. 테스트 handle도 포함한다. 공유 생활과 사적인 관계 경계는 ADR-0023을 따른다.

`CONTEXT.md`의 용어는 탐색 흐름 기준으로 갱신했고, 사이트 구성에 관한 ADR-0008은 ADR-0015로 대체했다. 서버 자체 저장소를 사용하는 ADR-0006과 대화별 도구·세션 경계를 다루는 ADR-0001·0002는 새 흐름에서도 검토 기준으로 삼는다.

## 구현 전 정할 세부 사항

제품 흐름을 다시 인터뷰하기 위한 목록이 아니라 구현 시 해소할 결정 목록이다. 추가 사용자 결정이 필요하면 question tool을 사용한다.

- [x] 사용자 사이트는 `apps/discovery`다. 기존 `discovery.hena.dev`와 `msg.hena.dev`는 리다이렉트 없이 종료한다. [기존 테스트 사이트 종료](../../apps/api/ops/README.md#retire-the-old-test-site) 순서를 따른다.
- [ ] Admin의 공개 도메인과 배포 방식.
- [x] 페르소나는 OpenCode Markdown + YAML frontmatter 형식으로 직렬화한다. 운영 이미지는 R2 HTTPS URL을 사용하고, 스타일별 메인과 독립 추가 사진을 선택적으로 기록한다. 로컬 개발은 `/images/`를 사용한다. 구 `portraitGallery`는 읽을 때 독립 사진으로 정규화한다.
- [x] Admin 편집 모델은 OpenCode로 정하고 기존 런타임과 로더를 공유한다. 현재 설정 변경은 API 재시작 후 반영한다.
- [ ] 새 첫 연락 예약과 진행 중 대화에서 설정 변경을 적용할 시점·정의 버전 정책.
- [x] handle당 하나·페르소나당 다섯 현재 배정으로 제한하며 예약과 테스트 시작에서 정원과 해당 handle의 종료 이력을 검사한다.
- [ ] 비공개 전환·후보 부재 시 기존 Like와 예약을 처리하는 정책. Like하지 않은 대체 페르소나를 임의로 배정하지 않는다.
- [x] 운영자 인증은 루프백 Admin의 비밀번호 인증으로 시작한다.
- [ ] 등록자의 상태 조회·연락처 수정 권한 확인 방식과 공개 배포 시 Admin 접근 경로.
- [ ] 수신 불가와 일시적 장애를 구분한 재예약·재시도·늦어진 예약 복구 정책.

## 권장 구현 순서

1. **기준 모델과 저장소**: Persona·등록·초대·선정·예약 모델, 마이그레이션, 공개/관리 API 경계를 만든다.
2. **Admin 페르소나 관리**: 생성·저장·수정·미리보기·공개를 구현하고 공개 목록과 런타임을 연결한다.
3. **사용자 탐색과 등록**: 스와이프·Like·연락처·웹 안내·동의·초대/대기 완료 화면을 구현한다.
4. **초대와 N명 선정**: 단일 사용, 대기자 초대 전환, 무작위 선정, 중복 방지, 운영 결과 화면을 연결한다.
5. **지연된 첫 연락과 복구**: 지속 예약·Greeting·전송 결과 확인·연락처 수정·자격 보존을 연결한다.
6. **배포와 종단 검증**: 앱 경로·CI·배포를 갱신하고 실제 iMessage 흐름을 확인한다.

## 완료 검증

- [ ] Admin에서 저장·공개한 페르소나가 사용자 카드와 실제 첫 연락에 연결된다.
- [x] 비공개 내부 설정은 공개 프로필 응답에 포함되지 않는다.
- [x] 몇 번만 스와이프한 뒤에도 Like가 있으면 등록할 수 있다.
