# 페르소나 탐색 웹사이트와 Admin — MVP 작업 스펙

상태: 제품 흐름은 확정, 화면·저장소·배포의 세부 설계는 아래 작업 목록과 미결정 항목으로 관리한다.

## 목표와 앱 구성

사용자가 틴더처럼 페르소나를 스와이프하고 Like하면, 그중 한 명이 나중에 iMessage로 먼저 연락한다. 운영자는 Admin에서 페르소나를 저장·관리하고, 초대 링크를 발급하며, 대기자 중 연락할 N명을 선정한다.

사용자 웹사이트는 기존 패키지를 `packages/discovery.hena.dev`로 이름을 바꾸고 `discovery.hena.dev`에 배포한다. Admin은 `apps/admin`에 둔다.

| 앱              | 경로                          | 역할                                                                           |
| --------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| 사용자 웹사이트 | `packages/discovery.hena.dev` | 페르소나 탐색, Like / Pass, 연락처 등록, 초대 적용, 등록 상태 확인·연락처 수정 |
| Admin           | `apps/admin`                  | 페르소나 저장·관리, 초대 링크 관리, 대기자 선정, 첫 연락 상태 확인             |

공개 페르소나 목록과 운영자 편집 화면은 같은 저장된 페르소나를 참조한다. 선정·초대 사용·발송 예약의 판단은 서버에서 수행하며, 두 웹 앱이 서로 다른 규칙을 구현하지 않는다.

### 1차 구현: Admin 페르소나 편집

- `apps/admin`에서 목록 → 생성/수정 → 저장 → 공개/비공개 흐름과 저장된 카드 미리보기를 제공한다.
- 인물 모델은 **OpenCode 기준**이다. 사용자 결정에 따라 Persona Engine 대신 프롬프트·언어·시간대·첫 인사 지침·기억 지침을 관리한다.
- `packages/personas`가 OpenCode Markdown 로더, 검증, 파일 저장, 공개 프로필 조회를 공유한다. 공개 프로필도 같은 Markdown의 YAML frontmatter에 저장하며 별도 메타데이터 DB를 두지 않는다.
- 공개 프로필 조회는 Admin 서버의 `GET /api/personas`로 제공한다. 반환 필드는 `id`, `name`, `bio`, `imageUrl`뿐이다. 사용자 사이트/API 배포 연결은 다음 단계에서 진행한다.
- 이미지는 첫 버전에서 HTTPS URL을 입력한다. 기존 파일에 공개 프로필 필드가 없으면 ID를 이름으로 표시하고 비공개 상태로 연다.
- 기존 iMessage API도 공용 로더를 사용한다. 같은 디렉터리를 지정하면 저장한 OpenCode 설정을 읽으며, 실행 중인 API에는 **재시작 후** 반영된다. 공개/비공개는 카드 노출 상태이며 기존 Conversation을 삭제하지 않는다.
- Admin은 어두운 중립색·고밀도 편집 화면으로 구성하고 네이티브 HTML 폼으로 저장한다. 브라우저 JavaScript와 별도 프런트엔드 빌드 없이 서버에서 HTML을 렌더링한다.

로컬 실행:

```sh
ADMIN_PASSWORD='<운영자 비밀번호>' bun run --cwd apps/admin dev
```

`http://127.0.0.1:3729`에 접속해 사용자 이름 `admin`과 설정한 비밀번호로 로그인한다. 포트는 `PORT`로 변경할 수 있다. 기본 저장 위치는 `apps/admin/data/personas`다. 실제 iMessage API와 같은 파일을 관리하려면 `PERSONA_DIRECTORY`에 API가 사용하는 절대 경로를 지정한다. 설정 예시는 `apps/admin/.env.example`에 있다.

Admin과 저장 API에는 비밀번호 인증과 동일 출처 폼 제출 검사를 적용한다. 공개 프로필 조회에는 인증이 필요하지 않다. 테스트·품질 검사는 저장소의 `.nvmrc`에 맞춰 **Node 24**에서 실행한다.

검증 결과:

- 전체 테스트와 파일별 커버리지 100%, `bun run ci:checks`, `bun run verify-gates`를 통과했다.
- 신규 Admin·공용 저장소의 변이를 모두 검출했고, 저장소 전체 변이 검사도 CI와 같은 `STRYKER_SHARD=1/4`부터 `4/4`까지 모두 100%로 통과했다. 단일 `bun run ci` 실행은 로컬 한 시간 제한에 걸려 변이 단계를 4개 shard로 나누어 완료했다.
- 실제 Bun 서버에서 인증·생성·저장 후 조회를 확인하고 Chromium으로 데스크톱·모바일 화면을 검토했다.
- Standards / Spec 코드 리뷰는 각각 지적 사항 0개였다.
- Mac의 대소문자 비구분 파일 시스템에서도 다른 대소문자의 ID로 기존 페르소나를 조회·수정하지 못하도록 실제 파일 이름과 일치하는 ID만 허용한다. 파일이 조회 도중 사라지면 기존과 동일하게 찾을 수 없음으로 처리한다.

다음 구현 단위는 `packages/discovery.hena.dev`의 공개 프로필 조회·카드 스와이프·Like / Pass 화면이다. 연락처 등록, 초대, 대기자 선정과 첫 연락 예약은 그다음 단위에서 연결한다.

## 확정된 제품 규칙

1. 연락 채널은 iMessage다. 전화번호를 기본 입력으로 받고 Apple ID 이메일도 허용한다.
2. 카드 스와이프 또는 버튼으로 Like / Pass한다. 모든 카드를 볼 필요는 없다.
3. 한 명 이상 Like하면 언제든 **연락받기**로 진행할 수 있다.
4. Like는 즉시 매칭이 아니다. 실제로 연락하는 페르소나는 Like한 후보 중 한 명이다.
5. 사용자당 한 페르소나와만 관계를 시작한다. 다른 초대 링크나 중복 제출로 관계를 추가하지 않는다.
6. AI 서비스 안내와 필요한 동의는 웹사이트에서 처리한다. 별도의 서비스 안내 iMessage는 보내지 않는다.
7. 첫 iMessage는 선택된 페르소나가 자신의 말투로 보내는 인사다.
8. 초대 등록자는 등록 완료 후 5분~1시간 사이에 첫 연락을 시도하도록 예약한다.
9. 일반 방문자는 대기 등록한다. 운영자가 **N명 선정하기**를 실행하면 대상과 페르소나를 무작위 선택한다.
10. 일반 대기자도 선정 후 5분~1시간 사이에 첫 연락을 시도하도록 예약한다.
11. 대기자는 등록 순서대로 선정하지 않는다. 먼저 사람을 무작위 선택하고, 각 사람의 Like 목록에서 페르소나를 무작위 선택한다. Like 개수가 선정 확률을 높이지 않는다.
12. 주기적 자동 선정이나 하루 신규 연락 한도 대신 운영자의 N명 선정 실행으로 대기자 유입을 조절한다. 초대 등록은 이 실행을 기다리지 않는다.

## 사용자 웹사이트 작업

### 페르소나 탐색

- [ ] 모바일 중심의 틴더 스타일 카드 탐색 화면을 만든다.
- [ ] 공개된 페르소나의 프로필을 서버에서 가져온다.
- [ ] 사진·이름·짧은 소개를 카드 구성의 기본안으로 삼아 디자인한다.
- [ ] Like / Pass 스와이프와 동일 기능의 버튼을 제공한다.
- [ ] 탐색 중 Like 목록을 유지하고 연락처 제출 시 함께 저장한다.
- [ ] Like가 한 명 이상이면 연락받기 버튼으로 등록을 진행할 수 있게 한다.
- [ ] 카드가 없거나 모두 탐색한 경우에도 기존 Like가 있으면 등록할 수 있게 한다.
- [ ] 로딩, 목록 조회 실패, 공개된 페르소나 없음, Like 없음 상태를 처리한다.

### 연락처 등록과 초대

- [ ] 전화번호 정규화·검증과 Apple ID 이메일 입력을 지원한다.
- [ ] 웹에서 AI 서비스 안내와 동의를 받으며 동의 버전·언어·시각을 보관한다.
- [ ] 초대 링크로 방문하면 등록 과정까지 초대 정보를 유지한다.
- [ ] 유효한 초대가 있으면 첫 연락 예약, 없거나 사용된 초대면 대기 등록으로 처리한다.
- [ ] 제출 중·실패·재시도 상태를 표시하고 중복 요청을 서버에서도 처리한다.
- [ ] 이미 등록된 연락처는 기존 등록·예약·관계를 재사용한다.

### 완료 안내와 등록 관리

- [ ] 초대 등록 완료 화면에서 Like한 페르소나 중 한 명에게 연락받을 예정임을 안내한다.
- [ ] 대기 등록 완료 화면에 다음 취지의 안내를 표시한다.

> 대기 등록이 완료됐어요.
> 준비되는 대로, 좋아한 페르소나 중 한 명이 연락할 거예요.

- [ ] 대기 등록 화면에서 등록 순서나 짧은 대기 시간을 약속하지 않는다.
- [ ] 대기 중·첫 연락 예정·대화 시작·연락처 수정 필요 상태를 확인할 수 있게 한다.
- [ ] 대기 중인 사람이 같은 연락처로 초대를 적용하면 기존 Like를 유지하며 첫 연락 예정으로 전환한다.
- [ ] 이미 예약되었거나 대화 중이면 기존 상태를 유지하고 새 초대 링크를 소진하지 않는다.
- [ ] 수신 불가 시 다른 전화번호 또는 Apple ID 이메일로 연락처를 수정할 수 있게 한다.
- [ ] 연락처 수정이 같은 등록의 초대·선정 자격과 연결되도록 한다.

## Admin 작업

### 페르소나 저장·관리

운영자가 코드를 수정하지 않고 페르소나를 만들고 저장하며, 사용자에게 보여줄 프로필과 실제 대화 설정을 함께 관리할 수 있어야 한다. 목록만 보여주는 관리 화면으로 끝내지 않는다.

- [x] 페르소나 목록·생성·상세·수정 화면을 만든다.
- [x] 저장한 페르소나가 새로고침·서버 재시작 후에도 유지되게 한다.
- [x] 이름·프로필 이미지·짧은 소개 등 공개 프로필 필드를 편집한다.
- [x] OpenCode 프롬프트·언어·시간대·첫 인사 지침·기억 지침을 편집한다. 말투와 대사 예시는 프롬프트에 작성한다.
- [x] 공개 프로필과 내부 프롬프트 등 비공개 설정을 구분한다. 공개 API에는 공개용 필드만 반환한다.
- [x] 필수 필드·시간대·HTTPS 이미지 URL을 검증하고 저장 실패를 표시한다.
- [x] 초안 저장과 공개·비공개 전환을 지원한다.
- [x] 사용자 웹에서 보일 저장된 카드 미리보기를 제공한다.
- [x] 공개 프로필 API에서 공개된 페르소나만 반환한다. 사용자 웹 연결은 탐색 단계에서 진행한다.
- [ ] 비공개 전환 시 기존 Like·발송 예약·진행 중 대화를 어떻게 처리할지 결정하고 적용한다.
- [ ] 참조 중인 페르소나를 관리 작업으로 제거하더라도 기존 등록과 대화의 참조가 깨지지 않게 한다.
- [x] 기존 파일 기반 페르소나를 같은 디렉터리에서 그대로 열고 저장하도록 한다.
- [x] Admin과 기존 iMessage 런타임이 공용 OpenCode 로더를 사용하게 한다. 변경은 API 재시작 후 반영된다.

### 초대 링크 관리

- [ ] 초대 링크를 생성하고 복사할 수 있게 한다.
- [ ] 미사용·사용됨 상태와 사용 시각·연결된 등록을 확인한다.
- [ ] 링크 하나당 한 명만 성공적으로 초대 등록할 수 있게 한다.
- [ ] 등록 저장·초대 사용·첫 연락 예약을 일관되게 완료하도록 서버 처리를 만든다.
- [ ] 수신 불가로 실패한 등록에서도 해당 등록자의 초대 자격을 확인할 수 있게 한다.

### 대기 리스트와 N명 선정

- [ ] 대기자 목록에서 연락처·등록 시각·Like한 페르소나·현재 상태를 확인한다.
- [ ] 선정 가능한 대기자 수를 표시한다.
- [ ] 양의 정수 N을 입력하고 **N명 선정하기**를 실행할 수 있게 한다.
- [ ] 실행 결과에 요청 인원·실제 선정 인원·선택된 페르소나·첫 연락 예약 시각을 표시한다.
- [ ] 선정 가능한 인원이 N보다 적으면 가능한 인원만 선정한다.
- [ ] 이미 예약되었거나 대화가 시작된 등록은 다시 선정하지 않는다.
- [ ] 연락처 수정 필요 또는 선정 가능한 Like 후보가 없는 등록은 선정 대상에서 제외한다.
- [ ] 반복 클릭·동시 실행·응답 유실 후 재시도로 같은 등록이 중복 선정되지 않게 한다.

### 첫 연락 상태와 운영 접근

- [ ] 예약 목록에서 예정 시각·페르소나·연락처·전송 상태를 확인한다.
- [ ] 수신 불가·일시적 실패·전송 결과 불확실을 구분해 표시한다.
- [x] 운영자만 Admin과 현재 페르소나 저장 경로에 접근할 수 있게 한다. 후속 관리 기능도 같은 인증 경계를 사용한다.
- [ ] 선정 실행과 페르소나 저장의 성공·실패 결과를 확인할 수 있게 한다.

| 선정         | 등록, 페르소나, 선정 시각, 초대 또는 운영자 선정 경로                                    |
| 첫 연락 예약 | 등록·페르소나 참조, 예정 시각, 전송 상태·시도 결과                                       |
| Conversation | 등록·사용자와 한 페르소나의 기존 대화 연결                                               |

### 기능

- [ ] 공개 프로필 조회, 연락처 등록, 초대 적용, 등록 상태 조회·연락처 수정 API를 만든다.
- [ ] 페르소나 저장·관리, 초대 생성·조회, 대기자 조회·선정, 예약 조회 API를 만든다.
- [ ] 연락처 변경 시 기존 등록과 관계를 유지하고 다른 기존 등록과의 충돌을 처리한다.
- [ ] 초대 사용과 N명 선정의 중복·경쟁 처리를 서버와 저장소에서 보장한다.
- [ ] 5분~1시간 구간의 첫 연락 예정 시각을 한 번 결정해 저장한다.
- [ ] 예약을 지속 저장하고 서버 재시작 후에도 이어서 처리한다.
- [ ] 예약된 첫 연락에서 별도의 서비스 Notice를 보내지 않고 Persona Greeting을 시작한다.
- [ ] 성공한 첫 연락을 이후 Conversation과 연결한다.
- [ ] 전송 결과가 불확실하면 실제 결과를 확인하기 전 중복 재전송하지 않는다.
- [ ] 기존 차단·삭제 요청 상태를 존중해 연락하지 않아야 할 대상에게 발송하지 않는다.

### iMessage 수신 불가

현재 구현은 실제 전송 결과로 iMessage 수신 가능 여부를 판단한다. 연락처 형식 검증에 성공한 등록과 실제 전달 성공을 구분한다.

- [ ] 메시지 없이 수신 가능 여부를 확인할 수 있는지 구현 전에 조사한다.
- [ ] 수신 불가가 확인되면 연락처 수정 필요 상태로 전환한다.
- [ ] 이미 사용한 초대 링크를 다시 공개하지 않고 그 등록자의 초대 자격을 보존한다.
- [ ] 일반 대기자도 이미 선정된 자격을 보존한다.
- [ ] 연락처 수정 후 초대·선정 자격을 유지하며 첫 연락을 다시 예약한다.
- [ ] 연락처 수정 권한을 확인할 수 있는 등록 관리 경로를 설계한다.

## 현재 저장소와 연결할 작업

- `packages/discovery.hena.dev`: 현재 단일 연락처 등록 사이트다. 도메인 전환 후 기존 `msg.hena.dev`는 리다이렉트 없이 종료한다. 탐색 기능은 이 패키지에 확장한다.
- `packages/onboarding`: Handle 검증과 요청·응답 형식을 재사용·확장한다. API가 별도로 배포되므로 신규 필드는 배포 전까지 선택적으로 두고 구 API의 응답도 처리한다.
- `packages/api-msg.hena.dev/src/onboarding/onboarding.ts`: 현재 고정 페르소나·즉시 Notice·Greeting 흐름을 새 등록·선정·예약 흐름으로 변경해야 한다.
- `packages/api-msg.hena.dev/src/personas/personas.ts`: `packages/personas`의 공용 OpenCode 로더를 재사용한다. 런타임 실시간 반영이 필요해지면 별도 적용 정책을 정한다.
- `packages/api-msg.hena.dev/src/database.ts`: 현재 이메일 기반 대기 리스트를 새 Handle·Like·상태 기반 등록과 어떻게 이관할지 결정해야 한다. 과거 항목에 없는 Like를 임의로 만들어 선정하지 않는다.
- `packages/api-msg.hena.dev/src/follow-ups/follow-ups.ts`: 기존 대화의 후속 연락 기능이다. 새 첫 연락 예약과 역할을 구분해 연결한다.
- `apps/persona-lab`과 `packages/persona-engine`: 별도의 인물 모델 실험 도구다. 새 Admin과 서비스의 페르소나 기준은 OpenCode로 결정했다.
- 앱 추가·사이트 이동에 맞춰 워크스페이스, 타입 검사, 품질 게이트 대상, CI 빌드, 배포 경로와 API CORS를 갱신한다. 라이브러리는 기존 JIT 형태를 유지한다.

### 기존 문서와의 관계

이번 탐색·등록·첫 연락 흐름은 [기존 컴패니언 MVP](companion-mvp.md)의 사용자가 한 명을 직접 확정하는 진입 흐름을 대체한다. 이미지·관계 엔진·과금에 관한 기존 논의를 모두 새로 확정하는 문서는 아니다.

기존 MVP에는 한 페르소나를 한 사용자에게 전속 배정하는 정책도 있다. 이번에 확정한 것은 **사용자당 한 페르소나**이며, **페르소나당 한 사용자** 여부는 아래 미결정 항목으로 남긴다. 선정 가능 조건에 영향을 주므로 구현 전에 정해야 한다.

`CONTEXT.md`의 Onboarding·Greeting·Waitlist·Notice 정의와 사이트 구성에 관한 ADR-0008은 기존 흐름을 설명한다. 실제 전환 시 용어와 배포 결정을 함께 갱신한다. 서버 자체 저장소를 사용하는 ADR-0006과 대화별 도구·세션 경계를 다루는 ADR-0001·0002는 새 흐름에서도 검토 기준으로 삼는다.

## 구현 전 정할 세부 사항

제품 흐름을 다시 인터뷰하기 위한 목록이 아니라 구현 시 해소할 결정 목록이다. 추가 사용자 결정이 필요하면 question tool을 사용한다.

- [x] 사용자 사이트는 `packages/discovery.hena.dev`, 도메인은 `discovery.hena.dev`로 정한다. 새 사이트 검증 후 기존 `msg.hena.dev`는 리다이렉트 없이 종료한다. [배포 순서](../../packages/api-msg.hena.dev/ops/README.md#discovery-domain-cutover)를 따른다.
- [ ] Admin의 공개 도메인과 배포 방식.
- [x] 페르소나 저장은 OpenCode Markdown + YAML frontmatter 단일 파일로 관리한다. 이미지는 HTTPS URL을 사용한다.
- [x] Admin 편집 모델은 OpenCode로 정하고 기존 런타임과 로더를 공유한다. 현재 설정 변경은 API 재시작 후 반영한다.
- [ ] 새 첫 연락 예약과 진행 중 대화에서 설정 변경을 적용할 시점·정의 버전 정책.
- [ ] 페르소나당 동시 사용자 제한 여부. 제한이 있으면 초대 등록과 N명 선정 모두 후보 가용성을 검사해야 한다.
- [ ] 비공개 전환·후보 부재 시 기존 Like와 예약을 처리하는 정책. Like하지 않은 대체 페르소나를 임의로 배정하지 않는다.
- [x] 운영자 인증은 루프백 Admin의 비밀번호 인증으로 시작한다.
- [ ] 등록자의 상태 조회·연락처 수정 권한 확인 방식과 공개 배포 시 Admin 접근 경로.
- [ ] 수신 불가와 일시적 장애를 구분한 재예약·재시도·늦어진 예약 복구 정책.

## 권장 구현 순서

1. **기준 모델과 저장소**: Persona·등록·초대·선정·예약 모델, 마이그레이션, 공개/관리 API 경계를 만든다.
2. **Admin 페르소나 관리**: 생성·저장·수정·미리보기·공개를 구현하고 공개 목록과 런타임을 연결한다.
3. **사용자 탐색과 등록**: 스와이프·Like·연락처·웹 안내·동의·초대/대기 완료 화면을 구현한다.
4. **초대와 N명 선정**: 단일 사용, 대기자 초대 전환, 무작위 선정, 중복 방지, 운영 결과 화면을 연결한다.
5. **지연된 첫 연락과 복구**: 지속 예약·Greeting·전송 결과 확인·연락처 수정·자격 보존을 연결한다.
6. **배포와 종단 검증**: 앱 경로·CI·배포를 갱신하고 실제 iMessage 흐름을 확인한다.

## 완료 검증

- [ ] Admin에서 저장·공개한 페르소나가 사용자 카드와 실제 첫 연락에 연결된다.
- [x] 비공개 내부 설정은 공개 프로필 응답에 포함되지 않는다.
- [ ] 몇 번만 스와이프한 뒤에도 Like가 있으면 등록할 수 있다.
- [ ] 초대 링크 하나를 동시에 사용해도 한 명만 초대 등록에 성공한다.
- [ ] 등록 직후 iMessage가 발송되지 않고, 예약 시점의 첫 메시지는 페르소나의 인사다.
- [ ] 초대 등록은 운영자 선정 없이 예약되고 일반 등록은 대기 상태로 남는다.
- [ ] N명 선정은 실제 가능한 인원만 무작위 선정하며 중복 선정하지 않는다.
- [ ] 대기자가 나중에 초대를 사용하면 기존 등록과 Like를 유지해 예약으로 전환된다.
- [ ] 이미 예약·대화 중인 사람이 새 초대를 사용해도 링크가 소진되거나 관계가 추가되지 않는다.
- [ ] 수신 불가 후 연락처를 수정해도 초대·선정 자격이 유지된다.
- [ ] 서버 재시작·요청 재시도·전송 결과 불확실 상황에서도 예약과 관계가 중복 생성되지 않는다.
- [ ] 사이트/API의 단계적 배포 중 구 API 응답을 처리하며 기존 대화를 유지한다.
- [ ] 새 앱과 변경 모듈이 저장소 품질 게이트에 포함되고 `bun run ci`를 통과한다.
