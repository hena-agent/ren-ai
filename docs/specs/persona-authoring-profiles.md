# persona.md: 단일 Markdown 원본과 공개 자기표현

상태: 구현. 단일 Markdown 원본에 실시간 공개 프리뷰와 반복 가능한 페르소나 개선을 연결한다.

## 원본과 추출

기본 설명에서 **Persona Markdown·초기 State·초기 Memory**를 한 생성 요청으로 만든다.
생성 응답은 `{ persona, state, memory }` JSON이며, `persona`는 인물 설정과 본인이 쓴
공개 프로필을 포함한 Markdown 원문, `state`는 컨디션 5개와 초기 호감도 `affection`의 정수, `memory`는 생활
기억 Markdown이다. 숨겨진 특성 이름·강도는 Persona에서 가져와 STATE.md를 구성한다.
세 문서를 함께 검수하고 필요할 때 한 번만 보정·재검수한다. 정상 생성·검수는 총 2회다.

Persona Markdown 본문은 D1 버전 이력의 유일한 작성 원본이다. 현재 Persona는 최신 버전을 연결해 읽는다. ID와 이름·성별·공개 상태·언어/시간대·런타임 지침은
관리 컬럼에, 사진 연결은 별도 관계 테이블에 둔다. 디자이너의 인증된 `persona.md` 내려받기는
관리 메타데이터를 frontmatter로 직렬화한 뷰다. `description`, `bio`, `profile-details` 사본은 저장하지 않는다.
초기 State·Memory는 별도 D1 텍스트 컬럼이다. 비공개 Catalog가 이를 iMessage에 전달하며,
새 Conversation 폴더에만 `STATE.md`·`MEMORY.md`로 설치한다. 기존 문서는 Catalog 수정으로 초기화하지 않는다.

- 내부 대화 설정은 전체 본문에서 읽는다.
- `## 공개 프로필` 앞은 비공개 인물 설정, 뒤는 공개 자기표현이다.
- API의 `bio`는 공개 영역의 첫 자기소개 문단을 plain text로 추출한 값이다.
- 선택적 `profile`은 서버가 공개 영역에서 추출한 구조화된 JSON이다. 공개 Markdown
  문자열(`publicProfile`)·전체 원본·내부 설정은 공개 응답에 넣지 않는다.
- 공개 경계는 정확히 한 번이고 마지막 최상위 영역이어야 한다. 내부 공개 제목은
  `###`부터 사용한다. AST로 경계를 확인하며 코드 블록 속 가짜 제목은 경계가 아니다.

## Persona 문서 버전과 복원

- 저장한 Persona 문서만 불변 버전으로 보관한다. 비공개 인물 설정과 공개 프로필을 함께
  담되 사진·공통 초기 State/Memory·실제 Conversation의 상태와 기억은 버전에 포함하지 않는다.
- 첫 저장은 v1이다. 문서가 달라진 저장은 번호를 하나 늘리고 저장 시각을 남긴다.
  동일 문서 재저장과 사진·초기값·관리 정보만 바꾼 저장은 문서 버전을 늘리지 않는다.
  줄바꿈 방식과 본문 앞뒤 공백만 다른 입력은 같은 문서로 취급하고 기존 원문을 유지한다.
- 과거 버전 복원은 그 원문을 담은 새 최신 버전이다. v1 → v2 → v1 복원은 v3이며
  `restoredFrom: 1`을 기록한다. 이력을 지우거나 현재 번호를 뒤로 돌리지 않는다.
- 복원은 Persona ID·현재 사진·공개 상태·초기값을 유지한다. 이름·성별은 복원한 문서에서
  읽어 관리 정보와 일치시킨다. 공개 저장 조건과 현재 State의 특성 일치를 검사하고,
  불일치하면 내용을 안내하며 어떤 데이터도 변경하지 않는다. 자동 생성은 호출하지 않는다.
- D1은 `persona_versions`에 원문을 저장하고 `personas.currentVersion`으로 최신 원문을
  연결한다. 이력 추가·현재 버전 전환·관리 정보/사진 저장은 기존 revision CAS와 같은
  원자적 batch에서 실행한다. 실패한 저장은 이력도 추가하지 않는다.
- 기존 D1 문서는 `0001_persona_versions.sql` 적용 시 현재 원문을 v1으로 보관한다.
  기존 사진·초기값·관리 revision·시간은 유지한다. 도입 이전에 덮어쓴 원문은 복원하지 않는다.
- Admin은 현재 버전과 버전 기록을 제공한다. 저장 시각·복원 출처·현재/선택 원문 비교를
  읽고 확인한 POST로 복원한다. 미저장 문서·초기값·사진 미리보기와 실행/대기 작업이 있으면
  기록 이동·복원을 거부하고 편집본을 보존한다. 이력 원문과 복원 출처는 공개 응답에 넣지 않는다.
- 편집 원본과 private Catalog의 직렬화된 메타데이터에 `version`을 포함한다. 원문이
  같아지는 복원 후에도 예전 편집 화면의 덮어쓰기를 막으며 프롬프트 본문에는 번호를 넣지 않는다.
- Catalog는 최신 버전 하나만 공급한다. 세션별 `persona.json`에 적용 버전을 기록하고
  낮은 번호로의 덮어쓰기는 거부한다. 현재 응답을 중단하거나 세션을 재생성하지 않는다.
- 동기화는 OpenCode의 실제 agent 목록에서 현재 지침을 읽는 것까지 확인한 뒤 새 입력을
  처리한다. 파일 감시/캐시 갱신을 최대 5초 기다리고 실패하면 다음 heartbeat에서 재시도한다.
  Catalog 갱신은 admission과 같은 lifecycle 잠금 안에서 실행한다. 이 과정에서 기존
  State/Memory·실행 기록과 보존된 과거 세션은 바꾸지 않는다.
- 버전 조회·저장·복원의 실패는 기존 요청 ID·단계·원인/코드로 진단한다. 적용 성공에는
  Persona ID·버전·소요 시간을 기록하며 원문·프롬프트·기억 내용은 로그에서 제외한다.

## 공개 내용 선택

**짧아도 자기소개는 필수**다. 공개 영역은 자기소개 문단으로 시작한다. 그 외에는
관심사·생활 방식·관계 스타일·문답·직업 등 정해진 필수 항목이나 개수가 없다.
Persona가 자신이 실제 프로필에 올릴 제목·글·목록·문답을 선택한다.

자동 생성은 짧은 자기소개로 끝내지 않고 생활·취향·관계 기대를 구체적으로 알 수 있는
항목을 선택한다. 모든 항목이나 고정 개수를 강제하지 않고 의도적인 비공개 선택은 유지한다.
공개 항목의 저장 표현은 다음과 같다. 별도 필드 사본은 저장하지 않는다.

- `### 기본 정보`, `### 라이프스타일`, `### 관계 스타일`: 자유로운 문장 또는
  `- 직업: 도예가` 같은 정보 목록. 공개 기본 정보에 나이·생년월일을 작성하지 않는다.
  기본 정보에서는 직업·지역 등 다른 공개 사실만 다룬다. 목록을 구조화해 표시하려면 정보 이름과 내용을
  비우거나 같은 섹션에서 이름을 중복하지 않는다. 그 외 표현도 일반 글로 저장·표시한다.
- `### 관심사`: 자유로운 문장 또는 `- 재즈`처럼 한 줄에 하나인 태그 목록.
- `### 문답: 완벽한 일요일은?`: 질문을 제목에, 답변을 본문에 작성하며 여러 문답을 허용한다.
- 자유 항목: 원하는 `### 제목`과 Markdown 본문. 알 수 없는 제목과 기존 글도 보존한다.

예를 들어 내부에 사진 취미가 있어도 처음 보는 사람에게 취미를 공개하지 않는
인물이면 공개 프로필에 관심사 섹션이 없어도 정상이다. 부재를 누락으로 진단하거나
검수·재시도 때 채우지 않는다. 제목을 바꾸거나 새 섹션을 추가할 수도 있다.

```markdown
## 공개 프로필

천천히 알아가는 쪽이 편해요. 답장이 조금 느려도 괜찮은 분이면 좋겠어요.

### 내가 편해지는 순간

서로 말을 많이 하지 않아도 어색하지 않을 때요.
```

내부 Stat·숨겨진 특성·생성 지침·검수 보고서·상대와의 기억은 공개하지 않는다.
[Persona Engine](persona-engine.md)의 기본 성향과 말투·숨겨진 면의 구분은 유지한다.
[상태·기억 설계](persona-state-memory.md)의 실제 상태와 기억은 런타임의 책임이다.

## 생성과 그림

기본 설명 → Persona·State·Memory 동시 생성 → 구조/범위/이름·성별 확인 → 함께 의미 검수
→ 필요한 경우 한 번 보정·재검수 → 세 문서 탭에 초안 반영 순서다.

비공개 생성 영역은 기존 인물 설정·성격·말투·기본 성향 6개와 근거·숨겨진 특성
형식을 사용한다. 공개 영역은 고정 필드 모델이 아니라 자유로운 Markdown이다.
이름·성별·원본의 명시 사실과 수치를 보존하고 낮은 수치를 결함으로 표현하지 않는다.
성공한 캐릭터 초안에는 공개 프로필도 이미 들어 있다. 사진 생성에서 소개·관심사를
따로 생성하지 않는다. 아직 완성되지 않은 기본 설명은 사진 호출 전에 문서 전체를
완성해야 한다. 유료 이미지는 기존 옵션 확인·개별 프롬프트·FIFO 큐로 생성한다.

포맷 오류는 성공한 초안으로 취급하지 않고 이전 입력과 결과를 보존한다. 실패에는
요청 ID·단계·모델·원인/코드·stack frame·소요 시간을 남기며 원본/프롬프트/검수
payload는 진단에서 제외한다. 모델 JSON은 생성 묶음과 검수 결과의 검증된 전달 형식이다.
State 또는 Memory만 다시 생성할 때는 현재 편집 중인 Persona의 비공개 영역만 입력하고
해당 문서만 출력하는 요청 1회를 사용한다. 공개 글·사진·다른 초기 문서는 보내지 않는다.
개별 재생성은 Persona·다른 문서·사진을 유지하고, 실패하면 기존 입력을 보존한다.

## 디자이너 화면

- **Persona / State / Memory** 탭에서 각 원문을 CodeMirror로 편집한다. Persona 공개
  영역은 같은 원문에서 수정·추가·삭제하고 상단 저장 버튼 한 번으로 세 문서를 반영한다.
- 공개 프로필도 Persona Markdown 초안 한 곳에서 편집한다. 항목별 입력 폼은 두지 않는다.
  `공개 프로필로 이동`은 코드 블록 밖의 실제 공개 제목을 선택하고 에디터로 이동한다.
  `?` 도움말 모달은 공개 범위·필수 자기소개와 기본 정보·관심사·라이프스타일·관계 스타일·
  문답·자유 항목의 Markdown 예시를 보여준다. 도움말 예시는 초안에 자동 삽입하지 않는다.
- 내부 문서의 읽기용 프리뷰와 **편집 / 미리보기** 토글은 제거한다. 탭 전환은 입력·
  커서·실행 취소 이력을 유지하며 저장 후에도 선택한 탭으로 돌아온다.
- 오른쪽에는 현재 이름·사진·공개 프로필 전체를 실제 사용자용 카드처럼 표시한다.
  스타일 전환과 사진 넘김을 제공하고 편집·이미지 큐 결과를 즉시 반영한다. 공개 경계가
  잘못되면 공개 영역 오류를 표시하며 비공개 원문을 대신 표시하지 않는다.
- 문법 강조·줄 번호·실행 취소/다시 실행을 제공한다. 원문 입력은 즉시 기존 저장 폼에
  동기화하고, 입력 후 250ms에 프리뷰와 진단을 갱신한다.
- 문서 탭은 동일 너비의 평평한 3개 영역으로 표시하고, 선택 표시는 해당 영역의 하단
  직선으로만 구분한다. 공통 버튼의 모서리·여백 스타일이 탭에 섞이지 않도록 분리한다.
- State도 Persona와 같은 방식으로 입력 중 검증한다. YAML 문법·중복/누락/추가 필드,
  컨디션 5개·affection·강도의 정수 0–100, active의 불리언, persistence의 lasting, Persona 특성
  이름·강도 일치를 검사한다. 모든 필드 오류를 실제 YAML 범위에 표시하고 오류를 누르면
  State 탭의 해당 행을 선택한다. 수정하면 표시를 지우며 공개 준비 상태도 즉시 갱신한다.
  공용 Effect 스키마와 YAML AST 위치 정보를 사용하고 파싱 경고에 입력 내용을 남기지 않는다.
- 실제 오류 범위를 밑줄과 설명으로 표시하고 오류 메시지를 누르면 그 범위를 선택해
  이동한다. Stat 오류는 잘못된 실제 행, 중복 경계는 중복된 실제 제목을 가리킨다.
  없는 섹션마다 1행 오류를 만들거나 문서 전체 테두리를 빨갛게 표시하지 않는다.
- 서버 렌더와 형식 검사 모두 실제 문서 내용으로 판정한다. 정상 문서는 버전 표시가
  없거나 오래됐어도 정상이다. 페르소나 개선은 형식 상태와 관계없이 실행할 수 있다.
- 상단에 이름·변경 상태·공개 설정·저장을 함께 표시하고 사진 작업은 옆에 둔다.
- 데스크톱과 모바일 모두 버튼은 최소 44px 높이와 14px 글자 크기를 사용한다.
  보강한 내용이 있는 변환 결과만 표시하며 원문 사본과 보강 0개 보고서는 제거한다.
- 이름·성별·비공개 설정·공개 글을 바꿔도 기존 사진을 유지한 채 저장한다. 사진
  생성·추가·재생성은 별도의 운영자 선택이며 원문 변경으로 저장이나 사진 동작을 막지 않는다.
- 이미지 실행·대기 중에는 원본·공개 편집·삭제·저장을 잠근다. 새로고침과 실패 재시도는
  최신 서명 미리보기를 이어받으며 완료 사진과 공개 블록을 보존한다.

## 공개 저장 조건

새 공개 저장에는 실제 Persona 필수 형식·이름/성별/생년월일·공개 자기소개·사진, State의 존재와
0–100 정수인 컨디션 5개·affection·숨겨진 특성 이름/강도 일치, Memory의 `# 현재 생활` 제목과 실제 내용을
모두 요구한다. 생년월일은 정체성 섹션의 `생년월일: YYYY-MM-DD` 한 줄이며,
Gregorian 달력에서 실제 존재하는 날짜이고 UTC 오늘 이후가 아니어야 한다. 공개 기본 정보의
수동 나이 행은 거부한다. 비공개 초안은 생년월일이 없어도 저장할 수 있다. 형식 버전 표시는 조건 충족의 근거가 아니다. 클라이언트의 공개 전환과
서버의 저장 경계에서 같은 공용 검사로 검증한다. 부족한 문서는 탭 이동 가능한 안내로
표시한다. 미완성 문서는 비공개 초안으로 저장할 수 있다.

기존 공개 인물은 생년월일 누락만으로 자동 비공개 전환하거나 목록에서 제외하지 않는다.
조회 중 날짜를 만들어 넣지 않는다. 전체 Persona 개선에서는 누락되거나 유효하지 않은 날짜를
기존 나이·연령대·성장 배경에 맞춰 보완하고 개선 요약·편집 초안에 반영한다. 기존의 유효한
생년월일은 보존하며, 일반 저장으로 확정한다. 다음 공개 상태 저장에서 새 조건을
적용하며, 기존 공개를 해제하는 저장은 계속 가능하다.
서명된 편집 원본으로 stale 요청을 검사하고, D1 revision CAS와 atomic batch로 세 문서와 사진 연결을 함께 확정한다.
충돌한 쓰기는 다른 저장의 사진 연결을 변경하지 않는다. 생성 사진은 먼저 R2에 업로드하고 private draft에 반영한다.
운영자 저장 전까지 공개 데이터는 바뀌지 않는다. 편집 draft·사진별 작업·중복 제출 상태는 공통 Durable Object에 영속화한다.

## 읽기와 표시

공개 API는 이름·사진·첫 자기소개 요약(`bio`)과 구조화된 공개 `profile`만 제공한다.
작성 원본은 Markdown 하나를 유지하고, 서버가 공개 경계 뒤의 내용만 결정적으로
변환한다. 조회 중 모델 호출·별도 프로필 사본 저장은 없다.

`profile`은 plain-text `introduction`과 작성 순서대로 정렬한 `sections`다. Catalog는
Persona 정체성의 유효한 생년월일에서 현재 나이를 계산해 별도 `age`로 제공한다.
나이는 UTC 오늘 날짜 기준이며, 2월 29일 출생의 비윤년 생일은 3월 1일에 도달한 것으로
판정한다(월·일 비교). 기존 API 배포 순서를 고려해 `age`는 API 전환 기간에 선택 필드다.

| `type`                      | 데이터                                     | 표시              |
| --------------------------- | ------------------------------------------ | ----------------- |
| `basics`                    | `title`, `items: [{ key?, label, value }]` | 기본 정보 행      |
| `lifestyle`, `relationship` | `title`, `items: [{ label, value }]`       | 생활·관계 정보 행 |
| `interests`                 | `title`, `items: string[]`                 | 관심사 태그       |
| `prompt`                    | `question`, `answer`                       | 질문/답변 카드    |
| `text`                      | `title`, `body`                            | 자유 제목과 글    |

기본 정보의 `key`는 직업 `occupation`, 지역 `location`이다. 나이는 정체성에서 계산해
표시하므로 profile 섹션에 중복 저장하지 않는다. 그 밖의
공개 정보는 `label`과 `value`만 유지한다. 자유 항목의 목록은 줄바꿈한 plain text로
보존한다. 강조·링크는 표시 텍스트만 남기고 HTML·링크 정의는 제거한다. 내용 없는
선택 항목은 생략한다. 정형 목록이 아닌 글은 같은 제목의 `text` 섹션으로 보존한다.
특정 공개 제목에 목록 형식을 강제하지 않으며 문장·일반 목록도 편집·개선·공개 저장에서
허용한다. 편집기·개선 결과·저장은 같은 공용 문서 검사로 필수 비공개 구조·이름·성별·
공개 경계·첫 자기소개 문단을 확인한다. 실제 문서 오류는 줄 번호와 이유를 표시한다.

Discovery는 Markdown을 파싱하거나 렌더링하지 않는다. Admin 미리보기는 정체성의
생년월일에서 `ageOn`을 사용해 계산한 숫자 나이를 Discovery와 같은 형식으로 표시하고,
비공개 원문이나 공개 글에서 나이를 추측하지 않는다. Admin 미리보기는 같은
변환·표시 컴포넌트를 사용한다. 정보는 `dl` 행, 관심사는 태그, 문답은 질문 카드로
표시한다. 카드에는 정체성에서 계산한 나이, 공개된 직업·지역과 짧은 첫 소개를 표시한다.
비공개 설정이나 소개 문장에서 누락된 정보를 추측해 채우지 않는다.

배포 순서는 API 읽기 계약 → Discovery → Admin 공개 응답이다. `profile`은 API가
배포되는 동안 선택 필드로 유지한다. 실행 중인 구 API 응답에도 기존 `bio`를 표시하며
이전 Markdown 응답은 파싱하지 않는다. 기존 ↑/↓·Escape, 사진·스타일 선택,
Like/Pass와 연락처 입력을 유지하며 마지막 내용이 플로팅 버튼 위까지 스크롤되도록 한다.

## 페르소나 개선

이전 `형식 정리` 작업과 제출 경로는 `페르소나 개선`으로 대체한다. 이미 수정한 정상
Persona도 현재 편집본을 기준으로 최신 작성 기준과 공개 프로필 정보를 보강할 수 있다.

- 범위는 전체 Persona 또는 공개 프로필만이며, 4,000자 이하의 선택적 개선 요청을 받는다.
- 빈 요청은 부족한 설명·구체적 공개 정보·구성을 보강한다. 기존 사실·말투·수치를 요청과
  무관하게 바꾸지 않고 이름·선택 성별을 검증한다. 의도적으로 숨긴 정보는 복원하지 않는다.
- 전체 개선은 기존 생성·검수·필요 시 한 번 보정 흐름을 사용한다. 공개 전용 개선은
  공개 결과만 원문에 결합하므로 비공개 인물 설정을 보존한다.
- 원문 도구줄의 `페르소나 개선` 버튼은 범위·선택 요청·취소/실행만 있는 모달을 연다.
  취소나 Escape로 닫으면 생성 요청을 보내지 않고 입력을 유지하며 버튼으로 포커스를 돌린다.
- 성공한 생성 결과는 편집 초안에 바로 반영한다. 기존 별도 적용/제안 취소 경로는 제거한다.
  CodeMirror의 같은 편집 영역에서 추가·삭제 diff를 표시하고 `변경 표시`로 표시만 끌 수 있다.
  비교 기준은 직전 개선에 제출한 초안이며 직접 수정해도 유지하고, 재개선 때 갱신한다.
  개선도 실행 취소할 수 있고, 요약은 접힌 보조 정보로 제공한다. 저장 후 diff는 사라진다.
- 저장 원본 충돌은 생성 전후와 저장 경계에서 검사한다. 실패 시 현재 입력과 선택 요청을
  보존하며 사진·State·Memory는 재생성하지 않는다. 공통 저장 전까지 공개 데이터는 유지한다.
- 개선 요청과 결과·요약은 private draft에만 둔다. 공개 응답·페르소나 파일·로그에 넣지
  않는다. 실패는 기존 요청 ID와 원인/코드·단계·소요 시간으로 진단한다.
- 적용으로 Persona와 State가 불일치하면 기존 공개 저장 검사가 안내한다. State·Memory
  수정 또는 개별 재생성은 운영자가 선택한다.

## 검사·명시적 가져오기

형식 버전은 **2**다. 실제 비공개 시트와 필수 공개 자기소개를 검사해 버전을 표시한다.
일반 런타임 파일 로더는 현재 저장 형식만 읽는다. 이전 사본 필드를 계속 읽는 호환
경로를 런타임에 추가하지 않는다.

Admin의 별도 전체 검사 메뉴와 페이지는 제거한다. 형식과 공개 조건은 Persona 편집
화면에서 확인한다. 이전
`description`/`bio`/고정 공개 항목 파일은 **명시적 디자이너 가져오기**에서만 읽어
원본 설정·공개 선택·이미지를 보존한 문서 초안으로 제시한다. 공개하지 않았던
취미를 새로 공개하지 않는다.

변환은 자동 저장하지 않는다. 보강한 내부 설정은 별도 private draft 보고서에 표시한다.
원본 파일이 변경되면 거부하고, 확인한 저장 요청에서만 현재 Markdown 파일로 교체한다.
공개 선택·사진·관리 상태를 유지하며 운영자가 문서 저장과 사진 재생성을 독립적으로 선택한다.
배포는 명시적 기존 파일 변환과 API 읽기 계약을 준비한 뒤 새 클라이언트·작성 흐름을 연결한다.

### 저장 형식 전환 시 운영 확인

현재 로더를 적용하기 전에 실제 저장 디렉터리의 모든 기존 파일을 검사하고 명시적으로
변환해야 한다. 테스트 fixture만 새 형식으로 바꾸고 운영 파일을 남기면 공통 목록 로드가
실패해 Admin 목록과 Discovery 목록이 함께 사용할 수 없게 된다.

이 실패를 실제 두 HTTP 경계에서 확인하고, 기존 4개 파일의 원본을 owner-only 백업한 뒤
검증된 변환기로 형식만 교체했다. 이름·성별·원문(줄바꿈 정규화 제외)·소개·공개 상태·
런타임 관리 설정과 이미지 참조를 비교했으며, 두 목록과 공개 이미지 16개의 HTTP 200을
확인했다. 전체 기존 catalog의 변환 전 실패/변환 후 복구를 회귀 테스트로 유지한다.

## 검증

### 후속 수정: 개선 자동 반영·인라인 diff·단일 초안

- 실제 Admin 요청에서 개선 직후 초안 반영, 저장 전 원본·사진·초기 문서 보존, 새로고침
  복구, 편집 후 재개선의 비교 기준 갱신과 저장 후 diff 제거를 검사한다. 기존 별도 적용·
  제안 취소 제출은 거부한다. 생성 실패 진단의 요청 상관관계와 비공개 내용 제외도 유지한다.
- 항목별 폼 대신 Markdown에서 공개 정보·관심사·문답·자유 항목을 편집·삭제·재정렬해
  프리뷰와 저장 폼에 반영되는 것을 검사한다. 인라인 diff를 껐다 켜도 내용·실행 취소 이력은
  유지되며, 개선 자체도 한 번의 실행 취소로 되돌린다. 이미지 작업 중 편집 잠금도 검사한다.
- 격리 저장소와 결정적 텍스트 생성기로 Chromium 1440×900·375×812에서 모달 취소·Escape·
  포커스 복귀·공개 영역 이동·도움말·자동 반영·diff·실행 취소/다시 실행·재개선·실패 복구·
  저장을 확인했다. 도움말은 모바일에서도 처음부터 읽히며 가로 넘침과 브라우저 예외는 없었다.
- Node 24에서 전체 1,211개 테스트·249개 파일과 파일별 커버리지 100%, 포맷·lint·타입·
  dead code·중복·예외 검사와 Discovery 빌드를 통과했다. `bun run ci`의 실행 시간 제한 뒤
  남은 단계를 개별 실행했다. `verify-gates`는 OpenCode 통합 테스트 타임아웃으로 한 번,
  병렬도를 2로 낮춘 재실행에서는 `host-stories.test.ts`의 HEIC 변환 중복 호출 assertion으로
  coverage 자체 검증을 끝내지 못했다. 이후 수신 폴링 두 개가 공유 북마크를 동시에 읽는
  경쟁을 최소 테스트로 재현하고, 폴링을 직렬화해 중복 이미지 변환·프롬프트 준비를 막았다.
  실제 호스트의 기존 HEIC 검사와 수신·재생·재구축 관련 22개 테스트를 통과했다.
- 최신 `main` 통합 후 전체 1,269개 테스트·258개 파일과 파일별 커버리지 100%, 모든 정적
  검사·Discovery 빌드·`verify-gates`를 통과했다. 구조화된 공개 프리뷰·버전 기록을 유지한
  상태로 1440×900·375×812 브라우저 흐름도 다시 통과했다. 공유 북마크 폴링은 `main`의
  동일한 잠금 구현을 사용하며, 사진 중복 변환 회귀는 기존 수신 경쟁 테스트 파일에 모았다.

### Persona 문서 버전 검증

- 실제 D1 저장과 Admin 요청에서 문서 변경만 버전 추가, 동일 내용 저장, 새 버전으로 복원,
  원자적 저장 실패, 동시 쓰기, 과거 원문과 같은 내용이 된 뒤의 오래된 편집 거부를 검증했다.
  기존 D1 원문을 v1으로 옮길 때 사진·초기값·관리 revision과 시각을 보존하는 것도 확인했다.
- 공개 응답에서 이력·내부 원문 제외, 요청 ID/복원 출처가 있는 실패 진단, 미저장 문서와
  이미지 미리보기 보존, 현재 State와 맞지 않는 공개 복원의 거부를 실제 요청으로 검사했다.
- 실제 OpenCode에서 새 버전과 복원한 새 최신 버전을 차례로 적용하고 다음 모델 요청의
  지침을 확인했다. 기존 대화 기록·State/Memory를 유지하고 낮은 버전 쓰기를 거부한다.
  준비되지 않은 native agent는 제한 시간 안에 준비 실패로 처리하는 것을 검사했다.
- 격리 저장소의 Chromium 1440×900·375×812에서 저장 → 기록/비교 → 복원 취소/확정,
