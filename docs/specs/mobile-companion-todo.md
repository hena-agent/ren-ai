# RenAI 모바일 동반자 TODO

## 목표

**돌아오면 나를 반겨주고, 평소에는 함께 시간을 보내며, 필요할 때는 내 일을 도와주는 AI 동반자.**

사용자가 특별한 목적이나 대화 주제를 준비하지 않아도 켤 수 있는 앱을 만든다. 첫 목표는 ‘돌아오면 반가운 앱’이며, 놀이와 업무 지원은 그 관계 위에 쌓는다.

이 문서는 제품 방향과 앞으로 할 일을 정리한 계획이다. 기존 도메인 모델과 운영 방식을 변경하는 구현 명세나 ADR은 아니며, 변경이 필요한 결정은 아래 TODO에서 확정한다.

## 합의한 방향

- 모바일 앱을 주된 접점으로 한다.
- 페르소나는 사용자 기기에서 함께 지내는 존재로 느껴져야 한다. AI 실행 위치가 기기 내부일 필요는 없다.
- 인간 외에 개, 고양이, 공룡, 마왕, 마녀 등 다양한 존재를 담는 방향으로 확장한다.
- 움직이는 모습은 **2D 원화 + rig-c**로 제작한다고 가정한다. 제품 구현에 앞서 실제 원화와 모바일 기기로 적합성을 검증한다.
- 현재 체형은 공통 베이스로 사용한다고 가정하고 얼굴·표정에 집중한다. 머리카락은 몸 앞/몸 뒤의 합성 관계로 분리한다. [Admin 얼굴 부품 검수 흐름](persona-discovery-admin.md#최신-검증-방향-공통-체형과-얼굴-부품)을 따른다.
- 앱을 열면 사용자를 알아보고 반겨준다. 이어서 대화나 행동을 재촉하지 않는다.
- 평소에는 느슨하게 함께 있고, 대화하거나 장난치다가 자연스럽게 일을 부탁할 수 있다.
- 놀이와 업무에서 같은 성격과 관계가 이어진다.
- AI 실행 엔진은 기존 OpenCode를 재사용하는 방향으로 검토한다.

## 경험 원칙

- **알아보기 → 반가움 표현 → 여유 주기**를 첫 만남의 기본 흐름으로 삼는다.
- 페르소나마다 반기는 방식이 다르다. 같은 환영 문구에 외형만 바꾸지 않는다.
- 이전 대화와 함께한 일을 적절히 이어가되, 매번 질문하거나 과거 일을 꺼내지 않는다.
- 사용자는 말하지 않고 잠깐 머물거나 바로 나가도 된다.
- 미방문에 대한 비난, 죄책감 유도, 관계 유지를 위한 출석·돌봄 숙제를 넣지 않는다.
- 성격은 표현에 드러나고, 맡긴 일은 신뢰할 수 있게 수행한다.

## 0. 최우선: 2D + rig-c 적합성 검증

**현재 단계는 채택을 가정한 검증이며, 실제 제작·재생 품질이 확인된 상태는 아니다.** 아래 결과를 기록하고 진행 여부를 결정한 뒤 앱의 본격적인 구현과 도메인 변경에 들어간다.

2026-11-09 진행: 공식 예제의 idle·hello 빌드와 브라우저 재생, 환영 동작 후 대기 복귀를 확인했다. 자체 원화·실제 휴대폰·비인간형은 미검증이다. 버전 차이와 시각적 경고를 포함한 결과는 [rig-c 검증 기록](mobile-companion-rig-c-validation.md)에 남겼다.

### 검증할 가설

- AI 중심의 제작 흐름으로 RenAI가 원하는 ‘나를 알아보고 반겨주는’ 장면을 만들 수 있다.
- 원화 하나의 성공에 그치지 않고, 다른 페르소나에서도 제작 과정과 품질을 재현할 수 있다.
- 모바일에서 작은 표정과 동작이 잘 보이고, 터치에 반응하며, 지속적으로 재생해도 실행 비용이 수용 가능하다.
- 페르소나별 수정 시간과 생성 비용이 운영 가능한 수준이다. 도구가 무료라는 사실을 제작비가 없다는 뜻으로 해석하지 않는다.

### 제작·실행 흐름의 작업 가정

```text
원화 생성
  → See-through 레이어 분리
  → @rig-c/parts: 부품·메시·뼈대·기본 동작 구성
  → @rig-c/core: 리그·모션 컴파일과 검증
  → @rig-c/play: 모바일 브라우저에서 재생
  → 실제 앱에 넣을 경우 WebView 등 연결 방식 검증
```

- rig-c 자체는 원화나 분리된 레이어를 생성하지 않는다. 이미지 모델과 See-through의 실행 환경은 별도로 준비한다.
- 에셋 제작은 사전 제작 과정이다. 사용자가 앱을 열 때마다 원화 생성이나 리깅을 수행하지 않는다.
- 앱 실행 중에는 완성된 리그와 동작을 사용하고, 이벤트에 따라 동작을 전환한다. 매 프레임의 움직임을 OpenCode가 생성하는 구조로 만들지 않는다.
- 제작 에이전트가 리그를 만드는 역할과, 사용자와 대화하며 일을 수행하는 OpenCode의 역할을 구분한다.

### A. 검증 입력과 기준 준비

- [x] 각 페르소나 편집 화면에서 해당 설명으로 rig-c 원화 한 장을 생성·교체한다. 공통 모델 카탈로그에서 모델을 선택하고, 선택 프롬프트·유료 호출 전 확인·공통 FIFO를 사용한다. 페르소나 ID별 현재 원화 한 장을 별도 영속 저장하며 교체 실패 시 기존 원화를 보존한다. 독립 원화 작업 공간은 제공하지 않는다. 실제 유료 API 품질 검증은 별도로 수행한다.
- [x] 애니메 인물 시트 원본을 필수 참조로 하고 현재 이름·비공개 설정 텍스트를 함께 보낸다. 참조 이미지 입력을 지원하는 공급자별 API를 사용하며 누락·읽기 실패·대기/재시도 중 시트 변경 시 유료 호출을 차단한다. 시트 이미지의 시각적 정체성을 우선하며 공개 소개·State·Memory·OCR 호출은 포함하지 않는다.
- [x] 고정 두 모델 선택을 models.dev 기반 다중 공급자 카탈로그로 교체한다. 공급자/연결 상태 필터·검색·새로고침·fal 추가 페이지와 스키마/단가 확인을 제공한다. 실제 공급자·모델 ID·참조 입력 규격·조회 단가는 서버 서명으로 확인하고 작업에 고정한다. 모델명 enum 없이 호환되는 신규 모델을 선택하며 미연결·미지원은 사유와 함께 비활성화한다.
- [x] 현재 원화의 저장된 분리 PNG로 여는 rig-c 움직임 테스트 페이지를 제공한다. PNG별 독립 메시·텍스처와 부모/자식 관절로 고개·팔꿈치·무릎을 움직인다. 강도·일시정지·원래/굽힌 자세 고정, 관절 드래그/방향키 조정과 레이어별 연결 변경을 제공한다. 원본 보충 레이어는 부위별 근접 관절에 연결하며 가려진 부위 복원·완성 리깅과 구분한다. 원화 생성 API는 호출하지 않는다.
- [x] 기본 몸은 속옷 차림으로 제작하고 의상은 해당 몸을 참조하는 별도 자산·레이어로 저장한다. 몸/의상별 확인·FIFO·CAS·영수증 복구와 움직임의 몸만/의상만/전체·개별 표시를 제공한다. 관절에는 둥근 숨은 겹침 복원을 요청한다.
- [ ] 새 기본 몸·의상 실출력으로 둥근 관절 겹침, 옷 아래 신체, 소매·장식 정합과 굽힌 자세를 검수한다. 구현·요청 지시의 검증과 실제 이미지 품질 합격을 구분한다.
- [ ] 첫 검증용 인간형 페르소나 하나를 정한다. 최종적으로 원하는 그림체와 얼굴 크기에 가까운 원화를 사용한다.
- [ ] 제품용 원화의 생성 모델과 레이어 분리 실행 경로를 정한다.
  - 원화 생성은 로컬 GPU 없이 호스팅 API를 사용한다. Admin 카탈로그의 호환 모델 후보를 비교한 뒤 채택한다. See-through도 원격 실행 경로를 확인한다.
- [ ] 기본 포즈와 부품 분리에 적합한 구도를 정한다. 정면, 팔과 몸 사이의 공간 등 도구의 원화 요구사항을 확인한다.
- [ ] 공식 예제는 설치·구동 확인에 사용하고, 자체 원화로 제작 가능한지는 별도로 확인한다.
- [ ] 패키지 버전, 원화·레이어, 설정, 명령, 수정 내역을 기록할 위치를 정한다.
- [ ] 측정 전에 대상 휴대폰과 브라우저, 목표 프레임률·로딩 시간·메모리·발열의 허용 기준, 제작 시간·비용 예산을 정한다.

### B. 환영 장면 하나 완성

- [x] 먼저 공식 가이드의 리그를 빌드·재생해 개발 환경을 확인한다.
- [ ] 자체 원화에서 레이어 분리 → 리깅 → 검증 → 재생까지 연결한다.
- [ ] 아래 동작을 하나의 장면으로 연결한다.
  1. **대기:** 쉬거나 무언가를 하면서 작은 호흡·눈 깜빡임이 있다.
  2. **알아보기:** 하던 동작을 멈추거나 줄이고 사용자를 향한다.
  3. **반기기:** 눈·얼굴·고개·몸짓으로 반가움을 표현한다.
  4. **기다리기:** 반긴 뒤 자연스럽게 대기로 돌아간다.
  5. **터치 반응:** 사용자의 가벼운 터치에 반응하고 다시 안정된다.
- [ ] 반복 터치와 동작 중 새로운 입력에서도 갑작스러운 포즈 전환이나 리그 깨짐이 없는지 확인한다.
- [ ] 머리카락·옷·관절의 틈, 가려진 부분, 메시 변형을 사람이 직접 확인한다.
- [ ] 전신 데모뿐 아니라 실제 앱에서 사용할 얼굴 크기에서도 시선과 미소가 자연스러운지 확인한다.
- [ ] 동작만 보는 경우와 짧은 환영 문구를 함께 보여주는 경우를 비교해, 문구 없이도 반가움이 전달되는지 기록한다.

### C. 표정·음성·체형의 한계 확인

- [ ] 기본 생성 동작과 추가로 작성한 표정·동작을 구분하고 각각의 제작 시간을 기록한다.
- [ ] 미소, 관심을 갖고 듣기, 생각하기를 어느 수준까지 표현할 수 있는지 확인한다.
- [ ] 음성 대화를 도입하기 전에 입 모양 세트와 립싱크의 추가 제작·재생 지원을 확인한다. 기본 파이프라인에 포함돼 있다고 가정하지 않는다.
- [ ] 인간형 검증 후 고양이 또는 공룡 하나로 같은 제작 흐름을 시도한다.
- [ ] 자동 제안이 사람의 관절·레이어 태그에 의존하는 부분과 비인간형에 필요한 개별 설정을 기록한다.
- [ ] 서로 다른 체형에서 재사용되는 부분과 새로 제작해야 하는 부분을 구분한다. 하나의 골격으로 전부 처리한다고 가정하지 않는다.

### D. 모바일 재생 검증

- [ ] 실제 대상 휴대폰의 브라우저에서 로딩 시간, 에셋 크기, 프레임률, 메모리, 터치 응답을 측정한다.
- [ ] 연속 재생 중 발열과 배터리 소모를 관찰하고 기기·화면 밝기·측정 시간 등 조건을 기록한다.
- [ ] 화면 크기와 픽셀 비율이 달라져도 얼굴·선·텍스처가 선명한지 확인한다.
- [ ] 앱 또는 브라우저가 백그라운드로 가면 불필요한 재생을 멈추고, 복귀하면 안정적으로 이어지는지 확인한다.
- [ ] 네이티브 앱을 선택한다면 해당 WebView에서도 같은 항목과 앱 UI 연동을 확인한다. 모바일 브라우저 성공만으로 앱 검증을 완료 처리하지 않는다.

### E. 제작 비용·재현성·판정

- [ ] 원화 생성, 레이어 분리, 리깅, 수정, 검수의 시간과 비용을 단계별로 기록한다.
- [ ] AI 호출·GPU 사용·재시도 비용과 사람이 직접 수정한 시간을 구분한다.
- [ ] 고정한 입력·버전·설정으로 다른 실행에서도 결과를 재현할 수 있는지 확인한다.
- [ ] 도구의 구조 검증 결과와 사람이 판단한 시각적 품질을 따로 기록한다. 빌드 통과를 매력적인 환영의 증거로 삼지 않는다.
- [ ] 도구, 생성 모델, 레이어 분리 모델, 원화의 상업적 사용 조건을 확인한다. 공식 예제 에셋의 조건과 도구의 MIT 라이선스를 혼동하지 않는다.
- [ ] 결과를 `docs/specs/mobile-companion-rig-c-validation.md`에 기록한다. 환경·버전, 재생 영상, 측정값, 비용, 수작업, 실패 사례와 미확인 항목을 포함한다.
- [ ] 검증 결과에 따라 **제품 구현 진행 / 보완 후 재검증 / 접근 재검토** 중 하나를 결정한다.

### 검증 완료 기준

- 자체 원화의 환영 장면이 실제 모바일에서 동작하고, 알아보기·반기기·기다리기의 차이가 전달된다.
- 표정 품질, 모바일 실행 비용, 제작 시간·비용이 사전에 정한 기준을 만족한다.
- 인간형과 비인간형의 결과를 구분해 지원 가능한 초기 범위를 명시한다. 비인간형이 미확인 또는 기준 미달이면 지원 완료로 취급하지 않는다.
- 버전과 입력으로 제작 과정을 재현할 수 있고, 자동화되는 부분과 수작업이 필요한 부분이 드러나 있다.
- 립싱크 등 미확인 기능이 첫 제품 범위에 필요하다면 해당 검증을 마친다. 필요하지 않다면 후속 범위로 명시한다.

## 1. 첫 경험 구체화

- [ ] 참고 대상으로 언급한 Instinct의 정확한 제품과 링크를 확인한다.
- [ ] 첫 페르소나 하나를 선택하고 성격, 외형, 반기는 방식을 정한다.
- [ ] 페르소나가 머무는 작은 공간 하나를 정한다.
- [ ] 아래 흐름을 화면과 짧은 시나리오로 구체화한다.
  - 앱을 열면 페르소나가 쉬거나 무언가를 하고 있다.
  - 사용자를 알아보고 시선·표정·자세가 바뀐다.
  - 짧게 반기고 사용자의 반응을 기다린다.
  - 사용자는 그냥 머물거나, 터치하거나, 말을 걸 수 있다.
- [ ] 첫 방문, 다시 방문, 잠깐 앱을 전환했다 돌아오는 경우의 반응을 정한다.
- [ ] ‘논다’의 초기 범위를 가벼운 수다와 작은 터치 반응으로 구체화한다.
- [ ] 첫 업무 기능 하나를 고른다. 실제로 완료할 수 있는 범위와 필요한 연결을 함께 정한다.

## 2. 제품·도메인 결정

- [ ] 사용자마다 페르소나의 기억과 변화가 독립적으로 쌓이는 모델을 채택할지 결정한다.
  - 제안: 같은 페르소나를 선택해도 나와 함께한 경험은 다른 사용자에게 영향을 주지 않는다.
  - 현재의 공유 State·Life memory 모델과 비교해 바뀌는 소유권과 경계를 명시한다.
- [ ] 기존 사용자, Conversation, 페르소나 선택·관계 종료 흐름을 새 앱에서 어떻게 다룰지 정한다.
- [ ] 일정·파일·업무 정보와 도구 권한의 사용자별 소유권 및 접근 경계를 정한다.
- [ ] 먼저 말을 거는 시점, 알림 설정, 조용히 있어야 하는 조건을 정한다.
- [ ] 결정된 변경을 CONTEXT.md와 필요한 ADR에 반영한다.

## 3. 검증 이후 실행 구조 결정

- [ ] 모바일 앱의 대상 플랫폼과 구현 방식을 정한다.
- [ ] rig-c 검증 결과를 바탕으로 초기에 지원할 체형·표정·동작과 에셋 제작 절차를 확정한다.
- [ ] 검증한 버전의 리그·텍스처·동작을 모바일 앱에 전달하고 로드·해제하는 방식을 정한다.
- [ ] 모바일 앱·RenAI 서비스·OpenCode의 책임과 연결 방식을 정한다.
  - 앱: 모습과 움직임, 대화, 터치 반응, 작업 상태와 결과 표시.
  - RenAI 서비스: 사용자 연결, 지속적인 기억, 작업 기록, 예약과 알림.
  - OpenCode: 모델 호출, 대화 실행, 도구 사용, 여러 단계의 작업 수행.
- [ ] 기존 OpenCode 세션·플러그인에서 재사용할 부분과 변경할 부분을 확인한다.
- [ ] AI 실행 상태를 페르소나의 동작과 연결하는 방식을 정한다.
- [ ] 앱 종료·재접속·실행 중단 시 대화와 작업을 복구하는 흐름을 정한다.
- [ ] 첫 업무에 필요한 기기 기능 또는 외부 서비스 연결을 정한다.
  - 서버의 OpenCode만으로 개인 휴대폰이나 컴퓨터에 접근할 수 있다고 가정하지 않는다.

## 4. 작은 제품을 끝까지 연결하기

각 단계는 이전 단계가 실제로 동작하는 상태에서 추가한다.

- [ ] **환영:** 앱을 열면 페르소나 하나가 사용자를 알아보고 반겨준다.
- [ ] **함께 있기:** 작은 터치 반응과 텍스트 대화를 같은 공간에서 제공한다.
- [ ] **연속성:** 앱을 닫고 다시 열어도 대화와 기억을 이어간다.
- [ ] **도움:** 선택한 업무 하나를 요청부터 완료·실패 안내까지 연결한다.
- [ ] **앱 밖의 연속성:** 앱을 닫아도 맡긴 작업이 이어지고, 설정에 따라 완료 알림을 보낸다.

## 5. 경험 검증과 다음 확장

- [ ] 실제 기기에서 환영의 시선·타이밍·말투가 자연스러운지 확인한다.
- [ ] 아무것도 입력하지 않아도 편안하게 머물 수 있는지 확인한다.
- [ ] 함께 놀다가 일을 부탁할 때 관계와 성격이 이어지는지 확인한다.
- [ ] 이전 만남을 기억하는 반응이 반갑고, 과도하거나 반복적이지 않은지 확인한다.
- [ ] 앱 재접속과 작업 실패 후에도 상태가 정확하게 보이는지 확인한다.
- [ ] 아래 질문으로 첫 버전의 가치를 판단한다.
  - 시킬 일이 없어도 다시 앱을 켜고 싶은가?
  - 페르소나가 나를 알아보고 반긴다고 느끼는가?
  - 일이 생겼을 때 이 존재와 같이 해보고 싶은가?
- [ ] 검증 결과에 따라 음성, 추가 페르소나, 함께하는 활동, 업무 도구, 개인 컴퓨터 연결의 우선순위를 정한다.

## 첫 버전의 완료 기준

**페르소나 하나와 작은 공간 하나에서, 앱 열기 → 반겨주기 → 함께 있기 → 대화·업무 도움 → 다음 방문에서 이어가기까지 실제로 동작한다.**

rig-c 적합성 검증의 완료와 첫 제품의 완료는 별개다. 환영 장면 검증만으로 대화·기억·업무 기능이 구현됐다고 판단하지 않는다.
